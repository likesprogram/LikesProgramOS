# Baleen 引导器

**Baleen 是 LikesProgramOS 的自家引导器子项目**，源码位于 `Packages/Baleen`，与系统本体 `LikesProgramOS` 平级。

它的职责只有一件事：**从不同硬件上找到指定 Ext4 文件系统的指定路径，把系统内核装载起来并完成交接。**

本文描述完整 Baleen 的目标职责与阶段划分。BIOS 一级引导的当前 ABI 单独定义在 [Baleen 一级引导契约](一级引导契约.md)，Stub 结构与自身完整性见 [Stub 约定与结构](../../../Packages/Baleen/Stub/README.md)，失败原因的稳定编号登记在[失败诊断编号](失败诊断编号.md)。

## 一、名字与命名口径

**Baleen 取自鲸须**：须鲸用鲸须从大量海水与浮游生物中筛出需要的食物，正如引导器要从多种固件、控制器、总线和介质中筛出唯一的目标卷，并从中取走指定的内核镜像。

**为什么不用 BootLoader 当名字**：那是这个组件的功能描述，不是名字。功能描述会在讨论、产物命名和诊断信息里反复出现——“BootLoader 加载失败”说不清是引导器的哪一段失败。项目内统一用 Baleen 指代这套引导链，产物名加 `Baleen` 前缀。

| 用在哪 | 怎么写 |
| --- | --- |
| 子项目、文档、讨论 | Baleen |
| 产物名 | `BaleenIPL.bin`、`BaleenStub.bin`、`BaleenCore.bin`、`BaleenLayout.bin`（见第八节） |
| 固件要求的固定名 | `BOOTX64.EFI` 等按协议保留，不套用本项目命名（见[后缀设计](../后缀设计.md)第六节） |

与其他生态重名时按[后缀设计](../后缀设计.md)第八节的口径处理：同名不构成关系，也不承诺互通。

## 二、职责边界

| Baleen 做 | Baleen 不做 |
| --- | --- |
| 在固件环境下枚举控制器、总线和设备，确定可引导介质 | 不加载 `.osm`、`.drv`、`.exe`；这些是内核装载器的职责 |
| 识别介质形态与分区布局，定位候选系统卷 | 不做通用文件系统操作：Ext4 读取仅为定位内核镜像服务，见第五节 |
| 校验卷身份（标识、布局描述、版本） | 不解析构建清单之外的容器内部结构 |
| 在系统卷的指定路径读取内核镜像与所需清单 | 不为第三方引导协议做适配，见[内核启动与固件边界](../内核启动与固件边界.md) |
| 按引导模式准备机器状态、装载镜像、交付 `BootInfo` | 不建立运行时设备模型；设备模型属于内核 |
| 引导选择器职责：选版、持久记录试启动状态、失败回退 | 不做运行期更新编排；那是 Updater 的职责 |

上表是整套 Baleen 的边界，具体按阶段划分如下。

| 阶段 | 负责内容 |
| --- | --- |
| BIOS IPL | 只做描述符区与 Stub 段的结构、起止扇区校验，装入 Stub，按 ABI 交权；任一失败诊断并停机 |
| BIOS Stub | A20、内存图、实模式磁盘会话、自身内存初始化，以及按 [Stub 说明](../../../Packages/Baleen/Stub/README.md)第二节的契约定位 BaleenCore、校验其镜像头与摘要、装载并交权 |
| BIOS BaleenCore | 入口、横幅与诊断、交权块与镜像事实核对、CPU 快照、运行期段表与中断表；`BaleenLayout.bin`、Ext4、系统卷定位、内核集选版与摘要 / 签名验证、持久状态和内核交接 |
| UEFI | UEFI 侧的布局、卷访问、内核集验证、选版与交接；该路径绕过 BIOS IPL 与实模式 Stub |

描述符区的 Stub 段仅定位 Stub 文件，与描述系统卷及内核路径的 `BaleenLayout.bin` 不是同一对象。IPL 不解析布局描述、Stub 头或文件系统，不检查 Stub 的 BSS、BuildId、摘要与签名。后续阶段缺失或占位件主动停机，不构成 IPL 缺陷；IPL 是否满足自己的边界仍须独立验证。

**引导器与内核各自持有文件系统代码，这不是“两套实现”。** [内核架构与自举闭包](../内核架构与自举闭包.md)禁止的是同一内核模块或驱动维护“引导简版 / 运行期完整版”，因为它们在同一个地址空间、同一套资源记录里工作。Baleen 独立运行在固件环境，与内核不共享地址空间，它的 Ext4 读取是为装载镜像服务的最小只读实现，内核的 Ext4 是含日志回放与写入的完整实现。两者不需要共享代码，但**可识别的卷格式范围必须一致**：镜像组装器为一套布局生成两边的访问路径，引导器读不了的卷，内核也不该被要求读出内容。

## 三、引导模式

引导模式分三层理解：**固件环境**决定 Baleen 以什么形态运行，**交权入口**决定内核以什么机器状态接手，**验证链**决定镜像要不要签名。本项目按支持梯队排序。BIOS 磁盘接口依据见 [一级引导契约](一级引导契约.md)第八节；coreboot payload 与 PVH 入口分别参见 [coreboot 官方文档](https://doc.coreboot.org/payloads.html)及 [Xen PVH 启动 ABI](https://xenbits.xen.org/docs/unstable/misc/pvh.html)。

### 3.1 固件环境

| 梯队 | 环境 | 说明 |
| --- | --- | --- |
| 必须支持 | **Legacy BIOS / CSM** | 16 位实模式起步，用 BIOS 磁盘与显示服务完成介质访问；光盘走 El Torito 引导目录 |
| 必须支持 | **UEFI x64** | 以 PE/COFF 固件应用形态运行，使用 Boot Services 的块设备与文件系统协议；包含无 CSM 的纯 UEFI 机器（通称 UEFI Class 3） |
| 明确不支持 | **UEFI IA32（32 位固件）** | 内核入口是长模式、UEFI 侧引导器是 x64 固件应用，32 位固件上没有可引导的载荷；ESP 里的 `\EFI\BOOT\BOOTIA32.EFI` 是一件**只打印不支持提示**的 IA32 应用（[UEFI 侧说明](../../../Packages/Baleen/Uefi/README.md)），让用户知道死在哪里，不承担引导 |
| 计划支持 | **coreboot** | 开源固件平台，以 SELF 机制装载 payload：SeaBIOS payload 提供 BIOS 环境，edk2 payload 提供 UEFI 环境，Baleen 以对应形态接入 |
| 计划支持 | **coreboot 发行版** | 在 coreboot 之上打包好 UEFI、SeaBIOS 或 LinuxBoot 环境的发行版（如 Dasharo）；Baleen 按其中实际提供的环境接入 |
| 计划支持 | **虚拟化直启（PVH）** | 由 Xen 引入，被 QEMU、Cloud Hypervisor、Firecracker 等采用的入口约定：内核以 ELF note 声明 32 位保护模式入口，不使用固件服务。见 3.2 |
| 记录在案 | **LinuxBoot** | 用 Linux 内核与 u-root initramfs 取代固件中大部分驱动与阶段，再由 kexec 载入目标内核；Baleen 的接入方式是作为其载入对象 |
| 记录在案 | **Slim Bootloader** | Intel 维护的开源固件，覆盖其多个客户端与嵌入式平台；是否作为接入目标待评估 |
| 记录在案 | **U-Boot** | 主要面向嵌入式平台，coreboot 也可把它当作 payload；本项目不将它列为 PC 首要目标 |
| 记录在案 | **网络引导（PXE / HTTP Boot）** | 两侧固件都提供网络引导基础：BIOS 侧经网卡 PXE Option ROM，UEFI 侧经固件 PXE 与 HTTP Boot；接入方式与时机列入后续扩展，不在首批交付 |

**这张表不承诺“固件名字相同就一定能启动”。** 同一固件在不同机器上开放的协议与服务可能不同，Baleen 按实际可用的接口探测，探测不到就报告，不猜测。

**实现次序：BIOS 路径先行，UEFI 侧随后。** 两条路径的目标职责相同——识别介质、定位系统卷、装载内核、准备机器状态——差别只在固件环境与机器状态的准备方式。交付按下面的次序安排，这不改变上表的支持范围：

- **BIOS 路径先收尾**：IPL → Stub → BaleenCore → 内核交接整条链完成到“从受支持介质启动并成功进入内核”，并通过实机与模拟器验证；
- **UEFI 侧在之后实施**：`BOOTX64.EFI` 以固件应用形态实现布局描述读取、卷访问、内核集验证与交接，与 BIOS 路径共用同一份布局描述与系统卷布局。

**在 UEFI 侧实施之前，介质上的 `BOOTX64.EFI` 是占位件**：它只证明固件侧的发现与加载路径可用（分区表、ESP 与 El Torito EFI 项），不代表 UEFI 引导已经可用，也不应被当作可用的启动路径。

### 3.2 交权入口

| 入口 | 进入内核时的状态 | 谁的机器状态准备 |
| --- | --- | --- |
| BIOS 路径 | IPL 从实模式起步并交给 Stub；Stub 负责 A20、内存图与 BaleenCore 装载，BaleenCore 完成面向内核的机器状态准备 | Baleen 自建；Stub → BaleenCore 的装载位置、格式、模式与交权按 [Stub 说明](../../../Packages/Baleen/Stub/README.md)第二节的契约执行 |
| UEFI 路径 | Baleen 作为固件应用运行，在交权前退出 Boot Services；内核在 `KernelMain` 第一步核对并确认固件启动服务已失效 | Baleen 准备，内核确认 |
| PVH 直启 | 内核以 ELF note（`XEN_ELFNOTE_PHYS32_ENTRY`）声明 32 位保护模式入口，进入时分页关闭，无固件服务可依赖 | Baleen 或虚拟机监视器按约定准备 |

**无论走哪条入口，内核看到的都是同一份 `BootInfo`。** 交权状态必须显式传递：UEFI 的 Boot Services 仍有效时，Baleen 在准备完成并取得有效内存图后调用 `ExitBootServices`；若已退出，不得重复调用，由 `BootInfo` 标记状态。BIOS 交权后不再调用 BIOS 服务。完整边界见[内核启动与固件边界](../内核启动与固件边界.md)。

### 3.3 验证链

| 机制 | 作用层级 | Baleen 的应对 |
| --- | --- | --- |
| **UEFI Secure Boot** | 固件验证引导程序镜像 | 提供可签名的 PE/COFF 形态；未签名或签名不受信任时固件不会执行它，这与本项目无关 |
| **Measured Boot（TPM）** | 固件与引导器把度量值记录进 PCR | 镜像与布局描述保持可度量、可复现：同一构建产出同样的字节 |
| **Intel Boot Guard / AMD 平台安全处理器** | 验证固件自身 | 在 Baleen 之下，不属于本项目可控范围 |
| **本项目签名与信任锚** | 验证内核集与构建清单 | 由引导选择器在装载前检查，见[内核集清单与签名](../内核集清单与签名.md) |

Secure Boot 与项目自身的签名是两条独立的链：前者让固件愿意执行 Baleen，后者让 Baleen 愿意装载内核集。两者不能互相替代。

IPL 当前没有 Stub 头、摘要或签名检查，这是分工而不是缺口。Stub 与 BaleenCore 镜像的文件长度、内存长度、入口、Baleen BuildId 与摘要定义在 [Stub 约定与结构](../../../Packages/Baleen/Stub/README.md)，由 `PackImage` 在构建期打包并校验、由 Stub 在运行期自检自身、在交权前校验 BaleenCore（第二、三节）；无头的开发占位件由组装器显式放行。Stub 的自校验与它对 BaleenCore 摘要的校验都不能构成执行前认证或信任根；Baleen 构建身份也不能代替内核集 BuildId。

## 四、硬件与介质支持范围

| 介质 | 引导期访问方式 | Baleen 看到的卷 |
| --- | --- | --- |
| 内部硬盘（SATA / NVMe / 老 IDE） | 优先走固件的磁盘服务或块协议；固件覆盖不到该控制器时走 Baleen 的最小控制器路径 | 分区上的 Ext4 卷 |
| U 盘、移动硬盘、外置 SSD | **只用固件提供的 USB 引导能力** | 分区上的 Ext4 卷，或混合镜像上的 ISO9660 卷 |
| ISO 镜像（写入 U 盘 / 移动硬盘、虚拟机挂载、物理光驱） | 固件的光盘访问路径，或按 U 盘方式引导 | ISO9660 卷，系统卷为其内部文件 |

**BIOS 路径的介质支持范围**：硬盘与 USB-HDD 按逻辑扇区 512 或 4096 访问，光盘的无仿真路径固定 2048；设备访问只经固件 INT 13h，不需要 Baleen 自带 USB、AHCI 或 NVMe 驱动。软盘、USB-FDD 与 USB-ZIP 不在范围内。引导二进制与逻辑扇区单位无关（载荷按 4096 对齐，扇区大小在运行期询问固件），同一份产物可写进 512e 或 4Kn 介质；**MBR 与 GPT 共用同一套引导区**，分区表由部署侧按目标设备生成，见[启动介质与文件系统](../Common/启动介质与文件系统.md) 4.1 与 4.2。各类启动模式的访问链见[启动介质与文件系统](../Common/启动介质与文件系统.md) 1.1。

**引导期的介质访问优先走固件能力。** BIOS 把可引导设备作为驱动器号暴露，UEFI 通过块设备协议暴露；能走固件就走固件，这是 Baleen 保持小体积的前提。

**Baleen 自建访问路径只有一个适用场合**：固件的磁盘服务覆盖不到目标控制器（例如 UEFI 下固件没有为该 NVMe 或 AHCI 控制器提供块协议）。此时 Baleen 按自己的最小控制器访问路径读取目标卷，这条路径只服务引导，不建立内核那样的设备模型。

**USB 不在此列。** 固件不提供 USB 引导支持的机器上，从 USB 介质启动不在支持范围；Baleen 不自带 USB 栈。内核的 USB 栈是运行期实现，此刻还没有运行，也不能被引导器依赖。

**ISO 是分发形态，不是物理设备。** 写入 U 盘或移动硬盘的镜像要在同一份字节上同时满足光盘与磁盘两种引导记录要求；虚拟机选择 ISO 文件时按虚拟光驱引导。三种方式在内核侧是同一条路径，见[启动介质与文件系统](../Common/启动介质与文件系统.md)第二节。

## 五、卷定位与内核路径

**目标是一个卷加一条路径，不是一个固定块偏移。** 以下由 BaleenCore / UEFI 执行，IPL 只按描述符区里 Stub 段的起止扇区读取 Stub：

1. **拿到候选设备**：由固件枚举或自行探测得到可引导设备列表。
2. **读布局描述**：在约定位置找到 `BaleenLayout.bin`，取得卷标识、系统卷位置、内核路径、引导状态区域及格式版本；字节表、写入位置与校验见[布局描述](布局描述.md)。布局描述不固定占用整盘 LBA1，不覆盖分区表或固件要求的区域。
3. **校验卷身份**：读 Ext4 superblock，核对卷标识与布局描述一致；不一致就换下一个候选设备，不猜测。
4. **按路径读内核**：逐级解析目录项与 inode，按 extent 读取内核镜像文件；路径与文件名由布局描述给定。
5. **校验后装载**：核对摘要与签名，按引导模式把镜像放到约定位置并准备机器状态。

**Ext4 读取是最小只读实现**，边界明确：

| 项 | 约定 |
| --- | --- |
| 能力 | 识别 superblock 与特性标志、读块组描述符与 inode、走 extent 树、解析目录项、读常规文件 |
| 不支持 | 不支持的特性标志（未知 `INCOMPAT` 位、缺失 `FILETYPE` 与 `EXTENTS` 前提位）、未干净卸载的卷、加密、内联数据等；遇到就明确拒绝并报告 |
| 符号链接 | 布局描述给出的路径不得依赖符号链接；镜像组装器保证这一点 |
| 写入 | **绝不写系统卷**。Baleen 对系统卷只有读操作，写操作仅针对引导状态区的裸块记录 |
| 布局约束 | 镜像组装器保证系统卷布局落在支持范围内；不支持的布局在构建或装载时明确拒绝，不做兼容性猜测 |

**卷定位失败的处理**：线索不足时继续在受支持设备中查找并验证，无法唯一定位就报告失败，不能猜测磁盘。这条约束同样适用于内核：内核拿到 `BootInfo` 里的设备线索后自己再校验一次卷标识和布局信息。

## 六、装载与交接

Baleen 交付给内核的内容：

| 项 | 内容 |
| --- | --- |
| 机器状态 | 引导模式要求的寄存器、栈、页表与长模式状态；进入内核后不得依赖任何固件服务 |
| 内核镜像形态 | 镜像文件起点的[内核镜像数据](内核镜像数据.md)与它给出的入口点：数据声明长度、内存跨度、装载地址与要求的 `BootInfo` 版本，并带整幅镜像的摘要；装载前核对数据与摘要，签名与选版属引导选择器职责。内核镜像不带固件可直接识别的标准头，固件接触的是 Baleen 自己 |
| `BootInfo` | 尺寸与版本、内存图、启动设备线索、系统卷标识、CPU/固件信息、可用输出通道、资源所有权，以及可选的内核集与试启动身份 |
| 所有权信息 | 哪些内存与固件资源已由 Baleen 占用、哪些交给内核接管，避免内核把引导器的残留当成可用资源 |
| 失败报告通路 | 交权前后各自的错误输出方式，保证“引导器失败”和“内核失败”可区分 |

`BootInfo` 的字段定义、版本规则与生成工具由 HostSDK 提供；内核侧只核对尺寸与版本，见[内核启动与固件边界](../内核启动与固件边界.md)。**第三方引导方式要用自己的实现构造同一份 `BootInfo`**，本项目不为它们提供适配层。

### 6.1 启动来源

内核与运行期更新都要知道“这次是从哪儿起来的”：更新要把新内核集写进**同一个卷**、发布到**同一条路径下的集根**、把 `Pending` / `Trying` / `Confirmed` 记录写回**同一处状态区域**。这些事实在引导期都是已知的，因此由 `BootInfo` 给全，**不让内核到设备里猜**——猜错就是写坏别的盘。

| 字段 | 语义 | 谁填 |
| --- | --- | --- |
| `LayoutOffset` | 布局描述在启动介质上的字节偏移；0 表示未提供 | BaleenCore / UEFI：取 `LayoutDescriptor::kOffset` |
| `VolumeOffset` / `VolumeBytes` | 系统卷在启动介质上的偏移与长度；两个都为 0 表示未提供，只给一个算不一致 | 两者：取自布局描述 |
| `StateOffset` / `StateBytes` | 引导状态区域在启动介质上的偏移与长度；两个都为 0 表示该介质没有状态区域（只读介质），只给一个算不一致 | 两者：取自布局描述 |
| `MediumBytes` | 启动介质容量，字节；0 表示引导器不知道 | UEFI：块设备协议的容量；BIOS：交权块没有这个事实，填 0 |
| `VolumeUuid[16]` | 系统卷标识（Ext4 `s_uuid`），全零表示未提供 | 两者：取自布局描述 |
| `KernelPath` / `KernelPathBytes` | 本次装载的内核镜像在卷内的路径（ASCII，不带结尾空字符） | 两者：取自布局描述；集根由它推出（`KernelSets/<BuildId>/`）。布局描述不会被更新推进改写，因此它同时是**出厂缺省集**这个最终兜底锚点的身份来源，见[内核集更新与回滚](../内核集更新与回滚.md) 6.1 |
| `DeviceKind` / `DevicePath` / `DevicePathBytes` | 启动设备线索：`UefiDevicePath` 时是 `EFI_DEVICE_PATH_PROTOCOL` 的字节（上限 `kDeviceClueMaxBytes`＝512，超出即按未提供交接），`BiosDrive` 时是 1 字节的驱动器号，`None` 表示未提供 | UEFI：分区句柄的设备路径；BIOS：IPL 交权时的 `DL` |
| `LoaderBegin` / `LoaderBytes` | 引导器自身占用的物理区间，内核不得当作可用内存 | 两者：自己的装载跨度 |

**定位规则：线索只用来缩小范围，身份必须由卷标识核对。** 内核按 `DeviceKind` 找到候选设备后，在 `LayoutOffset` 处读布局描述，核对 `VolumeUuid` 与卷内 Ext4 的 `s_uuid` 一致才认；不一致就换下一个候选，**无法唯一定位时报告失败**，与第五节对引导器的约束是同一条。`DeviceKind` 为 `None` 时（例如 UEFI 设备路径过长未能传递）只能靠卷标识在各设备里核对，同样不允许猜。

**内核按低 4GiB 的恒等映射读这些缓冲**：`BootInfo` 自身、内存图数组、内核路径字符串与设备线索都必须在 4GiB 以下；引导器把它们放在自己的映像里，因此映像被装到 4GiB 以上时内核读不到，会按 `WARN` 报告并按“未提供”处理（内存图读不到则在内核侧直接失败）。

**字段只追加、不移动。** 这些字段与[内核集清单与签名](../内核集清单与签名.md)第七节的 `KernelSetBuildId` / `AttemptId` 一样，属接口首次发布前的设计调整：直接加进 `Version=1`，尺寸随字段增加，既有字段偏移不变。内核核对 `Bytes` 与 `Version`，**读不到的字段按“未提供”处理**——第三方引导器构造的 `BootInfo` 可能比本项目的短，这不是错误。

## 七、引导选择器与状态持久化

自动回滚模式下，由 BaleenCore / UEFI 承担引导选择器职责，IPL 与 Stub 不执行选版。完整的 Pending / Trying / Confirmed / Failed 语义见[内核集更新与回滚](../内核集更新与回滚.md)，引导期的动作是：

1. 读引导状态记录，结合冗余副本选出最新完整有效的一份。
2. 无待试候选时选择已知良好集；有 `Pending` 候选时校验其完整性与签名，把选中的候选身份写入并持久化 `Trying`，再装载。
3. 记录已为 `Trying` 时，判定上次未确认并递减剩余尝试次数：仍有剩余就再记一次尝试并载入候选，次数用尽才记录失败并改选原良好集。
4. 记录有写入痕迹但全部无法验证时不猜测目标集，进入受控恢复或停止；区域从未写过（空区域）按“没有试启动记录”处理，直接启动布局描述指定的缺省集。

**运行期确认写入与引导期选择必须使用同一状态存储后端和记录格式**——记录格式与写入协议见[引导状态记录](引导状态记录.md)。只有该后端能在内核交权前可靠写入并持久化时，才启用试启动；否则直接启动指定的已确认镜像。

选版与验证用的集清单、签名与信任锚见[内核集清单与签名](../内核集清单与签名.md)：集按 `KernelSets/<BuildId>/` 并存，签名由引导器内嵌的公钥表验证，密钥轮换与撤销随引导器更新分发。

## 八、产物与验证

| 组件 | 输出名称 | 被谁载入 | 用途 |
| --- | --- | --- | --- |
| 一级引导 | `BaleenIPL.bin` / `BaleenIPLCd.bin` | BIOS / El Torito 引导目录 | 校验描述符区与 Stub 段结构、起止扇区，装入 Stub 并按 ABI 交权；失败停机 |
| 实模式服务层 | `BaleenStub.bin` | 一级引导 | 自身完整性头与 SHA-256 摘要自检；A20、内存图、固件磁盘会话；按描述符区的 BaleenCore 段定位 BaleenCore、校验其镜像头与摘要、校验装载区、装入高位并交权 |
| 核心阶段（BIOS 侧） | `BaleenCore.bin` | 实模式服务层 | 镜像带与 Stub 同构的完整性头与入口前缀，装入前由 Stub 校验头与摘要；验证布局与内核集，选版并持久记录试启动，按 Ext4 路径读入所选 `.os`，交付 `BootInfo` |
| 固件应用（UEFI 侧） | `BOOTX64.EFI` | UEFI 引导管理器，`\EFI\BOOT\` | 经固件接口完成布局、Ext4、选版、签名与状态持久化，传递内存图、输出信息及 Boot Services 状态；绕过 IPL |
| 布局描述 | `BaleenLayout.bin` | BaleenCore / UEFI 读取，不执行 | 卷标识、系统卷位置、内核路径、引导状态区域及格式版本；字节表、写入位置与校验见[布局描述](布局描述.md) |

`BOOTX64.EFI` 的名字由 UEFI 可移动介质引导路径要求决定，不是本项目选的，见[后缀设计](../后缀设计.md)第六节；镜像放在固有其他路径时可以改用启动项指向的名字，但可移动介质回退路径必须是它。布局描述的字节表、写入位置与校验见[布局描述](布局描述.md)；内容按介质形态由组装器回填，内核路径对两种形态相同。

**当前 ABI**：MBR 恰好 512 字节、代码不超过 446 字节；CD IPL 恰好 2048 字节，代码及 Boot Info Table 保留区限于首 510 字节，两者签名均在偏移 510。IPL 留在物理 `0x7C00`，Stub 从 `0x7E00` 装入，文件上限分别为 512 B HDD `0x8200`、4Kn HDD / CD `0x8000`（正式组装器统一按最严的 `0x8000` 检查文件长度，同一份产物写进三种介质都可引导）；IPL 用 `CX` 传递实际逻辑扇区大小，须与 Stub 配套更新；BSS 与头的内存跨度由 `Tools/Bin/PackImage` 在打包时检查、由 Stub 在运行期自检复核。描述符独占介质上的一个扇区，其 LBA 按本地单位取 272 / 68 / 34（512 / 2048 / 4096 字节），不作为持久指针传给 Stub；描述符区的段序列里有 Stub 阶段的 `CoreDescriptor` 段，IPL 不读它。BaleenCore 映像从物理 `0x100000` 装入，带与 Stub 同构的完整性头与入口前缀（入口在文件偏移 `0x90`），头与摘要由 Stub 在交权前校验。完整字段、交权状态、重试和错误码见 [一级引导契约](一级引导契约.md)。`Version=1` 标识当前格式。

**验证范围**：完整系统仍需覆盖 BIOS 与 UEFI 各入口、内部硬盘、U 盘、移动硬盘、ISO 写入 U 盘与虚拟机挂载 ISO，以及卷定位、镜像校验与失败报告；掉电回滚演练见[内核集更新与回滚](../内核集更新与回滚.md)。IPL 的检查与后续功能验证分别记录；UEFI 路径绕过 IPL。

**构建与测试边界**：正常构建只依赖正式 C++ / ASM / Makefile / sh 源码与工具，不依赖不上传的 `Test`。校验可由 NASM 汇编期检查或正式 C++ 工具承担；回归工具按需手工执行，不作为默认构建的运行依赖。占位标记只证明相应入口被执行，不证明 Stub、BaleenCore、Ext4、选版或签名功能已实现。
