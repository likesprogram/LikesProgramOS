# Baleen 引导器

**Baleen 是 LikesProgramOS 的自家引导器子项目**，源码位于 `Packages/Baleen`，与系统本体 `LikesProgramOS` 平级。

它的职责只有一件事：**从不同硬件上找到指定 Ext4 文件系统的指定路径，把系统内核与 `Modules.list` 里属于引导闭包期望集的模块装载起来并完成交接。**

本文描述完整 Baleen 的目标职责与阶段划分。BIOS 一级引导的当前 ABI 单独定义在 [Baleen 一级引导契约](一级引导契约.md)，Stub 结构与自身完整性见 [Stub 约定与结构](../../../Packages/Baleen/Stub/README.md)，失败原因的稳定编号登记在[失败诊断编号](失败诊断编号.md)。

## 一、名字与命名口径

**Baleen 取自鲸须**：须鲸用鲸须从大量海水与浮游生物中筛出需要的食物，正如引导器要从多种固件、控制器、总线和介质中筛出唯一的目标卷，并从中取走指定的内核镜像与它所需的引导闭包。

**为什么不用 BootLoader 当名字**：那是这个组件的功能描述，不是名字。功能描述会在讨论、产物命名和诊断信息里反复出现——“BootLoader 加载失败”说不清是引导器的哪一段失败。项目内统一用 Baleen 指代这套引导链，产物名加 `Baleen` 前缀。

| 用在哪 | 怎么写 |
| --- | --- |
| 子项目、文档、讨论 | Baleen |
| 产物名 | `BaleenIPL.bin`、`BaleenStub.bin`、`BaleenCore.bin`、`BaleenLayout.bin`（见第八节） |
| 固件要求的固定名 | `BOOTX64.EFI` 等按协议保留，不套用本项目命名（见[后缀设计](../后缀设计.md)第六节） |

与其他生态重名时按[后缀设计](../后缀设计.md)第八节的口径处理：同名不构成关系，也不承诺互通。

## 二、职责边界

| Baleen 做 | Baleen 不做 |
| --- | --- |
| 在固件环境下枚举控制器、总线和设备，确定可引导介质 | 不加载列表里的非闭包条目（运行期模块），也不加载 `.drv`、`.exe`；这些是内核装载器的职责 |
| 识别介质形态与分区布局，定位候选系统卷 | 不做通用文件系统操作：Ext4 读取仅为定位内核镜像与引导闭包服务，见第五节 |
| 校验卷身份（标识、布局描述、版本） | 不解析 `.osm` 容器内部结构：预装只做最小读取面，不重定位、不执行、不初始化模块，见 6.2 |
| 在系统卷的指定路径读取内核镜像、清单、`Modules.list` 与列表里的引导闭包模块 | 不为第三方引导协议做适配，见[内核启动与固件边界](../内核启动与固件边界.md) |
| 按引导模式准备机器状态、装载镜像、交付 `BootInfo`（含已验签的清单副本、`Modules.list` 副本与预装模块记录） | 不建立运行时设备模型；设备模型属于引导闭包，由内核初始化 |
| 引导选择器职责：选版、持久记录试启动状态、失败回退；预装失败按选版回退处理，不交接“半套” | 不做运行期更新编排；那是 Updater 的职责 |
| 引导闭包预装只是读文件字节并搬运到内存 | 不写系统卷；对系统卷只有读取，见第五节 |

上表是整套 Baleen 的边界，具体按阶段划分如下。

| 阶段 | 负责内容 |
| --- | --- |
| BIOS IPL | 只做描述符区与 Stub 段的结构、起止扇区校验，装入 Stub，按 ABI 交权；任一失败诊断并停机 |
| BIOS Stub | A20、内存图、实模式磁盘会话、自身内存初始化，以及按 [Stub 说明](../../../Packages/Baleen/Stub/README.md)第二节的契约定位 BaleenCore、校验其镜像头与摘要、装载并交权 |
| BIOS BaleenCore | 入口、横幅与诊断、交权块与镜像事实核对、CPU 快照、运行期段表与中断表；`BaleenLayout.bin`、Ext4、系统卷定位、内核集选版与摘要 / 签名验证、持久状态和内核交接 |
| UEFI | UEFI 侧的布局、卷访问、内核集验证、选版与交接；该路径绕过 BIOS IPL 与实模式 Stub |

描述符区的 Stub 段仅定位 Stub 文件，与描述系统卷及内核路径的 `BaleenLayout.bin` 不是同一对象。IPL 不解析布局描述、Stub 头或文件系统，不检查 Stub 的 BSS、BuildId、摘要与签名。后续阶段缺失或占位件主动停机，不构成 IPL 缺陷；IPL 是否满足自己的边界仍须独立验证。

**引导器与内核各自持有文件系统代码，这不是“两套实现”。** [内核架构与自举闭包](../内核架构与自举闭包.md)禁止的是同一内核模块或驱动维护“引导简版 / 运行期完整版”，因为它们在同一个地址空间、同一套资源记录里工作。Baleen 独立运行在固件环境，与内核不共享地址空间，它的 Ext4 读取是为装载镜像与引导闭包服务的最小只读实现，内核的 Ext4 是含日志回放与写入的完整实现。两者不需要共享代码，但**可识别的卷格式范围必须一致**：镜像组装器为一套布局生成两边的访问路径，引导器读不了的卷，内核也不该被要求读出内容。

## 三、引导模式

引导模式分三层理解：**固件环境**决定 Baleen 以什么形态运行，**交权入口**决定内核以什么机器状态接手，**验证链**决定镜像要不要签名。本项目按支持梯队排序。BIOS 磁盘接口依据见 [一级引导契约](一级引导契约.md)第八节；coreboot payload 与 PVH 入口分别参见 [coreboot 官方文档](https://doc.coreboot.org/payloads.html)及 [Xen PVH 启动 ABI](https://xenbits.xen.org/docs/unstable/misc/pvh.html)。

### 3.1 固件环境

| 梯队 | 环境 | 说明 |
| --- | --- | --- |
| 必须支持 | **Legacy BIOS / CSM** | 16 位实模式起步，用 BIOS 磁盘与显示服务完成介质访问；光盘走 El Torito 引导目录 |
| 必须支持 | **UEFI x64** | 以 PE/COFF 固件应用形态运行，使用 Boot Services 的块设备与文件系统协议；包含无 CSM 的纯 UEFI 机器（通称 UEFI Class 3） |
| 明确不支持 | **UEFI IA32（32 位固件）** | 内核入口是长模式、UEFI 侧引导器是 x64 固件应用，32 位固件上没有可引导的载荷；ESP 里的 `\EFI\BOOT\BOOTIA32.EFI` 是一件**只打印不支持提示**的 IA32 应用（[UEFI 侧说明](../../../Packages/Baleen/Uefi/README.md)），让用户知道死在哪里，不承担引导 |
| 计划支持 | **coreboot** | 开源固件平台，以 SELF 机制装载 payload：SeaBIOS payload 提供 BIOS 环境，edk2 payload 提供 UEFI 环境，Baleen 以对应形态接入 |
| 计划支持 | **coreboot 发行版** | 在 coreboot 之上打包好 UEFI、SeaBIOS 或 LinuxBoot 环境的发行版（如 Dasharo）；Baleen 按其中实际提供的环境接入 |
| 计划支持 | **虚拟化直启（PVH）** | 由 Xen 引入，被 QEMU、Cloud Hypervisor、Firecracker 等采用的入口约定：内核以 ELF note 声明 32 位保护模式入口，不使用固件服务。见 3.2 |
| 记录在案 | **LinuxBoot** | 用 Linux 内核与 u-root initramfs 取代固件中大部分驱动与阶段，再由 kexec 载入目标内核；Baleen 的接入方式是作为其载入对象 |
| 记录在案 | **Slim Bootloader** | Intel 维护的开源固件，覆盖其多个客户端与嵌入式平台；是否作为接入目标待评估 |
| 记录在案 | **U-Boot** | 主要面向嵌入式平台，coreboot 也可把它当作 payload；本项目不将它列为 PC 首要目标 |
| 记录在案 | **网络引导（PXE / HTTP Boot）** | 两侧固件都提供网络引导基础：BIOS 侧经网卡 PXE Option ROM，UEFI 侧经固件 PXE 与 HTTP Boot；接入方式与时机列入后续扩展，不在首批交付 |

**这张表不承诺“固件名字相同就一定能启动”。** 同一固件在不同机器上开放的协议与服务可能不同，Baleen 按实际可用的接口探测，探测不到就报告，不猜测。

**两条路径都已实现并进入内核。** 两条路径的职责相同——识别介质、定位系统卷、装载内核、准备机器状态；按新设计还包含交权前预装引导闭包 `.osm`（M2 起落地，见 6.2）——差别只在固件环境与机器状态的准备方式，支持范围不因实现载体而缩减：

- **BIOS 路径**：IPL → Stub → BaleenCore → 内核交接整条链已完成，QEMU 四档（HDD / ISO / 两种 U 盘形态，U 盘档经 QEMU xHCI 根端口）与 Bochs 两档（ATA 硬盘 / ATAPI 光盘）都从受支持介质启动并成功进入内核；
- **UEFI 路径**：`BOOTX64.EFI` 是真实的 PE32+ 固件应用，以固件块设备协议实现与 BaleenCore 相同的职责——布局描述读取、卷访问、内核集验证与选版、内核装载与交接，与 BIOS 路径共用同一份布局描述与系统卷布局；QEMU + OVMF 的 HDD / ISO / U 盘 / 4Kn U 盘 / NVMe 4Kn 五档都已进入内核，交权前退出 Boot Services。

**32 位固件（UEFI IA32）没有可引导载荷**：ESP 里的 `BOOTIA32.EFI` 只打印 `E-UEFI-11` 说明不受支持，不承担引导；这条路径在启动矩阵里按“停在该编号、不进内核”覆盖。

### 3.2 交权入口

| 入口 | 进入内核时的状态 | 谁的机器状态准备 |
| --- | --- | --- |
| BIOS 路径 | IPL 从实模式起步并交给 Stub；Stub 负责 A20、内存图与 BaleenCore 装载，BaleenCore 完成面向内核的机器状态准备 | Baleen 自建；Stub → BaleenCore 的装载位置、格式、模式与交权按 [Stub 说明](../../../Packages/Baleen/Stub/README.md)第二节的契约执行 |
| UEFI 路径 | Baleen 作为固件应用运行，在交权前退出 Boot Services；内核在 `KernelMain` 第一步核对并确认固件启动服务已失效 | Baleen 准备，内核确认 |
| PVH 直启 | 内核以 ELF note（`XEN_ELFNOTE_PHYS32_ENTRY`）声明 32 位保护模式入口，进入时分页关闭，无固件服务可依赖 | Baleen 或虚拟机监视器按约定准备 |

**无论走哪条入口，内核看到的都是同一份 `BootInfo`。** 交权状态必须显式传递：UEFI 的 Boot Services 仍有效时，Baleen 在准备完成并取得有效内存图后调用 `ExitBootServices`；若已退出，不得重复调用，由 `BootInfo` 标记状态。BIOS 交权后不再调用 BIOS 服务。完整边界见[内核启动与固件边界](../内核启动与固件边界.md)。

### 3.3 验证链

| 机制 | 作用层级 | Baleen 的应对 |
| --- | --- | --- |
| **UEFI Secure Boot** | 固件验证引导程序镜像 | 提供可签名的 PE/COFF 形态；未签名或签名不受信任时固件不会执行它，这与本项目无关 |
| **Measured Boot（TPM）** | 固件与引导器把度量值记录进 PCR | 镜像与布局描述保持可度量、可复现：同一构建产出同样的字节 |
| **Intel Boot Guard / AMD 平台安全处理器** | 验证固件自身 | 在 Baleen 之下，不属于本项目可控范围 |
| **本项目签名与信任锚** | 验证内核集与构建清单 | 由引导选择器在装载前检查，见[内核集清单与签名](../内核集清单与签名.md) |

**可复现构建的落地**：`make reproducible-check` 在固定 `SOURCE_DATE_EPOCH`、同一工具链与同一组外部密钥输入（`.cache/Keys` 与 `.cache/AltKeys`，不进仓库）下连续做两次 `clean-all` + 全量构建，核对 51 份交付物的 sha256 一致；PE 头时间戳、ISO 与 Ext4 元数据、文件 mtime 都已归一化。开发密钥是外部构建输入，缺失时普通构建会生成一次随机密钥、但不可复现，因此该目标要求密钥预先存在。

Secure Boot 与项目自身的签名是两条独立的链：前者让固件愿意执行 Baleen，后者让 Baleen 愿意装载内核集。两者不能互相替代。

IPL 当前没有 Stub 头、摘要或签名检查，这是分工而不是缺口。Stub 与 BaleenCore 镜像的文件长度、内存长度、入口、Baleen BuildId 与摘要定义在 [Stub 约定与结构](../../../Packages/Baleen/Stub/README.md)，由 `PackImage` 在构建期打包并校验、由 Stub 在运行期自检自身、在交权前校验 BaleenCore（第二、三节）；无头的开发占位件由组装器显式放行。Stub 的自校验与它对 BaleenCore 摘要的校验都不能构成执行前认证或信任根；Baleen 构建身份也不能代替内核集 BuildId。

## 四、硬件与介质支持范围

| 介质 | 引导期访问方式 | Baleen 看到的卷 |
| --- | --- | --- |
| 内部硬盘（SATA / NVMe / 老 IDE） | 优先走固件的磁盘服务或块协议；固件覆盖不到该控制器时走 Baleen 的最小控制器路径 | 分区上的 Ext4 卷 |
| U 盘、移动硬盘、外置 SSD | **只用固件提供的 USB 引导能力** | 分区上的 Ext4 卷，或混合镜像上的 ISO9660 卷 |
| ISO 镜像（写入 U 盘 / 移动硬盘、虚拟机挂载、物理光驱） | 固件的光盘访问路径，或按 U 盘方式引导 | ISO9660 卷，系统卷为其内部文件 |

**BIOS 路径的介质支持范围**：硬盘与 USB-HDD 按逻辑扇区 512 或 4096 访问，光盘的无仿真路径固定 2048；设备访问只经固件 INT 13h，不需要 Baleen 自带 USB、AHCI 或 NVMe 驱动。软盘、USB-FDD 与 USB-ZIP 不在范围内。引导二进制与逻辑扇区单位无关（载荷按 4096 对齐，扇区大小在运行期询问固件），同一份产物可写进 512e 或 4Kn 介质；**MBR 与 GPT 共用同一套引导区**，分区表由部署侧按目标设备生成，见[启动介质与文件系统](../Common/启动介质与文件系统.md) 4.1 与 4.2。各类启动模式的访问链见[启动介质与文件系统](../Common/启动介质与文件系统.md) 1.1。

**引导期的介质访问优先走固件能力。** BIOS 把可引导设备作为驱动器号暴露，UEFI 通过块设备协议暴露；能走固件就走固件，这是 Baleen 保持小体积的前提。

**Baleen 自建访问路径只有一个适用场合**：固件的磁盘服务覆盖不到目标控制器（例如 UEFI 下固件没有为该 NVMe 或 AHCI 控制器提供块协议）。此时 Baleen 按自己的最小控制器访问路径读取目标卷，这条路径只服务引导，不建立内核那样的设备模型。

**UEFI 自建路径的当前范围**：经 `EFI_PCI_IO_PROTOCOL` 定位启动控制器，按 PCI 类码支持 AHCI（ATA 盘，512 字节逻辑块）与 NVMe（512 / 4096 字节逻辑块）的只读访问；控制器读逻辑与内核侧的 AHCI / NVMe 模块共用同一份源码，不重复实现命令编码。该路径只读：不写介质、不申报刷新原语，引导状态写入按只读介质降级（`E-UEFI-70` WARN），不做 `Pending` / `Trying` 转换。AHCI 的 ATAPI（光盘）读与 4Kn SATA 不在当前范围；**BIOS 路径仍只经固件 INT 13h，不建立自建控制器路径**。真实固件“不提供块协议”的现场与实机验证门见 [Baleen 验证报告](../../Test/Baleen-验证报告.md)。

**USB 不在此列。** 固件不提供 USB 引导支持的机器上，从 USB 介质启动不在支持范围；Baleen 不自带 USB 栈。内核的 USB 栈随引导闭包 `.osm` 预装，由内核入口初始化；引导器不使用它，也不能被引导器依赖。

**ISO 是分发形态，不是物理设备。** 写入 U 盘或移动硬盘的镜像要在同一份字节上同时满足光盘与磁盘两种引导记录要求；虚拟机选择 ISO 文件时按虚拟光驱引导。三种方式在内核侧是同一条路径，见[启动介质与文件系统](../Common/启动介质与文件系统.md)第二节。

## 五、卷定位与内核路径

**目标是一个卷加一条路径，不是一个固定块偏移。** 以下由 BaleenCore / UEFI 执行，IPL 只按描述符区里 Stub 段的起止扇区读取 Stub：

1. **拿到候选设备**：由固件枚举或自行探测得到可引导设备列表。
2. **读布局描述**：在约定位置找到 `BaleenLayout.bin`，取得卷标识、系统卷位置、内核路径、引导状态区域及格式版本；字节表、写入位置与校验见[布局描述](布局描述.md)，其中引导状态区域的形态（4096 对齐、最小长度、端点与布局描述块 / 描述符区 / 系统卷不重叠）在这一步就拒绝（`E-CORE-90` / `E-UEFI-90`），不等到读状态区域时才发现。布局描述不固定占用整盘 LBA1，不覆盖分区表或固件要求的区域。
3. **校验卷身份**：读 Ext4 superblock，核对卷标识与布局描述一致；不一致就换下一个候选设备，不猜测。
4. **按路径读内核**：逐级解析目录项与 inode，按 extent 读取内核镜像文件；缺省集路径由布局描述给定，装载路径必须取自验签通过的清单登记的 `.os` 条目（布局路径与之不一致即拒绝，见[内核集清单与签名](../内核集清单与签名.md)第三节）。
5. **校验后装载**：核对摘要与签名，按引导模式把镜像放到约定位置并准备机器状态。
6. **预装引导闭包**：装载路径确定后，解析验签通过的 `Modules.list`，把其中命中引导闭包期望集的 `.osm` 逐个读进内存并记录落点，见 6.2。列表里的非闭包条目跳过（由内核挂卷后装载）；模块路径取自清单登记的相对路径，不按固定文件名拼接；只做最小读取面校验（含主版本硬门），不解析容器内部、不重定位、不执行。

**Ext4 读取是最小只读实现**，边界明确：

| 项 | 约定 |
| --- | --- |
| 能力 | 识别 superblock 与特性标志、读块组描述符与 inode、走 extent 树、解析目录项、读常规文件 |
| 不支持 | 不支持的特性标志（未知 `INCOMPAT` 位、缺失 `FILETYPE` 与 `EXTENTS` 前提位）、未干净卸载的卷、加密、内联数据等；遇到就明确拒绝并报告 |
| 符号链接 | 布局描述给出的路径不得依赖符号链接；镜像组装器保证这一点 |
| 写入 | **绝不写系统卷**。Baleen 对系统卷只有读操作，写操作仅针对引导状态区的裸块记录 |
| 布局约束 | 镜像组装器保证系统卷布局落在支持范围内；不支持的布局在构建或装载时明确拒绝，不做兼容性猜测 |

**卷定位失败的处理**：线索不足时继续在受支持设备中查找并验证，无法唯一定位就报告失败，不能猜测磁盘。这条约束同样适用于内核：内核拿到 `BootInfo` 里的设备线索后自己再校验一次卷标识和布局信息。

## 六、装载与交接

Baleen 交付给内核的内容：

| 项 | 内容 |
| --- | --- |
| 机器状态 | 引导模式要求的寄存器、栈、页表与长模式状态；进入内核后不得依赖任何固件服务 |
| 内核镜像形态 | 镜像文件起点的[内核镜像数据](内核镜像数据.md)与它给出的入口点：数据声明长度、内存跨度、装载地址与要求的 `BootInfo` 版本，并带整幅镜像的摘要；装载前核对数据与摘要，签名与选版属引导选择器职责。内核镜像不带固件可直接识别的标准头，固件接触的是 Baleen 自己 |
| 引导闭包模块 | `Modules.list` 里命中引导闭包期望集的 `.osm` 文件字节：只按最小读取面搬运到内存并记录落点；不解析容器内部、不重定位、不执行，见 6.2 |
| `BootInfo` | 尺寸与版本、内存图、启动设备线索、系统卷标识、CPU/固件信息、可用输出通道、资源所有权，以及可选的内核集与试启动身份、已验签的清单副本、`Modules.list` 副本与预装模块记录（6.2） |
| 所有权信息 | 哪些内存与固件资源已由 Baleen 占用、哪些交给内核接管，避免内核把引导器的残留当成可用资源 |
| 失败报告通路 | 交权前后各自的错误输出方式，保证“引导器失败”和“内核失败”可区分 |

`BootInfo` 的字段定义、版本规则与生成工具由 HostSDK 提供（清单副本、列表副本与预装模块记录见 6.2）；内核侧要求 `Version` 等于 `InfoLayout::kVersion`、`Bytes` 达到 `InfoLayout::kBytes`，见[内核启动与固件边界](../内核启动与固件边界.md)。**第三方引导方式要用自己的实现构造同一份 `BootInfo`**：更短的结构会被直接拒绝，本项目不为它们提供适配层。

### 6.1 启动来源

内核与运行期更新都要知道“这次是从哪儿起来的”：更新要把新内核集写进**同一个卷**、发布到**同一条路径下的集根**、把 `Pending` / `Trying` / `Confirmed` 记录写回**同一处状态区域**。这些事实在引导期都是已知的，因此由 `BootInfo` 给全，**不让内核到设备里猜**——猜错就是写坏别的盘。

| 字段 | 语义 | 谁填 |
| --- | --- | --- |
| `LayoutOffset` | 布局描述在启动介质上的字节偏移；0 表示未提供 | BaleenCore / UEFI：取 `LayoutDescriptor::kOffset` |
| `VolumeOffset` / `VolumeBytes` | 系统卷在启动介质上的偏移与长度；两个都为 0 表示未提供，只给一个算不一致 | 两者：取自布局描述 |
| `StateOffset` / `StateBytes` | 引导状态区域在启动介质上的偏移与长度；两个都为 0 表示该介质没有状态区域（只读介质），只给一个算不一致 | 两者：取自布局描述；布局描述读取阶段已按第四节判据拒绝非法形态，生成器应把无状态区域写成成对的 0/0 |
| `MediumBytes` | 启动介质容量，字节；0 表示引导器不知道 | UEFI：块设备协议的容量；BIOS：交权块没有这个事实，填 0 |
| `VolumeUuid[16]` | 系统卷标识（Ext4 `s_uuid`），全零表示未提供 | 两者：取自布局描述 |
| `KernelPath` / `KernelPathBytes` | 缺省集内核镜像在卷内的路径（ASCII，不带结尾空字符）；必须指向缺省集目录里清单登记的 `.os` 条目 | 两者：取自布局描述；集根由它推出（`KernelSets/<BuildId>/`），装载路径则取自验签通过的清单 `.os` 条目（两者逐字节一致）。布局描述不会被更新推进改写，因此它同时是**出厂缺省集**这个最终兜底锚点的身份来源，见[内核集更新与回滚](../内核集更新与回滚.md) 6.1 |
| `DeviceKind` / `DevicePath` / `DevicePathBytes` | 启动设备线索：`UefiDevicePath` 时是 `EFI_DEVICE_PATH_PROTOCOL` 的字节（上限 `kDeviceClueMaxBytes`＝512，超出即按未提供交接），`BiosDrive` 时是 1 字节的驱动器号，`None` 表示未提供 | UEFI：分区句柄的设备路径；BIOS：IPL 交权时的 `DL` |
| `LoaderBegin` / `LoaderBytes` | 引导器自身占用的物理区间，内核不得当作可用内存 | UEFI：退出启动服务之前从 `LoadedImage` 协议取出并保存的本映像装载跨度（协议内存退出后不保证有效）；BIOS：自己的装载跨度 |

**定位规则：线索只用来缩小范围，身份必须由卷标识核对。** 内核按 `DeviceKind` 找到候选设备后，在 `LayoutOffset` 处读布局描述，核对 `VolumeUuid` 与卷内 Ext4 的 `s_uuid` 一致才认；不一致就换下一个候选，**无法唯一定位时报告失败**，与第五节对引导器的约束是同一条。`DeviceKind` 为 `None` 时（例如 UEFI 设备路径过长未能传递）只能靠卷标识在各设备里核对，同样不允许猜。

**内核按低 4GiB 的恒等映射读这些缓冲**：`BootInfo` 自身、内存图数组、内核路径字符串与设备线索都必须在 4GiB 以下；引导器把它们放在自己的映像里，因此映像被装到 4GiB 以上时内核读不到，会按 `WARN` 报告并按“未提供”处理（内存图读不到则在内核侧直接失败）。

**字段只追加、不移动。** 这些字段与[内核集清单与签名](../内核集清单与签名.md)第七节的 `KernelSetBuildId` / `AttemptId`、6.2 的清单/加载列表/预装模块字段一样，属接口首次发布前的设计调整：直接加进 `Version=1`，既有字段偏移不变；6.2 的字段占用原 `reserved1` 区，结构长度保持 `kBytes` 不变。内核核对 `Bytes` 与 `Version`：版本不符或尺寸短于 `kBytes` 直接拒绝并停机，**不为第三方引导协议提供适配层**；结构成立后，字段为 `0`（未提供）或引用的缓冲不可读只按 `WARN` 播报，不影响启动。清单副本、列表与预装模块记录只有一部分可用时，按 6.2 的失败规则处理，不按“未提供”降级。

**屏幕事实与 FATAL 等待配置由引导器采集**（字段在 `BootInfo` 的 `0x24` 与 `0x30..0x50`，定义见 `Packages/Common/Include/BootInfo.hpp`）：

- **BIOS 路径**按 BDA 的当前显示模式（`0040:0049`）与列数（`0040:004A`）给事实：模式 2 / 3 时 `screenKind=VgaText`、`screenAddress=0xB8000`；模式 7（MDA）时地址是 `0xB0000`；几何固定 80×25、步长 160、字节数 4000、格式 0。模式不是文本模式或列数不是 80 时给 `None`（引导期已按 `E-CORE-60` 报过 WARN）。
- **UEFI 路径**取 GOP 协议的当前 mode info：`Framebuffer` + 帧缓冲基址 + 像素宽高 + 像素步长（`PixelsPerScanLine × 4`）+ 可写字节数 + 像素格式（GOP 的 `BlueGreenRedReserved8BitPerColor` → `Bgrx8888`、`RedGreenBlueReserved8BitPerColor` → `Rgbx8888`；`PixelBitMask` / `PixelBltOnly` 给 `None`）。
- **地址必须在低 4GiB 的恒等映射内**，否则按“未提供”给 `None`——屏幕是诊断增强，不是启动前提，内核只走流式通道。
- `fatalWaitMs` 由 Baleen 构建配置给出：`0` 表示内核按默认 10 秒；**测试变体可写小值加速失败注入**，上限由内核按 10 分钟处理。等待与屏幕都不改变启动判定。

### 6.2 内核集、加载列表与引导闭包的交接

**Baleen 在交权前按 `Modules.list` 预装引导闭包。** 引导选择器验签通过所选集的清单后，按清单 `Type=3` 条目核对 `Modules.list` 的字节数与摘要（[内核集清单与签名](../内核集清单与签名.md) 2.3），再解析列表：固定头 `LPML 1`、`major`、`revision`，随后是 `module <相对路径>` 条目（语法、容量与集合口径见[模块修订与更新](../模块修订与更新.md)第四节，上限 16 KiB、30 条）。列表是内核侧书写的完整模块加载列表，条目与清单 `Type=2` 一一相等；Baleen 按「路径主名派生 `ModuleId` → 命中 `BootClosure.def` 期望集」挑出闭包成员预装，**非闭包条目（运行期模块）跳过、不报错**，闭包成员缺 / 重仍按列表非法拒绝。

- `major` 必须等于 `.os` 镜像数据里的 `ModuleMajor`，不等即按所选集失败处理（`E-CORE-95` / `E-UEFI-95`）；列表结构非法（语法、容量、重复条目、路径不匹配清单 `Type=2` 条目）为 `E-CORE-96` / `E-UEFI-96`。
- 解析后按内嵌的引导闭包期望集（由 `Packages/Common/Contract/BootClosure.def` 生成，与内核入口同一份来源）核对：应有成员齐全、无重复；不一致同样按 `E-CORE-96` / `E-UEFI-96` 处理，detail 区分缺 / 重。列表里的非闭包条目（运行期模块）不是错误；Baleen 不维护第二份成员表。
- 列表是**配置**，不是完整性根：它的字节数与摘要由清单 `Type=3` 条目覆盖，改列表必须重新生成并重签清单。

**预装分四步：规划、落点、逐模块核对与读入、填记录。**

1. **规划**：按条目数算出记录数组大小（`8 + count × 16` 字节，数组静态留 32 槽冗余，`count` 上限按 30 校验）与模块字节总长；列表副本单独缓冲（容量按第四节 16 KiB）。
2. **落点**：在内存图里为每个模块找一段 4 KiB 对齐、可用、低 4GiB 的连续区间，避开引导器自身装载跨度、内核装载跨度与低 1 MiB；任何模块找不到落点即 `E-CORE-97` / `E-UEFI-97`，不交接半套。UEFI 侧没有内存图搜索接口，落点由固件页分配给出：分配器按同一套约束从高往低重试——候选区间压住保留跨度就 `FreePages` 归还、把分配上界降到该跨度之下再要一次，直到落点合法或用尽轮数。
3. **逐模块核对与读入**：先按**最小读取面**核对文件头前 `0x14` 字节——`Magic`、`Version == 1`、`HeaderBytes == 0x80`、`Flags == 0`、`TotalBytes`（必须同时等于清单条目 `DataBytes` 与实际文件长度）；再定向读 `0x66` 两字节的 `ModuleVersionMajor` 与 `.os` 的 `ModuleMajor` 比较，跨主版本不搬运（`E-CORE-95` / `E-UEFI-95`）。只有这两步通过才整文件读入并复算 SHA-256，与清单 `Digest` 核对（不符 `E-CORE-68` / `E-UEFI-68`，读取失败 `E-CORE-67` / `E-UEFI-67`）。`0x18..0x66` 与 `0x68` 之后的字段**不读、不校验**；不解析段表与接口表、不重定位、不执行模块、不初始化模块、不写系统卷。容器格式见[内核模块容器](../内核模块容器.md)，主版本门与修订模型见[模块修订与更新](../模块修订与更新.md)。
4. **填记录**：每条记录写模块字节的物理地址（低 4GiB）、字节数、该模块在清单产物数组里的下标（`artifactIndex`，必须是 `Type=2` 条目）与保留位 0；记录数等于列表里命中引导闭包期望集的成员数（当前 13），不是列表条目总数。清单副本在验签时已按规则把签名值 64 字节归零，交出的是这份字节，内核不重验签名。

**可观测的预装摘要行**（G2/G5 断言用）：预装完成后输出一行 `boot closure preloaded: count=<n> bytes=<m> bad=0`，`count` 与记录数一致、`bytes` 是全部模块字节之和、`bad` 恒为 0（预装失败不落成半套，不走本行）。每模块的 `idx/base/len` 只在 `DEBUG` 等级输出，不影响断言。

**交权时 `BootInfo` 携带清单副本、`Modules.list` 副本与预装模块记录**。`BootInfo` 的版本保持 `1`、长度 `kBytes`（`0x100`）不变：字段占用原 `reserved1[4]` 区（偏移 `0xE0..0x100`），既有字段偏移不动。

| 偏移 | 字节 | 字段 | 语义 |
| --- | --- | --- | --- |
| `0xE0` | 8 | `kernelSetManifest` | Baleen 已验证的清单副本的物理地址（低 4GiB）；`0` = 未提供 |
| `0xE8` | 8 | `bootList` | Baleen 已验证的 `Modules.list` 副本的物理地址（低 4GiB）；`0` = 未提供 |
| `0xF0` | 8 | `bootModules` | 预装模块记录数组的物理地址（低 4GiB）；`0` = 未提供 |
| `0xF8` | 4 | `kernelSetManifestBytes` | 清单副本字节数；`0` = 未提供 |
| `0xFC` | 4 | `bootListBytes` | `Modules.list` 副本字节数；`0` = 未提供 |

预装模块记录数组以一个 8 字节头开始：`count`（u32）与保留（u32，必须 0）；随后是 `count` 条记录，每条 16 字节：

| 记录内偏移 | 字节 | 字段 | 语义 |
| --- | --- | --- | --- |
| `0x00` | 8 | `phys` | 模块文件字节的物理地址（低 4GiB） |
| `0x08` | 4 | `bytes` | 模块文件字节数 |
| `0x0C` | 2 | `artifactIndex` | 清单产物条目下标（必须是 `Type=2` 的 `.osm`） |
| `0x0E` | 2 | `reserved` | 必须为 `0` |

规则：

- **清单与列表副本都是验签/摘要通过的那一份字节**，不是从卷上另读的一份；记录必须指向 Baleen 实际装载的模块字节，不能是“清单里写了、实际没装”的位置。
- Baleen 不按固定文件名拼接模块路径：`Modules.list` 的条目与清单 `Type=2` 条目的相对路径一一对应；内核装载路径仍取自清单。
- 内核入口在任何模块执行前核对清单副本、列表副本与记录数组可读且不越界、记录与清单条目一一对应（类型、路径、长度、摘要）、`.os` 的 `BuildId` 等于清单 `BuildId`、`.os`/列表/每个模块的主版本硬相等；然后把这些物理区间在页帧分配器里标为已占用，再复制/接管到内核自有内存。容器解析、摘要核验、映射、重定位、导入解析、依赖检查与初始化都由内核完成。
- 清单/列表副本缺失、记录缺失、引导闭包成员缺 / 重、列表与清单 `Type=2` 集合不等、摘要不符、主版本不等、条目重复：属内核侧失败，按 `FATAL` + 屏幕报错 + 等待 + 重启处理（`E-KRN` 50–59 段，具体号已在 T3.6 定稿，见[内核诊断编号](../内核诊断编号.md)）。列表里的非闭包条目不是错误：它们是运行期模块。第三方引导器不按同一模型交接时落到同一条失败路径——本项目不支持第三方引导，不为它们提供适配层。
- 这组字段属于接口首次发布前的设计调整，直接加进 `Version=1`；字段与记录格式已定稿，M2 起 Baleen 两侧按此填写（`Packages/Common/Include/BootInfo.hpp` 的字段、清单、列表与预装记录），M3 起内核入口按同一份字节核对。

## 七、引导选择器与状态持久化

自动回滚模式下，由 BaleenCore / UEFI 承担引导选择器职责，IPL 与 Stub 不执行选版。完整的 Pending / Trying / Confirmed / Failed 语义见[内核集更新与回滚](../内核集更新与回滚.md)，引导期的动作是：

1. 读引导状态记录，结合冗余槽位选出代次最高且完整有效的一份。
2. 无待试候选时选择已知良好集；有 `Pending` 候选时校验其完整性与签名，把选中的候选身份写入并持久化 `Trying`，再装载。
3. 记录已为 `Trying` 时，判定上次未确认并递减剩余尝试次数：仍有剩余就再记一次尝试并载入候选，次数用尽才记录失败并改选原良好集。
4. 记录有写入痕迹但全部无法验证时不猜测目标集，进入受控恢复或停止；区域从未写过（空区域）与没有状态区域按“没有试启动记录”处理，直接启动布局描述指定的缺省集——空区域在可写介质上验证缺省集后会把事实落成 `Confirmed` 记录（缺省集作为已知良好集，已见最高安全版本与吊销并集一并持久化），下次启动按 `Confirmed` 走。状态区读失败或区域参数非法都不是空区域，分别以 `E-CORE-89` / `E-CORE-90` 停机，不按零事实启动；其中布局描述里的形态问题（对齐、长度、与布局描述块 / 描述符区 / 系统卷重叠）在读布局描述那一步就按 `E-CORE-90` / `E-UEFI-90` 拒绝，读状态区域时只再按设备逻辑块与区域长度判断。

**引导闭包预装失败走同一条选版回退，不交接“半套”。** 预装阶段读不到模块、长度与清单 `DataBytes` 不符或最小读取面校验不通过（6.2），都按所选集装载失败处理：候选集失败时按本节第 3 条的尝试次数递减与回退规则改选已知良好集；已知良好集（含缺省集）也失败时终止启动并报告，不启动内核。**只有内核镜像、清单副本、模块记录与模块字节全部就绪才交权**：任何一项缺失都不交出残缺的交接现场。

**运行期确认写入与引导期选择必须使用同一状态存储后端和记录格式**——记录格式与写入协议见[引导状态记录](引导状态记录.md)。只有该后端能在内核交权前可靠写入并持久化时，才启用试启动；否则直接启动指定的已确认镜像。

选版与验证用的集清单、签名与信任锚见[内核集清单与签名](../内核集清单与签名.md)：集按 `KernelSets/<BuildId>/` 并存，签名由引导器内嵌的公钥表验证，密钥轮换与撤销随引导器更新分发。

## 八、产物与验证

| 组件 | 输出名称 | 被谁载入 | 用途 |
| --- | --- | --- | --- |
| 一级引导 | `BaleenIPL.bin` / `BaleenIPLCd.bin` | BIOS / El Torito 引导目录 | 校验描述符区与 Stub 段结构、起止扇区，装入 Stub 并按 ABI 交权；失败停机 |
| 实模式服务层 | `BaleenStub.bin` | 一级引导 | 自身完整性头与 SHA-256 摘要自检；A20、内存图、固件磁盘会话；按描述符区的 BaleenCore 段定位 BaleenCore、校验其镜像头与摘要、校验装载区、装入高位并交权 |
| 核心阶段（BIOS 侧） | `BaleenCore.bin` | 实模式服务层 | 镜像带与 Stub 同构的完整性头与入口前缀，装入前由 Stub 校验头与摘要；验证布局与内核集，选版并持久记录试启动，按 Ext4 路径读入所选 `.os` 与清单标志置位的引导闭包 `.osm`，交付 `BootInfo`（清单副本与预装模块记录自 M2 起随 `BootInfo` 交付，见 6.2） |
| 固件应用（UEFI 侧） | `BOOTX64.EFI` | UEFI 引导管理器，`\EFI\BOOT\` | 经固件接口完成布局、Ext4、选版、签名与状态持久化，装载内核镜像与 `Modules.list` 里的引导闭包 `.osm`（自 M2 起落地），传递内存图、输出信息及 Boot Services 状态；绕过 IPL |
| 32 位固件提示件 | `BOOTIA32.EFI` | 32 位 UEFI 引导管理器，`\EFI\BOOT\` | 32 位固件上没有可引导载荷：只打印 `E-UEFI-11` 说明原因并停机，不承担引导 |
| 布局描述 | `BaleenLayout.bin` | BaleenCore / UEFI 读取，不执行 | 卷标识、系统卷位置、内核路径、引导状态区域及格式版本；字节表、写入位置与校验见[布局描述](布局描述.md) |

`BOOTX64.EFI` 的名字由 UEFI 可移动介质引导路径要求决定，不是本项目选的，见[后缀设计](../后缀设计.md)第六节；镜像放在固有其他路径时可以改用启动项指向的名字，但可移动介质回退路径必须是它。布局描述的字节表、写入位置与校验见[布局描述](布局描述.md)；内容按介质形态由组装器回填，内核路径对两种形态相同。

**当前 ABI**：MBR 恰好 512 字节、代码不超过 446 字节；CD IPL 恰好 2048 字节，代码及 Boot Info Table 保留区限于首 510 字节，两者签名均在偏移 510。IPL 留在物理 `0x7C00`，Stub 从 `0x7E00` 装入，文件上限分别为 512 B HDD `0x8200`、4Kn HDD / CD `0x8000`（正式组装器统一按最严的 `0x8000` 检查文件长度，同一份产物写进三种介质都可引导）；IPL 用 `CX` 传递实际逻辑扇区大小，须与 Stub 配套更新；BSS 与头的内存跨度由 `Tools/Bin/PackImage` 在打包时检查、由 Stub 在运行期自检复核。描述符独占介质上的一个扇区，其 LBA 按本地单位取 272 / 68 / 34（512 / 2048 / 4096 字节），不作为持久指针传给 Stub；描述符区的段序列里有 Stub 阶段的 `CoreDescriptor` 段，IPL 不读它。BaleenCore 映像从物理 `0x100000` 装入，带与 Stub 同构的完整性头与入口前缀（入口在文件偏移 `0x90`），头与摘要由 Stub 在交权前校验。完整字段、交权状态、重试和错误码见 [一级引导契约](一级引导契约.md)。`Version=1` 标识当前格式。

**验证范围**：完整系统仍需覆盖 BIOS 与 UEFI 各入口、内部硬盘、U 盘、移动硬盘、ISO 写入 U 盘与虚拟机挂载 ISO，以及卷定位、镜像校验与失败报告；掉电回滚演练见[内核集更新与回滚](../内核集更新与回滚.md)。IPL 的检查与后续功能验证分别记录；UEFI 路径绕过 IPL。

**构建与测试边界**：正常构建只依赖正式 C++ / ASM / Makefile / sh 源码与工具，不依赖不上传的 `Test`。校验可由 NASM 汇编期检查或正式 C++ 工具承担；回归工具按需手工执行，不作为默认构建的运行依赖。占位标记只证明相应入口被执行，不证明 Stub、BaleenCore、Ext4、选版或签名功能已实现。
