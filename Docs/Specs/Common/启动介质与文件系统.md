# 启动介质与文件系统

本文定义系统需要支持哪些启动介质、每种介质经由哪条控制器与访问链，以及必备文件系统和相关取舍。

介质怎样被引导器找到并装载，见 [Baleen 引导器](../Baleen/README.md)；内核侧的控制器与文件系统实现见[内核模块与驱动清单](../内核模块与驱动清单.md)；引导器与内核共用的块设备、偏移视图与统一路径接口，以及内核侧 VFS / 块设备层的 ops 语义、系统卷核对与挂载规则见[文件系统抽象与 VFS](文件系统抽象与VFS.md)。本文定介质与访问链、必备文件系统与读写阶段策略；接口层不在本文重复。

## 一、启动介质与访问链

系统需要在没有内置硬盘时从 U 盘、移动硬盘、外置 SSD 或光盘启动，USB 3.x 存储设备也属于必备支持范围。统一设备模型根据启动线索优先扫描相关磁盘、USB 控制器和设备；线索只缩小范围，身份由卷标识核对。访问系统卷所需的驱动与文件系统在引导闭包 `.osm` 内（交权前由 Baleen 预装、内核入口校验后初始化），不等待外部 `.drv`，内核核心也不内置简版实现。

| 启动介质 | 控制器与访问链 | 默认系统卷路径 |
| --- | --- | --- |
| 内置 SATA 盘 | 内置 AHCI | Ext4 |
| 内置 NVMe 盘 | 内置 NVMe（4Kn 与 512e，逻辑块大小取控制器 `Identify` 上报） | Ext4 |
| 老 IDE 盘 | 内置 ATA PIO | Ext4 |
| U 盘（USB 2.0/3.x） | 内置 xHCI 根端口、USB 核心、BOT/SCSI 存储（M6 落地；hub 下游设备枚举与 UAS 属阶段 3 以后） | Ext4 |
| USB 移动硬盘 / 外置 SSD | 同上；包含通过 USB-SATA、USB-NVMe 桥接的存储设备 | Ext4 |
| SATA 光驱 | 内置 AHCI ATAPI | ISO9660 → Ext4 镜像 |
| 老 IDE 光驱 | 内置 ATA PIO ATAPI | ISO9660 → Ext4 镜像 |
| USB 光驱 | 内置 xHCI 根端口、USB 核心、BOT/SCSI 光驱命令 | ISO9660 → Ext4 镜像 |

### 1.1 引导期的启动模式与访问链

上表是内核侧的介质访问目标。**引导期由 Baleen 承担介质定位与内核装载**，它按介质与装配方式覆盖的启动模式如下：BIOS 路径按固件提供的 INT 13h 访问设备（不自行实现 USB、AHCI 或 NVMe 驱动），UEFI 路径按固件应用与块设备协议访问。

**两种固件环境都已实现完整的引导链**：BIOS 路径（IPL → Stub → BaleenCore → 内核交接）与 UEFI 路径（`BOOTX64.EFI` 作为 PE32+ 固件应用，经固件块设备协议完成同样的介质识别、选版、验签与交接，交权前退出 Boot Services）都已从受支持介质启动进入内核。UEFI 侧的机器状态准备由引导器完成、内核入口只核对；32 位固件上的 `BOOTIA32.EFI` 只打印 `E-UEFI-11` 说明不受支持、不承担引导，见 [Baleen 引导器](../Baleen/README.md) 3.1。

| 启动模式 | 装配方式 | 载体与接口 |
| --- | --- | --- |
| 硬盘（512e / 4Kn） | 安装工具装配 | 固件映射为硬盘的 SATA / IDE / SCSI 扩展卡 / NVMe 等；BIOS 路径经固件 INT 13h，UEFI 路径经固件块设备协议 |
| U 盘、移动硬盘、外置 SSD（512e） | 从 ISO 刻录 / 安装工具装配 | 固件 USB 引导能力（USB 1.1 / 2.0 / 3.x 控制器） |
| U 盘、移动硬盘（4Kn 透传） | 从 ISO 刻录 / 安装工具装配 | 同上；部分固件的 USB 存储层只接受 512 字节块设备（如 SeaBIOS），此时设备不可见。介质布局与内置硬盘一致，固件能识别即可引导；UEFI 块设备协议按设备报告的逻辑块大小工作，不受该限制 |
| 光盘（El Torito 无仿真） | 从 ISO 刻录（含虚拟机挂载） | SATA / IDE ATAPI 光驱、虚拟机挂载 ISO；经引导目录与 EFI 项引导 |
| 软盘、USB-FDD、USB-ZIP | — | 传统软驱与仿真；不在支持范围 |
| 网络引导（PXE / HTTP Boot） | 从网络 | 网卡与固件网络栈：BIOS 侧为 PXE Option ROM，UEFI 侧为 PXE 与 HTTP Boot；列入后续扩展 |

**两种装配方式的差别在介质内容，不在引导二进制**——两者用的是同一份 IPL、Stub 与 BaleenCore：

| 装配方式 | 介质内容 | 系统卷形态 | 承担者 |
| --- | --- | --- | --- |
| 从 ISO 刻录 | 混合镜像：MBR 引导记录 + ISO9660 卷 | ISO9660 卷内的 Ext4 镜像文件 | `MakeImage`（通用镜像制作器）产出混合镜像，由用户或写盘工具写入介质 |
| 安装工具装配 | 磁盘布局：MBR 分区表 + 引导载荷 + ESP + 系统卷分区 | 分区上的 Ext4 卷，与内置硬盘一致 | `TestInstaller`（测试安装器）产出整盘镜像直写，代替尚未实现的 ISO 内交互式安装器（可选内置硬盘、U 盘或移动硬盘为目标） |

**USB 存储的 4Kn 限制来自固件，与装配方式、介质布局无关**：安装器装配后的 U 盘、移动硬盘与内置硬盘内容一致，接入方式（USB 桥是否透传 4Kn）与固件的 USB 存储实现决定它能否被枚举。BIOS 侧部分固件只接受 512 字节块设备；UEFI 侧按块设备协议处理设备报告的逻辑块大小，不受此限制。

**引导二进制与逻辑扇区单位解耦**：BIOS 路径按介质起始的固定偏移读描述符与载荷、运行期向固件询问扇区大小，载荷按 4096 对齐，因此同一份二进制在 512e 与 4Kn 上都能引导。**分区表属于部署阶段**（写入方按目标设备生成），引导二进制不解析它，见 4.1 与 4.2。

## 二、ISO 镜像形态与三种投递方式

**ISO 是分发形态，不是一种物理设备。** 项目的引导介质是“系统引导文件”，它可以被投递到三种载体上，而内核对这三种载体的访问链完全一致：

| 投递方式 | 载体呈现 | 引导侧 | 内核侧看到的卷 |
| --- | --- | --- | --- |
| 写入 U 盘或移动硬盘 | 混合镜像（hybrid ISO）：介质同时带光盘布局与可引导分区记录 | 固件按 U 盘方式引导 | ISO9660 卷 |
| 虚拟机选择 ISO 文件 | 虚拟光驱（QEMU `-cdrom` 等） | 虚拟机固件按光驱引导 | ISO9660 卷 |
| 物理或外置光驱 | 光盘 | 固件按 El Torito 引导 | ISO9660 卷 |

因为写入 U 盘后的介质呈现的仍是 ISO9660 卷，**内核不需要区分“这来自光驱还是来自 U 盘”**：三种方式都归到同一条 `ISO9660 → 卷内 Ext4 镜像` 路径。刻录或写入时由镜像组装器保证同一份镜像同时满足光盘与 U 盘两种引导记录要求，写法与限制见 [Baleen 引导器](../Baleen/README.md)。

**光盘上的系统卷是卷内文件，不是整盘系统卷。** 将 Ext4 系统卷镜像作为 ISO9660 文件保存，**ISO 内文件名固定为 `/SystemVolume.img`**（构建器的 `SYSTEM_VOLUME_ISO_NAME` 默认值，见 `MakeImage` 的 `--iso-name`），与磁盘版本共用卷内布局（卷内目录树见[系统卷布局](系统卷布局.md)）；内核通过块设备偏移视图访问它。采用单区段实现时，镜像组装器必须保证文件连续，装载时验证，不支持的布局明确拒绝。

**单区段连续性与身份核对是两件事。** 位置与连续由镜像组装器按布局描述写入（`VolumeOffset` / `VolumeBytes`，见 [Baleen 布局描述](../Baleen/布局描述.md)），读取方在挂载前核对区段边界、起点按介质逻辑块大小对齐以及卷标识一致，不解析 ISO9660 目录树也能切出系统卷偏移视图。**ISO9660 模块（M6 已落地只读实现）能按名字定位 `/SystemVolume.img` 并读出其内容**，可作为同一区段的第二来源比对；ISO9660 卷上的名字按大小写折叠并去掉 `;N` 版本后缀，所以 `SYSTEMVO.IMG;1` 与 `/SystemVolume.img` 是同一路径。**第二来源在 M6 已接线**：主路径仍是 `volumeOffset` 偏移视图，光盘档在挂载与读清单之后由内核核心从 ISO9660 主卷描述符 / 根目录独立推出 `/SystemVolume.img` 的区段并与 `BootInfo.volumeOffset` / `volumeBytes` 比对（稳定行与 `E-KRN-77` / `E-KRN-78` 见 3.1），它不改变“ISO9660 不成为系统卷挂载格式”的结论。区段起点必须按介质逻辑块对齐（光盘 2048 字节；写入 4Kn 介质时须 4096 对齐，组装器做不到即不支持该组合，明确拒绝、不向下取整）。

## 三、必备文件系统

**USB 存储、Ext4、ISO9660、FAT32 是本项目的必备能力，由引导闭包 `.osm` 提供：** 交权前由 Baleen 预装、内核入口校验后初始化，因此退出固件启动服务后、挂载系统卷之前即可使用。M6 的落地范围：

- **USB 存储**：xHCI 主控（ABAR、命令/事件环、EP0 控制与批量传输）+ USB 核心（控制器/类/设备表、根端口枚举状态机）+ 设备类驱动，存储侧为 **BOT/SCSI**，支持 512e 与 4Kn 设备；**hub 类驱动已落地但只做 hub 描述符与端口电源/连接变化，下游设备枚举没有实现**；**UAS 未实现**（只有 BOT）。这两项是已知边界，归阶段 3 以后。
- **NVMe**：ABAR 映射、Admin/IO 队列、`Identify`、READ（PRP1 + 内核缓冲），按 `Identify` 上报的 4096 / 512 字节逻辑块工作（4Kn 与 512e）。
- **ISO9660**：只读，主目录与 Rock Ridge，不要求 Joliet。
- **FAT32**：只读，可读已识别的 FAT32 引导、安装与恢复介质。

三个文件系统通过统一 VFS 和块设备层访问设备。模块归属见[内核架构与自举闭包](../内核架构与自举闭包.md) 2.2。

**M6 仍只有读路径。** Ext4 只读解析、ISO9660 与 FAT32File 只读实现、系统卷挂载与卷标识核对、NVMe/USB 真实驱动、运行期 `.osm` 装载与同集两修订选择/回退都在本阶段交付；写入、日志回放、中断异步与 `Activate` 属阶段 3 以后。Ext4 的特性接受集合拆成两个常量、在同一份头文件里单点定义（`Packages/Common/Include/Storage/Ext4Features.hpp`）：`kBaleenAccepted` 是只读最小实现接受的集合，`kKernelAccepted` 是内核完整实现的最终超集（`kKernelAccepted = kBaleenAccepted | RECOVER`，其余回放 / 写入位按阶段 3 增补），`kBaleenAccepted ⊆ kKernelAccepted` 由编译期断言固定；**本阶段两侧只读都按 `kBaleenAccepted` 判定**（判定函数默认参数就是它），`kKernelAccepted` 只在阶段 3 的写 / 回放路径显式传入。**位被认识不等于本阶段可挂载**：本阶段只读、不回放日志，置 `RECOVER` 或未干净卸载的卷在 `Mount` 的卷状态核对阶段仍被拒绝。卷标识（Ext4 `s_uuid`）由文件系统模块提供、核对责任在 Vfs 的 `Boot.Volume`，块设备层只透传候选设备、不解析卷格式；接口与判定规则见[文件系统抽象与 VFS](文件系统抽象与VFS.md) 3.6、4.3 与 4.5。

FAT32 支持同样属于引导闭包，M6 已交付只读解析（BPB、FAT 链、LFN 与 8.3 目录项），可读取已识别的 FAT32 引导、安装和恢复介质；内核在 M6 **不自动挂载任何 FAT32 卷**（系统卷仍是 Ext4），FAT32 与 ISO9660 的挂载消费方、交换卷读写随阶段 3 以后与 M7 的模块接入确定。默认系统卷仍是 Ext4；FAT32 的必备支持不把所有文件系统都变成系统卷，也不要求每次启动挂载每一个卷。ISO9660 只要求主目录与 Rock Ridge，不要求 Joliet；镜像组装器保证所需路径能被这套实现识别。

### 3.1 M6 系统卷链路与可观测标记

**M6 的内核侧链路**（主线验证五档：BIOS HDD / BIOS ISO / UEFI HDD / UEFI ISO / UEFI NVMe 4Kn）：

1. 引导器（阶段 0）：预装 13 个引导闭包 `.osm` 并交出 `BootInfo`；串口出现 `boot closure preloaded: count=13 bytes=<m> bad=0`（Baleen 侧标记）。选择器同时播报本次选定的集与修订：`Set=<64 位小写十六进制> Attempt=<n> Rev=<0x + 16 位十六进制>`。
2. 内核核心：校验交接包，按依赖拓扑装载并 `Init` 闭包模块（DevModel → DriverLoader → 启动驱动 → Vfs → Ext4 / ISO9660 / FAT32File）；每个模块 `Init` 成功打印一条 `module init ok: <逻辑名>`（共 13 条）。
3. 驱动在自己的 `Init` 里构造 `DriverDesc`（`BlockDeviceOps` + context）经 `Drv.Loader.RegisterDriver` / `Bind` 登记进 `Dev.Model`；内核在模块 `Init` 之间编排 `Drv.Loader.Start`。**Vfs `Init` 从 `Dev.Model` 取绑定事实，作为唯一的 `Block.Registry.Publish` 调用者把块设备登记进注册表**（驱动不导入 `Block.Registry`、不依赖 Vfs）；Ext4 / ISO9660 / FAT32File 各在自己的 `Init` 里向 `Fs.Vfs` 登记 `FileSystemOps`。
4. 闭包全部 `Init` 之后，内核核心调用 `Boot.Volume.MountSystemVolume`：候选为全部已登记**根设备** → 按 `BootInfo.volumeOffset` / `volumeBytes` 开偏移视图 → 只读挂载 Ext4 → `VolumeIdentity` 与 `BootInfo.volumeUuid` 核对 → 唯一匹配才把系统卷挂到 `/`。
5. 挂载成功后由 `Boot.Volume` 打印 `[ OK ] system volume mounted: uuid=<32 位小写十六进制>`；读清单成功打印 `[ OK ] system manifest read: bytes=<n> digest=<16 位小写十六进制>`，`digest` 取前 32 字节 SHA-256 的前 8 字节；路径推导 / 打开 / 读取 / 摘要核对失败分别按 `E-KRN-73`–`76` 处理。
6. **ISO9660 第二来源核对（M6 新增，仅光盘介质档）**：内核核心从 ISO9660 主卷描述符（逻辑扇区 16 的 `CD001`）与根目录项独立推出 `/SystemVolume.img` 的区段（目录项 extent LBA × 2048 字节），与 `BootInfo.volumeOffset` / `volumeBytes` 比对；一致打印 `[ OK ] iso9660: system volume file=SystemVolume.img bytes=<n> offset=<0x…>`，不一致按 `E-KRN-77` 走 FATAL；读不到 ISO 卷、根目录损坏或没有该文件只 `WARN E-KRN-78`，不改变已完成的挂载判定。
7. **运行期模块（M6 新增，M8 改识别口径）**：`Modules.list` 里不属于引导闭包期望集的条目在挂卷、读过清单之后逐条只读装载；每个成功打印 `runtime module init ok: <逻辑名>`，全部处理完打印 `[ OK ] runtime modules: loaded=<n> failed=<n> optional=<n>`。正式发布集没有运行期条目，三个数都是 0；必需失败 `E-KRN-80`–`82` 走 FATAL + 等待 + 重启，可选失败只 `WARN E-KRN-83` 并继续。识别口径与失败语义见[模块修订与更新](../模块修订与更新.md) 第五节。
8. 至此 M6 的可运行链条成立：闭包真实驱动 → 系统卷挂载 → 清单核对 → ISO9660 第二来源（光盘档）→ 运行期模块装载；块设备与文件系统仍只有读路径。

**标记行的断言口径**：

| 标记 | 出现时机 | 断言用途 |
| --- | --- | --- |
| `boot closure preloaded: count=13 bytes=<m> bad=0` | 引导器交权前 | 预装齐全、无坏模块 |
| `Set=… Attempt=… Rev=…` | 引导器选版与回退改选后各一次 | 修订选择：正式镜像 `Rev=1`；两修订夹具按 2 / 1 / 回退到 1 断言 |
| `module init ok: <逻辑名>`（13 条） | 内核装载闭包后 | 闭包全部 `Init` 成功，顺序与 `BootClosure.def` 一致 |
| `system volume mounted: uuid=…` | 系统卷挂载成功（`Boot.Volume` 的 OK 行） | 卷标识核对通过、系统卷挂在 `/`；当前不含 `bytes=` 字段 |
| `system manifest read: bytes=… digest=…` | 读清单文件成功（内核核心打印） | 经 VFS 真的从系统卷读到了内核集文件；`digest` 为 SHA-256 前 8 字节的 16 个十六进制字符 |
| `iso9660: system volume file=SystemVolume.img bytes=… offset=…` | 光盘档第二来源核对一致（内核核心打印） | ISO 源列；目录项区段与 `BootInfo` 一致；不一致 `E-KRN-77` 停机、不可用只 `WARN E-KRN-78` |
| `runtime module init ok: <逻辑名>` | 运行期模块装载成功（装载器打印） | 运行期 `.osm` 真的装载并 `Init`；闭包列只数 `module init ok:`，两者不混淆 |
| `runtime modules: loaded=<n> failed=<n> optional=<n>` | 运行期条目处理完（内核核心打印） | 运行期列取 `loaded`：正式镜像为 0，可选成功夹具为 1 |

以上标记都以 `[ OK ]` 等级前缀输出（由 Print 的等级标签加），断言按行内子串匹配；任一环节失败时不打印对应行。

**驱动自报标记**（只作诊断，不进矩阵列判定）：NVMe 打印 `[ NVME ] nvme: probing controller` / `nvme: controller ready`，设备行 `nvme: <型号> sectors=0x<块数> block=0x<逻辑块>`；xHCI 打印 `[ XHCI ] xhci: probing controller` / `xhci: controller running` / `xhci: controller added handle=0x<句柄> ports=0x<端口数> slots=0x<槽数>`；USB 核心打印 `[ USB ] usbcore: ready` / `usbcore: controller added` / `usbcore: controller ports=<n>` / `usbcore: device enumerated` / `usbcore: class registered`；hub 打印 `usbhub: hub bound ports=<n> connected=<n>`；存储打印 `usbstorage: device bound block=0x<逻辑块> sectors=<块数>`。失败侧为普通诊断行：`[ WARN ] nvme: no device`、`[ WARN ] xhci: no device`、`[ WARN ] usbhub: no hub device`、`[ WARN ] usbstorage: no device`，以及表满、描述符读取失败等；这些都不带 `E-KRN` 编号，不改变内核失败判定。

**文件系统模块的日志口径**：ISO9660 / FAT32File **不打印以 `iso9660:` / `fat32:` 开头的成功行**——成功只体现为装载器统一打印的 `module init ok: <逻辑名>`；失败时只打印不带编号的普通日志（如 `[ ISO9660 ] the Fs.Vfs import isn't bound`、`[ ISO9660 ] registering the iso9660 file system failed`，FAT32File 同形且标签为 `[ FAT32File ]`）。这些日志不是矩阵判据：`CheckAll.sh` 的启动矩阵列按 `system volume mounted:`、`system manifest read:`、`runtime modules: loaded=` 等内核核心标记判定，模块日志只进现场记录。

**矩阵列口径**（`CheckAll.sh --with-boot` 启动矩阵）：M6 的列为「进内核 / 刷新路径 / 诊断编号 / 预装 / 闭包Init / 挂卷 / 清单 / ISO源 / 运行期」。硬判定七档（BIOS HDD / BIOS ISO / BIOS USB 两档、UEFI HDD / UEFI ISO / UEFI NVMe 4Kn）要求：预装 = 13、闭包 Init = 13、挂卷与清单行都在、运行期 = 0、**光盘直挂两档（BIOS ISO、UEFI ISO）还要求 `iso9660: system volume file=` 标记**、内核侧无 `E-KRN-*` 与 `[ FATAL ]`；UEFI 各档另要求“清单已验证 / 已退出启动服务 / 内核已放到装载地址”三条固件阶段标记。矩阵的 USB 档用 QEMU 的 xHCI 控制器、根端口直连 `usb-storage`：BIOS 两档已按上面的列硬判，**同时验证内核 xHCI / UsbStorage 链**；UEFI USB / 4Kn U 盘两档当前只显示不判定（收紧归 M7 收尾 / 后续）。内核 USB 驱动的细项仍由宿主检查兜底（见 3.2）。

**失败口径**：无块设备候选 / 卷标识不符 / 位置不对齐 / 挂载失败时，`MountSystemVolume` 返回 `NotFound` 或其他 `Storage::Error`，内核核心按 `E-KRN-70`–`76` 报 `[ FATAL ]` + 屏幕 + 等待（默认 10s）+ 复位（70 接口不可用 / 71 挂载失败 / 72 身份不符 / 73 清单路径不可用 / 74 打开失败 / 75 读取失败 / 76 摘要不符，具体文本以[内核诊断编号](../内核诊断编号.md)与 `Diagnostics.hpp` 登记为准）。`.osm` 模块不写带编号的 `E-KRN` 行、不自行等待或复位；失败 detail 由内核核心按返回码与阶段拼（模块侧如需补充说明，只允许不带编号的普通日志行，例如 `no system volume candidate`、`multiple system volume candidates: <n>`）。运行期模块的 `E-KRN-80`–`83` 在挂卷与读清单之后打印，detail 带集内路径与机制层原因。光盘档的第二来源不一致按 `E-KRN-77` 报 `FATAL`（detail 给 ISO 侧与 `BootInfo` 侧的偏移/长度），ISO 卷不可用或根目录无该文件按 `WARN E-KRN-78` 继续，不改变已完成的挂载判定。不降级、不挂死。

### 3.2 M6 介质与驱动落地边界

M6 的引导闭包内，介质驱动与文件系统模块都是真实实现（13 个闭包成员全部落地，不再有“`Init` 成功但不登记块设备”的玩具模块）：

| 模块 | 落地能力 | 已知边界 |
| --- | --- | --- |
| AtaPio | PIO、`IDENTIFY`、ATAPI（光盘）读 | 轮询完成，无中断 |
| Ahci | ABAR 映射、命令列表 + PRDT、`IDENTIFY`、`READ DMA EXT`、端口复位与有界超时 | 轮询完成，无中断 |
| Nvme | ABAR 映射、Admin/IO 队列、`Identify`（Controller + Namespace NSID=1）、4Kn/512e 逻辑块、READ（PRP1 + 内核缓冲） | 只读（写返回 `ReadOnly`）；轮询完成，无中断；只处理 NSID 1 |
| Xhci | ABAR、命令/事件环、EP0 控制与批量传输、根端口设备枚举 | 轮询完成，无中断；不枚举 hub 下游设备 |
| UsbCore | 控制器 / 类 / 设备三张表（2 / 4 / 16）、枚举状态机、类匹配按接口 class 字节 | 只覆盖主控根端口；无中断 / 异步；设备表满会拒绝新设备 |
| UsbHub | hub 类描述符、端口电源与连接变化 | **不做下游设备枚举**（`Usb.Host:1` 只服务根端口），阶段 3 以后补齐 |
| UsbStorage | BOT/SCSI 存储：INQUIRY、READ CAPACITY(10)、READ(10) 分包读，支持 512 与 4096 字节块 | 只读（`capabilities=0`）；**UAS 未实现**，阶段 3 以后 |
| ISO9660 | 只读 PVD / Rock Ridge、目录遍历、按名字查文件（含 `;N` 折叠） | 固定 2048 字节逻辑块；拒绝 Joliet、多区段、SL 符号链接跟随、关联属性与 EA 记录 |
| FAT32File | 只读 BPB、FAT 链、LFN / 8.3 目录项遍历 | 仅 FAT32（拒绝 FAT12/16、簇大小 > 4 KiB 等），拒绝损坏的簇链 |

- **4Kn / 512e**：块设备契约携带设备报告的逻辑块大小，NVMe 按 `Identify` 上报（512 或 4096）、USB 存储按 SCSI `READ CAPACITY(10)` 上报、ATA 按 `IDENTIFY` 上报；镜像位置与偏移视图按字节描述、起点按逻辑块对齐（见第一节与 4.1）。
- **USB 链路边界**：M6 落地的是“xHCI 根端口 + USB 核心 + BOT/SCSI”；hub 类驱动存在但不做下游设备枚举，UAS 没有实现。所以 M6 的 USB 存储能力边界是**设备直连主控根端口、使用 BOT 协议**；hub 后面的设备、UAS 设备属阶段 3 以后。
- **矩阵与驱动路径**：启动矩阵的 USB 档用 QEMU 的 xHCI 控制器（`qemu-xhci`）、根端口直连 `usb-storage`，验证内核 xHCI + UsbStorage 链而不是固件 USB 路径；BIOS USB 两档已按主线列硬判，UEFI USB / 4Kn U 盘两档当前只显示。内核 USB 驱动的细项由宿主检查 `CheckUsbCore` / `CheckXhci` / `CheckUsbHub` / `CheckUsbStorage` 覆盖，NVMe 由 `CheckNvme` 与启动矩阵的 UEFI NVMe 4Kn 档（QEMU 上挂 4096 逻辑块的 NVMe 控制器）验证；光盘直挂两档的 ISO 源列按 `iso9660: system volume file=` 标记判定。
- **宿主检查**：`CheckStorage`、`CheckExt4`、`CheckVfs`、`CheckDevModel` 保持 M5 覆盖；M6 新增 `CheckNvme`、`CheckUsbCore`、`CheckXhci`、`CheckUsbHub`、`CheckUsbStorage`、`CheckIso9660`（21 例）、`CheckFat32`（20 例）。
- **尚未接线的部分**（不得写成已实现）：① `DeviceKind` 缩范围与布局描述重读仍未接线；② FAT32 没有内核挂载消费方。这两项归 M6 收尾 / M7，接线前文档与验证都按“主路径只有偏移视图 + Ext4 身份核对”口径。**ISO9660 第二来源已在 M6 落地**：内核核心在光盘档做最小解析（PVD + 根目录项推出 `/SystemVolume.img` 区段并与 `BootInfo` 比对，`E-KRN-77` / `E-KRN-78`），它不属于 Boot.Volume 的挂载判定，也不依赖 ISO9660 模块的 `FileSystemOps`。

**诊断口径**：若启动机器的系统盘只经由尚未接线的路径覆盖的介质（例如 hub 下游的 USB 设备、UAS-only 设备，或完全没有块设备候选），块设备注册表里没有可用设备 → `MountSystemVolume` 返回 `NotFound`，内核打印 `[ FATAL ] E-KRN-7x`（detail 如 `no block device registered` / `no system volume candidate`）+ 屏幕 + 等待 + 复位。**不得**打印 `system volume mounted` 行、不得谎称已挂载、不得挂死或空转。

## 四、取舍与边界

引导期的启动模式与访问链见 1.1；内核侧的介质访问目标见第一节。引导期按固件报告的逻辑扇区大小访问介质，物理扇区大小不替代它。

| 取舍 | 决定与约束 |
| --- | --- |
| 读写 | 同一驱动和文件系统实例早期只读；Ext4 日志回放等会修改介质的操作不得隐式发生。需要恢复的卷只在具备安全写入与恢复条件后处理，否则报告并停止该启动路径 |
| DMA 与中断 | 早期允许必要的 DMA，轮询完成并设置超时；中断、工作队列和异步请求在依赖就绪后启用，沿用同一请求模型和资源归属 |
| 设备范围 | 优先扫描启动所需设备，之后在同一设备树上继续发现其他设备；不得另建早期设备表并在运行期重复绑定 |
| USB 控制器与链路 | xHCI 是引导闭包中的必备主控，M6 落地根端口上的 USB 3.x 链路及其管理的 USB 2.0 设备；根据主控、端口、线缆和设备实际能力协商速率。纯 EHCI 没有内核驱动；启动矩阵的 USB 档用 QEMU 的 xHCI 控制器（根端口直连 `usb-storage`），验证的是内核 xHCI 链而不是固件 EHCI 路径 |
| USB 存储协议 | M6 只有 BOT：按接口描述符找 Bulk IN/OUT 端点，用 CBW/CSW 完成 INQUIRY、READ CAPACITY(10) 与 READ(10)。UAS 属阶段 3 以后（未实现）；不能假定 USB 3.x 设备一定使用 BOT，UAS-only 设备本阶段不支持 |
| USB hub | M6 只落地 hub 类描述符与端口电源/连接变化，**不枚举 hub 下游设备**（`Usb.Host:1` 只服务主控根端口）；下游拓扑需扩展 UsbCore 的接口能力与验证范围，属阶段 3 以后，不另建运行期替代栈 |
| ISO9660 | 只读；主目录与 Rock Ridge，不要求 Joliet；固定 2048 字节逻辑块；名字按大小写折叠并去掉 `;N` 版本后缀；拒绝 Joliet、多区段、SL 符号链接跟随、关联属性与 EA 记录。镜像组装器保证所需路径能被这套实现识别 |
| 光盘系统卷 | 将 Ext4 系统卷镜像作为 ISO9660 文件保存，与磁盘版本共用卷内布局 |

USB 3.x 表示链路能力，BOT 表示存储传输协议，二者分别识别；支持 USB 移动存储不等于自动支持其上的所有文件系统。USB-SATA、USB-NVMe 桥接设备在此通过它们暴露的 USB 存储接口访问，不要求把 USB 桥接路径当作直接 AHCI 或 PCIe NVMe 控制器。

**UAS 属阶段 3 以后。** M6 的存储传输只有 BOT；UAS 需要命令/数据/状态端点、streams 能力检查与超时恢复，这组能力不在 M6 收尾范围内，也没有“UAS 不行就退回 BOT”的自动回退路径——设备只提供 UAS 接口时本阶段不支持。轮询和运行期异步处理共用同一协议状态与设备实例，异步化时再按第五节切换。

AHCI 的 CPU 侧传输使用 DMA，即使设备侧执行 PIO 命令也是如此。依据是 Intel AHCI 规范。

块设备契约必须携带设备报告的逻辑块大小，不得写死 512 字节（512e 为 512、4Kn 为 4096、光盘为 2048，都是合法取值）。镜像位置用字节偏移和长度描述，并检查边界与对齐：**偏移视图的起点必须按介质逻辑块大小对齐**，长度非零且不越界，读写的偏移与长度按逻辑块对齐由接口判定；起点不满足对齐就拒绝，不向下取整。光盘上的 Ext4 镜像使用块设备偏移视图；采用单区段实现时，镜像组装器必须保证文件连续且区段起点按目标介质的逻辑块对齐（4Kn 上为 4096），装载时核对，不支持的布局明确拒绝。内核侧的设备句柄、读写与刷新原语、子设备视图语义见[文件系统抽象与 VFS](文件系统抽象与VFS.md) 4.1。

**内核挂载系统卷的判定顺序**：闭包全部 `Init` 之后由内核核心调用 `Boot.Volume.MountSystemVolume`：候选 = 全部已登记根设备（M6 仍未接 `DeviceKind` 缩范围）→ 按 `volumeOffset` / `volumeBytes` 开偏移视图（起点按驱动报告的逻辑块大小对齐）→ 只读挂载 Ext4 并取卷内 `s_uuid` → 与 `BootInfo.volumeUuid` 逐字节核对 → **只有恰好一个候选通过才挂到 `/`**；零个或多个匹配都是失败（返回 `NotFound`，不按设备顺序挑、不猜），内核核心报 `E-KRN-70`–`76` 的 `FATAL` + 屏幕 + 等待 + 复位，不降级启动。挂载成功后由 `Boot.Volume` 打印 `system volume mounted: uuid=…`，再经 `Fs.Vfs` 读清单并打印摘要行，随后装载运行期模块（3.1）。**M6 仍不重读布局描述、`DeviceKind` 缩范围也还没有落地**（见 3.2 的“尚未接线”项，接口语义见[文件系统抽象与 VFS](文件系统抽象与VFS.md) 4.5 与第七节）；ISO9660 第二来源核对已由内核核心在光盘档实现（见 3.1）。

### 4.1 分区、部署与逻辑扇区单位

**分区表由部署阶段生成，不属于引导二进制。** MBR 分区项与 GPT 表项的长度字段不带单位，固件按目标设备的逻辑扇区解释，同一个整数在 512e 与 4Kn 上指向相差 8 倍的位置；分区表因此在写入时按目标设备确定单位，不存在一份字节同时适配两种逻辑扇区的写法。部署环节与职责：

| 部署环节 | 职责 |
| --- | --- |
| 通用镜像制作器（`MakeImage`） | 把引导载荷与系统卷组装成混合镜像（`LikesProgram.iso`）：刻录到 U 盘、移动硬盘、CD，或由虚拟机直接选择 ISO 文件启动 |
| 测试安装器（`TestInstaller`） | 模拟正式安装器，按目标设备生成 MBR 分区表与引导载荷，产出可写入内置硬盘、移动硬盘或 U 盘的整盘镜像 |
| 安装器（ISO 内运行） | 用户选定内置硬盘、U 盘或移动硬盘后，读取该设备报告的逻辑扇区大小，据此生成分区表并写入系统 |

**引导区与分区表分开看**：描述符区与载荷的位置字段以 512 字节为基准写入，同一份字节在 512e、4Kn 与 2048 字节单位的光盘上都指向同一处物理位置，BIOS 路径的装载方按运行期探测到的单位换算，因此同一份镜像可直接刻录到这些介质；分区表则相反——分区项不带单位，必须按目标设备生成（见 4.2）。

引导二进制（IPL、Stub、BaleenCore 与 `BOOTX64.EFI`）不解析分区表：BIOS 路径按介质起始的固定偏移读取描述符与载荷，扇区大小在运行期向固件询问；载荷按 4096 对齐，在 512 / 2048 / 4096 三种单位下都能整扇区读取。同一份二进制可直接写进 512e 或 4Kn 介质，不需要按扇区单位重新编译。

部署侧的分区要求：

| 项 | 要求 |
| --- | --- |
| 分区表形态 | MBR 与 GPT 两种形态共用同一套引导区，读取方按 LBA 访问；介质前部布局见 4.2 |
| 0 号分区 | ESP：类型 `0xEF`、FAT16、分区项起点固定 LBA 2048；512e 固件读到 1 MiB、4Kn 固件读到 8 MiB，两处各放一份同样的 FAT 卷，内容含 `\EFI\BOOT\BOOTX64.EFI` |
| 1 号分区 | 系统卷：类型 `0x83`、Ext4 |
| 引导载荷保护区 | 介质起始区不得被分区覆盖：描述符独占一个扇区（`CoreDescriptor` 是其中的一个段），引导载荷自描述符扇区之后、按 4096 对齐 |
| 系统卷定位 | 由 `BaleenLayout.bin` 布局描述给出，写入方保证分区表、布局描述与实际写入位置一致 |

**ISO 是分发与安装媒介**：运行于虚拟机挂载、U 盘启动或移动硬盘启动，用于试用与执行安装；硬盘上的正式系统由安装器按上面的要求写入。系统卷在 ISO 内是 ISO9660 卷内的 Ext4 镜像文件，与磁盘形态共用卷内布局。

### 4.2 引导区与分区表保留区

**MBR 与 GPT 共用同一套引导区。** 描述符独占一个扇区（`CoreDescriptor` 是描述符区里的一个段），引导载荷自描述符扇区之后、按 4096 对齐：两者都落在 GPT 保留区（主头 LBA 1、分区项区 LBA 2–33）之后，也落在 MBR 只用 LBA 0 的范围之后。分区表形态因此只影响介质最前部的分区描述，切换形态不需要调整引导区，也不需要重新编译任何二进制。

介质前部的两类内容分开看（LBA 以设备逻辑扇区为单位）：

| 内容 | MBR 分区表 | GPT |
| --- | --- | --- |
| LBA 0 的 0–445 字节 | IPL 引导代码（两种形态共用同一份） | 同左 |
| LBA 0 的 446–509 字节 | 槽位 0 = ESP（`0xEF`）、槽位 1 = Ext4（`0x83`） | 槽位 0 = `0xEE` 保护项，覆盖全盘 |
| LBA 1–33 | 空闲 | GPT 主头（LBA 1）与分区项区（LBA 2–33） |
| `0x20000` | 布局描述（`BaleenLayout.bin`）：卷标识、系统卷位置、内核路径与状态区域 | 同左 |
| `0x21000` | 引导状态区域：引导选择器的裸块状态区 | 同左 |
| 描述符扇区 | 引导区的描述符区：头部与段序列（两种形态共用；LBA 272 / 68 / 34） | 同左 |
| `0x23000` 起 | 引导载荷：Stub 与 BaleenCore | 同左 |
| 第一个分区 | 0 号分区 ESP（FAT16）、1 号分区 Ext4 系统卷 | 同左，分区改由 GPT 项描述 |
| 磁盘末尾 | — | GPT 备份表与备份头 |

**分区表的写入方**：MBR 分区表由通用镜像制作器与测试安装器（`MakeImage` / `TestInstaller`）生成；GPT 分区表的写入列入部署侧实现（安装器按目标盘生成），两者的 LBA 单位都按目标设备的逻辑扇区确定（见 4.1）。

**混合 ISO 固定使用 MBR 分区表。** 光盘形态没有分区表，混合镜像（写 U 盘或移动硬盘）的 MBR 只为固件找 ESP 服务；GPT 与 ISO 结构有三处硬冲突：GPT 主头与标准项区（LBA 1–33）覆盖 El Torito 引导镜像（位于字节 `0x800`）与 ISO9660 元数据（主卷描述符固定在 LBA 16）；备份表需要盘尾扇区，而那里是 ISO9660 的文件数据区；GPT 服务的需求（超过 2 TiB 的盘、与其他系统共存）也不适用于安装介质。**需要 GPT 的是安装器装配的磁盘布局**，不是 ISO 本身。

描述符独占一个扇区，其 LBA 按单位取 272 / 68 / 34，三者指向同一物理扇区，都在 4Kn 的 GPT 保留区之后。**同一份镜像在三种单位下的引导区位置一致**，不随介质单位变化。

引导区的容量要求：Stub 的装入窗口按介质为 `0x8200`（512e）或 `0x8000`（4Kn / CD），正式组装器统一按最严的 `0x8000` 检查文件长度，使同一份产物写进三种介质都可引导；BaleenCore 上限为 `0x400000`，若核心载荷接近该上限，"1 MiB 之前"的范围（约 1 MiB 减保留区）容不下，写入侧需后移第一个分区起点或为核心载荷另划未分区区段。

读盘只走 EDD：引导区位于保留区之后，超出传统 C0H0 兼容范围，不保留 CHS 回退。

## 五、阶段切换与写入启用

同一实例从轮询转为中断或异步处理时，要暂停新请求、完成或收敛在途 I/O、切换完成通知方式，再恢复请求。写入的启用还须验证介质可写、缓存刷新、文件系统一致性及失败处理能力。阶段切换不构成驱动热替换，也不释放仍有效的实例和资源。

**M6 仍只有读路径。** 引导闭包交付的驱动（ATA / AHCI / NVMe / xHCI / USB 存储）只用读命令，Vfs / Ext4 / ISO9660 / FAT32File 都停在只读阶段；运行期 `.osm` 的装载也是只读（`Stat` / `Open` / `Read` / `Close`）。写操作、日志回放、中断与异步、`Activate` 都是阶段 3 以后的能力。块设备的刷新能力按接口事实携带（`BlockDeviceOps.capabilities` 的 bit0，对应共用接口 `HasFlushPrimitive()`，见[文件系统抽象与 VFS](文件系统抽象与VFS.md) 3.2 与 4.1）；M6 各驱动的 `BlockDeviceOps.capabilities` 都是 0（没有真实刷新原语），本阶段也不使用写路径；切到写路径时先满足本段与上一段的条件，再谈持久化。同一设备与文件系统实例跨启动期与运行期不变：阶段 3 切换只换完成通知方式，不重新绑定、不换实例。

**没有可写介质时只读运行。** 日志保存在内存和可用输出通道，配置及内核集不能更新，也不启用需要持久试启动记录的自动回滚协议。U 盘、移动硬盘和外置 SSD 上的系统在写入条件满足后可以写入，日志和更新元数据应控制写入频率。
