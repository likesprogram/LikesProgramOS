# 内核启动与固件边界

本文定义内核入口的最小契约、固件服务在本项目中的失效边界，以及第三方引导方式接入本内核的条件。

**核心口径：内核只认自家引导器 [Baleen](Baleen/README.md) 的交接契约；进入 `KernelMain` 的第一步就是让固件启动服务失效，此后固定运行模式，不降级回固件。**

## 一、内核入口契约

内核入口由引导器按其交接契约提供，包含三部分：

- **镜像入口**：内核镜像文件起点的[内核镜像数据](Baleen/内核镜像数据.md)与它给出的入口点；数据声明内核的长度、内存跨度、装载地址、要求的 `BootInfo` 版本与所属发布线 `ModuleMajor`，并带整幅镜像的摘要与 `.os` 发布线身份 `BuildId`。身份与摘要由清单生成工具写入、由打包器校验，Baleen 在装载前再核对。
- **交接事实**：`BootInfo` 的尺寸与版本、机器状态、内存图、启动来源、输出通道、内核集身份，以及内核集交接包（已验证清单副本、`Modules.list` 副本、预装模块记录）。
- **预装字节**：`Modules.list` 里命中引导闭包期望集的 `.osm` 文件字节，由 Baleen 在交权前读入低 4GiB 内存，并在 `BootInfo` 中交出地址、长度与清单产物条目下标。每个预装模块的主版本必须与 `.os` 的 `ModuleMajor` 硬相等，不等即按所选集失败处理，不进入内核。

**内核不为第三方引导协议提供适配层。** `.os` 里没有 Multiboot2、Linux boot protocol 之类的入口实现，也不承诺从这些入口启动。BIOS 与 UEFI 是本项目自家支持的引导模式，它们的入口形态由 Baleen 一侧负责准备——UEFI 固件加载的是 Baleen 的固件应用，BIOS 加载的是 Baleen 的一级引导，两者都不直接接触内核镜像，因此**内核镜像不需要附带任何固件能直接识别的标准头**。内核在入口处先按镜像数据核对自身链接布局，再核对 `BootInfo` 的尺寸与版本，然后按其中声明的机器状态进入自己的初始化序列。`BootInfo` 的字段定义、生成方式和版本规则由 [Baleen 引导器](Baleen/README.md) 定义。

**第三方引导方式必须交出同样的交接包。** 它要像 Baleen 一样先验证清单、按 `Modules.list` 预装引导闭包成员，再交出清单副本、`Modules.list` 副本与预装模块记录；不预装或交不出这些事实的引导方式会在入口核对阶段落到 `FATAL` 路径，本项目的规格不为它保留降级或适配分支。

**内核还要知道自己是从哪儿起来的。** `BootInfo` 的启动来源字段给出启动设备线索、系统卷位置与卷标识、引导状态区域、内核路径与引导器占用区间（见 [Baleen 引导器](Baleen/README.md) 6.1）：运行期更新据此把新内核集写进同一个卷、把状态记录写回同一处区域。**`BootInfo` 是定长契约：内核要求 `Version` 等于 `BootInfo::InfoLayout::kVersion`、`Bytes` 达到 `InfoLayout::kBytes`，版本不符或短于该尺寸直接拒绝并停机——不为第三方引导协议提供适配层，“结构更短”不解释成缺字段。** 结构成立后，内核入口核对并播报这些事实，把引导器占用区间标为不可用内存；启动来源字段为 `0`（未提供）或彼此不一致时按 `WARN` 报告并按“未提供”处理，不停机（内存图不属于启动来源：读不到在内核侧直接失败）。按线索去 `LayoutOffset` 处重新校验卷标识与布局信息这一步，在引导闭包的设备模型初始化后接上；当前内核核心还没有设备枚举实现。

**`BootInfo` 还携带内核集交接包。** 清单副本与 `Modules.list` 副本都是 Baleen 验签/摘要通过的那份字节；预装模块记录逐条给出模块文件字节的物理地址（低 4GiB）、长度与清单产物条目下标。交接包字段在 `BootInfo` 的既有保留区：`kernelSetManifest`、`bootList`、`bootModules` 三个地址字段与 `kernelSetManifestBytes`、`bootListBytes` 两个长度字段，预装记录数组以 `count` 头开始、每条 16 字节；字段偏移、记录布局与保留字段要求见 [Baleen 引导器](Baleen/README.md) 6.2，语义定义在[内核集清单与签名](内核集清单与签名.md) 2.3。签名由引导器在交权前验证，内核不重验签名，只以交接的清单副本与摘要为准。接口版本保持 `1`、`kBytes` 保持 `0x100`，只追加、不移动；字段定义已定稿，M2 起 Baleen 两侧采集与填写、M3 起内核入口按同一份字节核对，均已落地。

**内核入口在任何模块执行前核对交接包**：清单副本、`Modules.list` 副本与预装模块记录可读且不越界、列表条目集合与清单 `Type=2` 条目集合相等（类型、路径）、记录只覆盖列表里的引导闭包条目并与清单长度一致、`.os` 的 `BuildId` 等于清单 `BuildId`、`.os`/列表/每个预装模块的主版本硬相等、引导闭包成员齐全且无重复。列表里的非闭包条目是运行期模块，不属于交接包核对失败。三类缓冲同样必须在低 4GiB 的恒等映射内可读；交接包缺失或不可读不按“未提供”放过，而是按引导闭包不完整处理。核对通过后，把这些物理区间在页帧分配器中标为已占用，再复制或接管到内核自有内存，之后才允许执行任何模块入口。

**交接包不成立时不做降级启动。** 缺清单副本或列表副本、缺预装记录、列表与清单 `Type=2` 集合不等、引导闭包成员缺失、摘要不符、`.os` 的 `BuildId` 与清单不一致、主版本不等、条目重复，一律输出 `[ FATAL ] E-KRN-5x`（编号在 `50`–`59` 段内，已定号）屏幕可见报错，等待（默认 10 秒，可配）后请求平台复位重启；复位不可用时停机并保留诊断。屏幕事实（`screenKind` / 地址 / 几何 / 格式）与 `fatalWaitMs` 的字段已定稿（`Packages/Common/Include/BootInfo.hpp`、[Baleen 引导器](Baleen/README.md) 6.1），屏幕目标、等待与复位已由 M3 落地（T3.5）。

这样安排的理由是职责单一：**识别介质、定位卷、读入镜像、读入清单与引导闭包、预装字节、准备机器状态全部属于引导器**，内核从“已经拿到并验证过的启动信息与字节”开始工作。内核对引导器用什么方式找到系统卷不感兴趣，只要求 `BootInfo` 里的事实准确、交接包与清单一致。

## 二、固件服务失效边界

**固件不是被假定已经卸载，而是在 `KernelMain` 的第一步失效。** 区别很重要：

- 引导阶段的介质访问、卷定位、内核与引导闭包装载由引导器完成，此时代码运行在固件提供的环境中（BIOS 中断或 UEFI Boot Services）。
- 进入 `KernelMain` 后，内核立即让固件启动服务失效，此后不再调用任何固件服务。目的不是“清理”，而是**固定运行模式**：内核之后的每一条执行路径都只能依赖自己的实现，不存在“这次不行就退回固件”的分支。

| 环境 | 失效动作 | 之后 |
| --- | --- | --- |
| UEFI，Boot Services 仍有效 | **本阶段登记为不适用**：内核入口只拿到 `BootInfo`，其中没有 SystemTable、ImageHandle 与 MapKey，无法调用 `ExitBootServices`；该状态保留 `E-KRN-07` 并停机，不做“尽力退出”的假实现。要支持它必须扩 `BootInfo` 契约（表指针 + 映像句柄 + MapKey），属后续阶段的契约变更，不在 P5 | 无（停机） |
| UEFI，引导器已退出 Boot Services | 不重复调用，只核对 `BootInfo` 中的状态标记 | 同上 |
| Legacy BIOS | BIOS 服务只在实模式可用，长模式下本就不具备调用条件；内核不建立回退路径，也不保留实模式跳板 | 不再使用 BIOS 中断服务 |

**“不降级”的准确含义**：不因为固件还能提供某项能力就把该能力算作可用。UEFI Runtime Services 在 `ExitBootServices` 之后技术上仍然存在，本项目也不使用它们——需要平台能力（时间、变量、复位、电源）时，由内核对相应硬件或 ACPI 表自行实现，或由用户态服务接管。这条边界同时约束驱动和模块：**内核代码不得为“固件还能帮忙”设计任何分支**。

失效之后的启动全过程见下一节；设备与文件系统能力来自交权前预装的引导闭包 `.osm`，见[内核架构与自举闭包](内核架构与自举闭包.md) 2.2 与[启动介质与文件系统](Common/启动介质与文件系统.md)。

## 三、载入链

```text
阶段 0  固件 → 引导工具 / 引导选择器（Baleen）→ 所选内核集
        读清单并验签，装载 .os，并按 Modules.list 里的引导闭包成员装载预装 .osm
        核对摘要、BuildId、主版本硬门与内存落点
        自动回滚模式先持久记录 Trying，再交权；BootInfo 交付统一启动状态、清单副本、Modules.list 副本与预装模块记录
阶段 1  KernelMain：核对镜像数据与 BootInfo 的入口事实
        让固件启动服务失效，固定运行模式
        校验交接包：清单副本、Modules.list 副本、预装模块记录、BuildId、主版本与摘要的一致性
        初始化内核核心：平台、内存、对象/归属、调度、IRQ、容器与模块装载
        把预装字节在页帧分配器中标为已占用并接管到内核自有内存
        按依赖序初始化引导闭包：
        DevModel 优先发现启动路径 → 启动设备驱动与 DriverLoader → VFS 与块设备 → Ext4/ISO9660/FAT32File
        挂系统卷；集目录由 KernelPath 与 KernelSetBuildId 推出
阶段 2  按所选模块修订的清单登记路径从系统卷读取运行期 .osm，逐条核对长度与摘要后按硬依赖图装载
        运行期基础模块通常包括 Process、Ipc、Fault；缺必需模块走 FATAL + 等待 + 重启
阶段 3  按激活条件启用调度、IRQ、工作队列及驱动异步能力
        同一 DevModel 继续枚举；DriverLoader 装载额外 .drv，已有绑定不重复创建
        引导闭包中的启动驱动继续使用同一实例，满足介质和文件系统条件后开放写入
阶段 4  内核 exec Init.exe → 必需服务与健康检查 → 会话或发行指定的就绪状态
        试启动满足全部确认条件后，持久提交 Confirmed（确认整个修订）
失败    引导闭包或必需模块缺失、校验失败（含主版本门）：[ FATAL ] E-KRN-5x 屏幕可见 + 等待（默认 10 秒，可配）+ 平台复位重启
        可选运行期模块失败：传播依赖失败并按发行策略降级（WARN），不重启
        已激活状态不可恢复：报告并重启；选择器回退整集或上一模块修订
```

`Init` 只做可撤销的软件准备，不启动线程、不启用设备中断、不执行不可逆设备操作；`Activate` 才按依赖启用对应能力。启动设备的首次硬件激活发生在引导闭包初始化期间、挂系统卷之前，可使用同步轮询。后期异步能力的启用是该实例的阶段转换，不是再次执行 `Init` 或创建替代实例；引导闭包内部同样按同一依赖图检查。阶段转换与写入启用条件见[启动介质与文件系统](Common/启动介质与文件系统.md)。

阶段 0 的引导闭包装载（M2）、阶段 1 的交接包核对（M3/M4）与阶段 2 的运行期模块装载（M6）均已落地；内核当前停在调度与进程模型之前的阶段边界。

**引导闭包完整性由内核入口把关，不在后面阶段补。** 清单副本、`Modules.list` 副本、预装模块记录与清单之间的任何不一致都在任何模块执行前按 `FATAL` 报错、等待与重启；缺任何一个引导闭包条目都按所选集失败处理，不存在“先启动再补装”的路径。第三方引导器不预装引导闭包时落到同一条路径。

**启动设备线索不足时，由内核在引导闭包初始化后校验卷标识和布局信息；无法唯一定位就报告失败，不能猜测磁盘。** 线索由 `BootInfo` 传入，校验规则见 [Baleen 引导器](Baleen/README.md)。

进入用户态之后的启动编排见[用户空间与常驻服务](用户空间与常驻服务.md)。
