# 内核架构与自举闭包

本文定义 LikesProgramOS 内核的组成方式：内核核心与引导闭包的划分、`LINK_MODE` 与源码边界、模块与驱动的交付归属，以及镜像体积口径。

**内核 = 内核核心 `LikesProgram.os` + 引导闭包 `.osm` + 发行选择的运行期 `.osm`。** 三者与构建清单同属一个内核集，共享同一个 `.os` 发布线身份 `BuildId`；同一个发布线内的模块按修订更新，补丁不换 `BuildId` 与集目录，也不换 `.os`。引导闭包是退出固件启动服务后、挂载系统卷之前就必需的模块集合，由 [Baleen](Baleen/README.md) 在交权前随 `.os` 一起从集目录读出并预装；内核入口核对交接事实后才初始化它们，再挂系统卷、装载运行期模块。发行配置不能裁掉引导闭包；运行期模块可以按需选择，但被选中能力的硬依赖必须齐全。

内核模块共用源码和接口契约，通过 `LINK_MODE` 决定编入 `.os` 内核核心，还是生成引导闭包或运行期装载的 `.osm`。拆分的目的有两个：

- **引导期自足。** 内核核心不内置设备与文件系统实现，也能启动：引导闭包在交权前已由引导器预装，内核入口不必先挂载系统卷就能校验并初始化它们。
- **更新可恢复。** 主版本升级换新的 `.os` 与新的 `KernelSets/<BuildId>/` 目录，按整集切换与回滚；同一发布线内的模块按修订更新，整修订重启切换、整修订回退。模块可以分别存储和传输，但不能绕过主版本门与清单一致性检查跨发布线混装。

后缀语义见[后缀设计](后缀设计.md)；`.osm` 容器格式、接口版本与依赖规则见[内核模块容器](内核模块容器.md)，本文引用其约定，不另行定义。

## 一、构建模式与源码边界

| 取值 | 产物 | 初始化调用方 |
| --- | --- | --- |
| `LINK_MODE=builtin` | 编进 `LikesProgram.os` 内核核心 | 内核核心启动序列 |
| `LINK_MODE=module` | 编成 `xxxx.osm` | 引导闭包：内核入口校验交接后初始化；运行期模块：内核挂载系统卷后装载 |

`LINK_MODE` 决定链接目标，不决定模块由引导器预装还是由内核装载——后者由集内的 `Modules.list` 决定（列表是内核侧书写的完整模块清单，其中命中引导闭包期望集的成员由引导器在交权前预装，其余由内核挂卷后装载），见[内核集清单与签名](内核集清单与签名.md) 2.3。同一次构建里一个模块只产出一个形态；两种目标共用模块逻辑、接口声明和初始化契约，不按链接目标维护两套实现。

构建与装载遵守以下规则：

1. **内核核心只保留内核核心能力。** 内核核心负责平台初始化、物理与虚拟内存、Objects、Sched、Irq、输出与诊断、容器与模块装载、配置与清单解析、启动状态/信任锚/契约层；这些能力编进 `.os`，不产出 `.osm`。设备模型、驱动装载、VFS 与块设备层、启动设备驱动和文件系统一律不编进内核核心，见第二节。
2. **引导闭包成员固定，发行配置不能裁剪。** 成员见 2.2；它们必须出现在 `Modules.list` 里，由引导器在交权前预装。禁止把其中任何一条改回内核核心，也禁止在发行配置里删掉——否则“内核核心 + 引导闭包”的启动组成不成立。
3. **内核核心不得硬依赖 module。** 构建系统按接口需求和依赖声明检查依赖图：内核核心的导入只能由内核核心自身满足，或经契约层注册面在提供者就绪后启用，不能直接导入具体 `.osm` 的符号。引导闭包内部可以互相硬依赖并按依赖序初始化；运行期模块可以依赖引导闭包已发布的接口。
4. **跨模块接口只有一份定义。** 契约层生成导出与导入声明；编入 `.os` 时由链接器解析，生成 `.osm` 时由装载器按接口 ID 与版本解析。调用方式的差异由构建和装载工具处理，模块实现不因交付形态分叉。
5. **模块与驱动只有一份实现。** 引导闭包中的启动设备驱动是完整实现，启动到运行期沿用同一设备身份、资源记录和驱动实例；早期同步轮询、后期中断与异步工作的区别是同一实现的运行阶段，不是 `boot/full` 两套代码。引导器不解析 `.osm` 的段表与接口表、不重定位、不执行模块，它对引导闭包的职责只是把清单验签通过的字节预装到内存，见 [Baleen 引导器](Baleen/README.md) 6.2。
6. **一个内核集对应一个 `.os` 发布线。** `BuildId` 是发布线身份：`.os` 文件起点的 `BuildId` 字段就是集目录名，`.osm` 不自带 `BuildId`、摘要或签名，完整性由清单摘要级联。同一发布线内允许保留多个模块修订，装载时核对清单、摘要与集身份，不接受跨发布线混装，见[内核集清单与签名](内核集清单与签名.md) 2.2。
7. **模块主版本跟随 `.os` 发布线。** `.os` 镜像数据里的 `ModuleMajor` 是发布线（[内核镜像数据](Baleen/内核镜像数据.md)）；每个 `.osm` 的 `ModuleVersionMajor` 必须与它硬相等，跨主版本一律拒绝装载，即使 ABI、接口与依赖范围碰巧匹配。模块修订只在重启后整修订生效，运行期不替换、不卸载，见[模块修订与更新](模块修订与更新.md)与[模块与驱动装载](模块与驱动装载.md)。

## 二、内核的组成：内核核心、引导闭包与运行期模块

### 2.1 内核核心（`.os`）

内核核心负责从入口到“能够挂载系统卷并装载其余模块”的全部机制，不含设备与文件系统的具体实现。入口核对镜像数据与 `BootInfo`、让固件启动服务失效，随后校验交接包、初始化平台与内存，再在页帧分配器中标占预装区间、接管预装字节，并按依赖序初始化引导闭包——这条路径不依赖任何文件系统。内核入口的交接契约见[内核启动与固件边界](内核启动与固件边界.md)第一节。

内核核心的模块及其硬依赖设为 `LINK_MODE=builtin`：

| 模块 | 内容与边界 |
| --- | --- |
| 平台初始化 | GDT/TSS/IDT、长模式、页表与 physmap、CPU 特性与拓扑探测、异常处理和早期计时；自举所需 ACPI 等平台事实在此取得。描述符表的装载机制与 Baleen 的分工见 [CPU 描述符表](CPU描述符表.md) |
| 物理内存与虚拟内存 | 页帧分配器、地址空间、映射、内核堆及 DMA 缓冲区管理 |
| Objects | 统一对象、句柄、代际、命名空间和归属记录；设备资源从首次登记起使用同一套机制，用户句柄在进程环境就绪后启用 |
| Sched | 调度器、线程、等待队列和同步机制；早期不需要线程的路径同步执行，就绪后启用工作队列和抢占 |
| Irq | 统一 IRQ 登记、分发和排空；早期设备 I/O 可轮询，满足激活条件后启用设备中断 |
| 输出与诊断 | 内存日志 ring、可用串口、VGA 文本、BootInfo 帧缓冲绘字、栈回溯和诊断；持久输出等待写路径可用；文本输出的前端与阶段装配见[输出通道与Print](输出通道与Print.md) |
| 容器与模块装载 | 有界解析、段映射、重定位、导入解析、接口版本选择、依赖校验及初始化编排；容器格式见[内核模块容器](内核模块容器.md) |
| 配置与清单 | 解析配置与引导器交来的已验证清单副本，选择能力与发行策略；不能通过配置改写产物的硬依赖 |
| 启动状态、信任锚与契约层 | 所选内核集与试启动身份、失败报告和重启请求、信任及撤销规则、公共基础库和接口声明 |

内核核心的失败报告要能到达屏幕：致命失败按[内核诊断编号](内核诊断编号.md)用 `[ FATAL ] E-KRN-xx` 行报告，并具备等待后请求平台复位的机制。屏幕事实与等待配置已定稿，屏幕目标、等待与复位已由 M3 落地（T3.5）；内核链路已到引导闭包装载、系统卷挂载、清单读取与运行期模块装载。

### 2.2 引导闭包（`.osm`）

引导闭包是退出固件启动服务后、挂载系统卷之前必需的模块集合。它们按 `Modules.list` 里的闭包成员在交权前由引导器预装，内核入口校验交接后按依赖序初始化；成员固定为下表，发行配置不能裁剪。

| 模块 | 内容与边界 |
| --- | --- |
| DevModel | 完整设备模型：设备身份、PCI/USB 与平台枚举、资源分配、拓扑和绑定关系；早期优先发现启动路径，运行期在同一设备树上继续枚举和处理热插拔 |
| DriverLoader | 统一管理驱动描述与外部 `.drv`：匹配、校验、初始化、绑定、停用及符合条件的热替换 |
| VFS 与块设备层 | 统一挂载、路径解析、文件引用、块大小和偏移视图；早期与运行期沿用同一卷和设备实例；接口与内核侧落地口径见[文件系统抽象与VFS](Common/文件系统抽象与VFS.md) |
| 启动设备驱动 | AtaPio、Ahci、Nvme、UsbCore/Xhci/UsbHub、UsbStorage：ATA PIO/ATAPI、AHCI/SATA、NVMe、xHCI 与 USB 2.0/3.x 设备与 hub、BOT/UAS 与 SCSI 存储；覆盖 U 盘、移动硬盘、外置 SSD 与 USB 光驱，同一实例分阶段启用读写、中断和异步处理 |
| Ext4 | 默认系统卷文件系统，包含读写实现；早期只读，日志回放与写入在具备安全写入与恢复条件后启用 |
| ISO9660 | 只读光盘文件系统，支持主目录与 Rock Ridge，用于定位系统卷镜像和读取光盘文件 |
| FAT32File | FAT32 读写，提供引导文件、安装恢复介质和交换卷的访问能力；读写共用同一实现，早期只读 |

**M6 实现状态**：上表 13 个模块均已落地为真实实现；USB 链为 xHCI 根端口 + BOT/SCSI（hub 下游枚举与 UAS 属阶段 3 以后），DevModel 以 PCI 枚举为主、USB 设备经 UsbCore `Register` 接入，外部 `.drv` 装载、热插拔、Ext4 写与日志回放、FAT32 / ISO9660 的挂载消费者属后续阶段。

引导闭包的内核侧处理规则：

1. **预装由引导器负责，容器解释由内核负责。** Baleen 只核对 `.osm` 的最小读取面（魔数、`Version`、`HeaderBytes`、`TotalBytes`）并按清单核对长度与摘要，还读文件头到 `ModuleVersionMajor`（偏移 `0x66`）与 `.os` 的 `ModuleMajor` 比较，跨主版本不搬运；不解析段表、不做重定位、不执行模块。容器解析、摘要核验、段映射、重定位、导入解析、依赖检查与初始化都由内核完成，见[内核模块容器](内核模块容器.md)。
2. **先校验交接，再执行任何模块。** 内核入口核对清单副本、`Modules.list` 副本与预装模块记录可读且不越界、列表条目集合与清单 `Type=2` 条目集合相等、记录只覆盖列表里的引导闭包条目并与清单长度一致、`.os` 的 `BuildId` 等于清单 `BuildId`、`.os`/列表/每个预装模块的主版本硬相等、引导闭包成员齐全且无重复；随后把预装字节的物理区间在页帧分配器中标为已占用，再复制或接管到内核自有内存。核对规则见[内核启动与固件边界](内核启动与固件边界.md)第一节。
3. **按依赖序初始化，不降级启动。** 引导闭包在挂载系统卷之前完成初始化与挂卷必需的激活；缺清单副本或列表副本、缺预装记录、应有条目缺失、摘要不符、`.os` 的 `BuildId` 与清单不一致、模块主版本与 `.os` 发布线不符、条目重复或未知，一律按所选集失败处理：`[ FATAL ] E-KRN-5x`（编号在 `50`–`59` 段内，P5 定号）屏幕可见报错、等待（默认 10 秒，可配）、请求平台复位重启；复位不可用时停机并保留诊断。第三方引导器不预装引导闭包时落到同一条失败路径，本项目不为第三方引导方式提供适配层。
4. **不维护“早期替代实现”。** 内核核心不内置简版设备或文件系统实现作为回退；引导闭包中的驱动与文件系统就是完整实现，早期只读、轮询与后期读写、中断异步是同一实例的阶段转换，见[启动介质与文件系统](Common/启动介质与文件系统.md)。

**引导闭包成员表是单点定义。** `Packages/Common/Contract/BootClosure.def` 用 `closure <顺序> <逻辑名>` 固定 13 个成员的预装顺序与逻辑名（逻辑名同时是 `ModuleId` 派生输入与文件名主名），由 `MakeContract` 生成内核期望集表；Baleen 的预装筛选、内核 `E-KRN-55` 的完整性判定与 `CheckPreload` 都用这一份，不在别处维护第二份成员表。成员固定、发行配置不能裁剪；增删成员必须同步本表与[模块修订与更新](模块修订与更新.md)第四节，并重签清单。

引导闭包预装与交接字段的字节表见 [Baleen 引导器](Baleen/README.md) 6.2；`BootInfo` 的交接包字段（清单副本、`Modules.list` 副本与预装记录）定义已定稿，M2 / M3 起已按此实现。

### 2.3 运行期模块（`.osm`）

运行期模块指装载时机在挂载系统卷之后的 `.osm`：内核按清单登记的路径与摘要从系统卷读取，逐条核对后按硬依赖图装载。路径相对集目录，集目录由 `BootInfo.KernelPath` 与 `KernelSetBuildId` 推出，装载路径取自验证通过的清单条目，见[内核集清单与签名](内核集清单与签名.md)与 [Baleen 引导器](Baleen/README.md) 6.1。**同一集目录里可能保留多个模块修订的文件**（`Modules/` 下平铺、文件名带版本），一次启动只装载所选修订，旧修订只是回滚材料；模块主版本必须与 `.os` 的 `ModuleMajor` 硬相等，跨主版本拒绝，修订切换重启生效、整修订回退（[模块修订与更新](模块修订与更新.md)）。

- **通常必需的模块**：`Process`、`Ipc`、`Fault`。发行通常把它们列为必需；缺失按所选集失败处理，走 `[ FATAL ] E-KRN-5x` 屏幕报错、等待与重启，不做“只少一个模块”的降级启动。
- **可选模块**：`ExFAT32File` 等按发行需要选择。缺失或初始化失败按发行策略降级并输出 `WARN`，不重启；被选中能力的硬依赖仍必须齐全。
- **全部在启动阶段装载**：“运行期”指装载时机在挂载系统卷之后，不是运行期按需加载。内核模块成功激活后与内核同寿命，不卸载；没有按需热加载模块的路径。

装载流程、初始化契约、归属登记与失败语义见[模块与驱动装载](模块与驱动装载.md)。

**完整实现不等于全部功能同时启动。** Objects、Sched 与 Irq 随内核核心内置，避免设备框架与引导闭包反向依赖尚未装载的模块；引导闭包提供完整设备与文件系统实现，但只在对应设备、卷和运行条件就绪时启用读写、中断与异步。初始化与运行阶段都参与依赖检查：不能因为某次调用发生得晚，就允许内核核心直接导入具体 `.osm` 的符号。

早期 I/O 默认采用有超时的同步轮询和必要的 DMA。切换到中断或异步处理前，使用同一实例完成请求排空、通知方式和同步状态切换；设备身份、资源所有权和上层引用保持有效，不重新绑定第二个“完整驱动”。阶段转换规则见[启动介质与文件系统](Common/启动介质与文件系统.md)。

## 三、外置能力归属

| 外置能力 | 归属 |
| --- | --- |
| 进程与用户地址空间管理、IPC、运行期故障策略 | 运行期 `.osm`；发行通常列为必需，早期故障报告和停止路径不依赖这些模块 |
| Ext4、ISO9660、FAT32File 之外的文件系统、网络协议栈、审计 | 运行期可选 `.osm` |
| 非启动必需设备及扩展驱动 | 外部 `.drv`，由引导闭包中的 DriverLoader 管理 |
| 设备管理策略、日志归档、显示合成、会话与登录、升级编排、诊断工具 | 用户态 `.exe` 与服务声明 |
| 分发和安装 | 安装包 `.app` 与 Installer |

具体模块与输出名称见[内核模块与驱动清单](内核模块与驱动清单.md)和[用户空间与常驻服务](用户空间与常驻服务.md)。

## 四、镜像体积与参考口径

**体积分两栏统计：内核核心 `.os` 与整集。** 内核核心按发布 `.os` 文件大小单独记录；引导闭包与运行期模块按整集合计记录，并分列各自的合计。集级体积与启动峰值内存的规划量级在 P5 实测后给出——它是规划参考，不是硬上限，也不作为构建失败条件；自举能力、必备功能和依赖完整性优先。

构建报告分别记录内核核心文件大小、引导闭包合计、运行期模块合计、整集合计、采用压缩时的压缩前后大小、启动峰值内存和运行期常驻内存；调试符号单独统计。启动峰值内存包含 `.os` 装载跨度与交权前预装的引导闭包字节。不能用一个数字代替全部口径。

主流系统也会在启动早期准备启动依赖，但打包方式不同：Linux 可以由引导器提供 initramfs，也可以将其嵌入内核镜像；Windows 的 OS loader 提前装入 boot-start 驱动；macOS 使用预链接启动镜像或 Kernel Collection。LikesProgramOS 的选择是把启动必需的设备与文件系统实现放进引导闭包 `.osm`，由引导器在交权前与 `.os` 一起从集目录读入并预装；内核核心因此不必内置这些实现，但也不要求内核自己先从卷上读取它们。引导闭包仍属于整集，随主版本升级或同一发布线内的模块修订更新与回滚。
