# 内核诊断编号

本文登记内核侧失败路径的稳定编号，前缀 `E-KRN`。编号是工单、日志聚合与自动化回归引用的标识；**同一编号的含义一经发布不再改动，文本可以润色**。

编号随诊断行一起输出，行格式见第一节。文本与编号的配对定义在源码 `Packages/LikesProgramOS/Core/Include/Diagnostics.hpp` 的 `Kernel::Diagnostics::Diagnostic` 常量，行写法（`WriteDiagnostic` 与多字段现场用的 `WriteDiagnosticPrefix`）在 `Packages/LikesProgramOS/Core/Src/Tags.cpp` 实现；本表是它的登记副本，**新增编号必须同时改源码与本文**。

本文只覆盖内核镜像接管之后（`_Kernel_Main` 及其调用链）的失败路径。引导器交权之前的编号（`E-IPL` / `E-STUB` / `E-CORE` / `E-UEFI`）仍登记在[失败诊断编号](Baleen/失败诊断编号.md)，两套编号的关系见第五节。

**M7 状态：**`Diagnostics.hpp` 的 **49 个** `Kernel::Diagnostics::Diagnostic` 常量已全部落地，并与本文第四节的 49 行表格**逐字一致**（T7.4 脚本比对 0 差异）；未占用的序号是预留位，不是待定项，新增编号按第二节规则只增不改。历史任务号（T3.6/T5.9/G6d 等）只用于追溯编号来源，不再表示"待落地"。

## 一、行格式

带编号的诊断行统一写成 `[ 等级 ] E-KRN-<两位序号> <文本>`：编号与文本之间一个空格；等级由 `Kernel::Tags` 给出，带编号的行使用 `FATAL`（致命错误，随后停机）与 `WARN`（异常但继续）两个等级；文本为英文、句尾不带标点，与 Baleen 侧同一风格。

```text
[ FATAL ] E-KRN-07 The UEFI boot services are still active and exiting them isn't implemented
[ WARN ] E-KRN-22 The BootInfo volume is inconsistent: Layout=0x... Offset=0x... Bytes=0x...
```

现场的写法都不替代编号：

- **单个原因用括号 detail**：机制层回报的原因文本（如字段校验的具体原因）附在文本后的括号里，`[ FATAL ] E-KRN-10 The kernel image data is invalid (The kernel image data magic doesn't match)`。
- **启动来源的 WARN 字段紧跟文本**：行本身描述的事实由多个字段组成时，字段以冒号引出、按固定顺序排列（`E-KRN-20`–`E-KRN-23`），`[ WARN ] E-KRN-22 The BootInfo volume is inconsistent: Layout=0x... Offset=0x... Bytes=0x...`。
- **异常现场的数值放进括号**：CPU 异常按 `Vec=` / `Err=` / `Rip=` / `Cs=` / `Rflags=` 的顺序排列，`[ FATAL ] E-KRN-41 Exception (Vec=0x... Err=0x... Rip=0x... Cs=0x... Rflags=0x...)`。

**进度行与阶段边界行不是失败诊断，不带编号**（例如内核核心阶段到此结束的边界 WARN）。带编号的行通过 `Kernel::Tags` 与 `Print` 写到当前已装配的通道；同一个失败在所有通道上是同一行文本。

## 二、编号稳定规则

1. **首次发布之前不背兼容包袱**：编号可以直接改写、删除或重排，本文不留已废弃行（与[失败诊断编号](Baleen/失败诊断编号.md)第六节是同一条原则）。
2. **首次发布之后编号只增不改**：含义变化时分配新编号，旧编号不再复用；删除的编号标记为已废弃，不回收。
3. 文本可以润色，编号的含义不变；改动文本必须同时改源码常量与本文表格。回归与自动化按编号聚合，不按文本子串断言。
4. 编号在 `E-KRN` 命名空间内唯一，为两位十进制序号（`00`–`99`），不要求连续。新增编号取所属号段里下一个未用序号，不得跨段借用。
5. 每条 `Kernel::Diagnostics::Diagnostic` 常量都必须在本文登记；新增与删除都必须同一次改动里完成“源码常量 + 本文表格”两处。
6. 机制层补充现场（字段原因或机制层错误名一类）作为 detail 附在编号行末尾，不属于编号体系。

## 五、与 Baleen 失败诊断编号的关系

- **分属两层、两个前缀**：`E-IPL` / `E-STUB` / `E-CORE` / `E-UEFI` 登记引导器交权之前的引导链失败，`E-KRN` 登记内核接管之后的失败。两者行格式与稳定规则相同，编号空间独立，**不做同号异前缀映射**：同一个序号在两层可以含义不同，跨层定位按前缀查各自的表。
- **共享机制只回报文本、不产生编号**：`Kernel::CheckImageData`（`Packages/Common/Include/KernelImage.hpp`）只回报字段校验的原因文本。内核侧在调用点按失败点选号（`E-KRN-10`），原因文本作 detail；引导器侧对同一函数也是同样处理，只是选它自己的 `E-CORE-54` / `E-UEFI-54`。编号由调用方按各自的编号表分配，机制层不产生编号。
- 一次启动失败的日志里可能同时出现两层编号：引导链编号按[失败诊断编号](Baleen/失败诊断编号.md)查，内核编号按本文查。Baleen 文档开头有指向本文的交叉引用。
- `E-KRN` 是内核侧唯一的诊断编号命名空间：P5 起的 `.osm` 模块装载、设备模型、文件系统与基础模块失败都按第三节号段使用同一前缀，不另立内核侧第二套编号前缀。

## 六、屏幕与重启要求（已落地）

- **屏幕可见是 FATAL 的硬要求**：带编号的 `FATAL` 行必须同时输出到 `BootInfo` 报告的全部输出通道，并能到屏幕（BIOS 文本模式 / UEFI 帧缓冲）；屏幕上的行与流式通道上的行是同一行文本（同一编号与文本），不是另写一份提示。
- **引导闭包或必需模块失败（缺失、摘要不符、模块主版本与 `.os` 发布线不一致、`Modules.list` 非法、修订切换失败、依赖或 ABI 不满足等）**：内核输出屏幕可见的 `FATAL`（编号见第四节，`50`–`59` 已分配），等待一段时间（默认 10 秒，可配）后请求平台复位重启；复位不可用时停机并保留诊断。非必需模块失败按发行策略降级为 `WARN`，不重启。主版本门与 `Modules.list` 的语义见[模块修订与更新](模块修订与更新.md)第三节与第四节。
- **等待配置的载体是 `BootInfo.fatalWaitMs`**（`u32`，毫秒，偏移 `0x24`）：`0` 表示默认 10 秒（`InfoLayout::kFatalWaitMsDefault`），超过 10 分钟上限（`kFatalWaitMsMax`）按默认处理；测试镜像写小值加速失败注入。等待是失败可见性的一部分，不是安全边界，读方不做严格校验。
- **屏幕事实的载体是 `BootInfo` 的屏幕字段组**（`screenKind` / `screenAddress` / `screenWidth` / `screenHeight` / `screenStride` / `screenBytes` / `screenFormat`，偏移 `0x30..0x50`），采集规则见 [Baleen 引导器](Baleen/README.md) 6.1；事实不成立或内核不支持该像素格式时只走流式通道，**这不是失败**，也不改变等待与复位行为。
- **当前实现（M7）**：控制台由 `Console.cpp` 装配 `Serial` / `DebugPort` 流式通道，并在 `BootInfo` 屏幕事实成立时装配内核自绘屏幕目标（`ScreenTarget.cpp`，BIOS 文本页 / UEFI 帧缓冲）；`Fail()` 的路径统一为「报编号 → 按 `fatalWaitMs` 等待（默认 10 秒）→ 请求平台复位 → 复位不生效则停机」（`Core.cpp`），等待时基不可用与复位失败分别用 `E-KRN-90`（WARN）/ `E-KRN-91`（FATAL）报出。运行期必需模块失败的等待与复位循环证据：M6 证据目录 `boot/runtime/fault-reset`（26 秒定长跑，2 次启动、2 条 `E-KRN-81`，随后复位重启）。
- `50–59` 号段（内核集身份与模块装载）已分配并登记在第四节；`90–99` 号段留给停机、重启与恢复要求本身，其中 `90`（等待回退 WARN）与 `91`（复位失败）已分配并登记，`92`–`99` 预留。
