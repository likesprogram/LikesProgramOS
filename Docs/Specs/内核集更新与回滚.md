# 内核集更新与回滚

本文定义内核集的构成、试启动状态机、确认条件与失败处理，以及各类更新对象的生效边界。引导期的选版与状态写入由 [Baleen 引导器](Baleen/README.md) 承担，本文只规定它必须满足的语义；记录与清单的字节形态分别在[引导状态记录](Baleen/引导状态记录.md)与[内核集清单与签名](内核集清单与签名.md)。

## 一、内核集与并存

**选版、试启动、确认和回滚的单位是整个内核集。** 一个内核集包含一次构建的 `.os`、所需 `.osm` 和签名构建清单；清单还绑定启动配置、必需能力和健康确认条件。单个模块的改动也要生成新的内核集，不把旧构建模块补入新集。集的落点与清单格式见[内核集清单与签名](内核集清单与签名.md)。

系统保留候选集和已知良好集，两者的文件和清单不得互相覆盖。传输可以按文件或内容差异优化，但只有完整集校验通过后才能发布。用于启动的驱动、Init、服务声明和配置也须保留对应版本：同时兼容新旧内核的产物可以共享，不兼容的必须随启动配置并存。确认前不得执行破坏旧集恢复能力的不可逆共享数据迁移。

更新由 Updater 暂存产物并检查摘要、签名、依赖和外部 ABI，完成必要的数据刷盘后，最后发布 `Pending` 记录。引导选择器在固件服务仍可用时负责选版和早期状态写入；`.os` 的只读早期路径不承担这些写操作。Updater 的职责与启动时机见[用户空间与常驻服务](用户空间与常驻服务.md)。

## 二、持久状态与转换

| 持久状态 | 含义 | 下一次动作 |
| --- | --- | --- |
| `Confirmed` | 已知良好集已确认，无待试候选 | 选择已知良好集 |
| `Pending` | 候选已完整落盘，尚未试启动；保留原良好集 | 选择器校验候选，写入并持久化带唯一尝试身份的 `Trying`，再载入候选；每候选最多尝试三次 |
| `Trying` | 已记录候选尝试，尚未成功确认 | 当前运行到达确认点可提交 `Confirmed`；若再次进入选择器仍为该状态，则判定上次未确认并递减剩余次数：仍有剩余就再记一次尝试并载入候选，次数用尽才记录失败并选择原良好集 |
| `Failed` | 候选校验、试启动或健康检查失败 | 选择原良好集；只有显式发布新的 `Pending` 才会再次尝试候选 |

**每候选允许有限次尝试，默认三次。** 尝试次数由 `Pending` 记录带回，按[引导状态记录](Baleen/引导状态记录.md)的 `TriesRemaining` 在每次尝试前递减并持久化；递减的是“还可以试几次”，不改变“确认点必须是成功条件”。次数用尽是候选失败的判定之一，与校验失败、健康失败并列。

每份状态记录包含代次、状态、候选与良好集的标识和清单摘要、尝试身份及完整性校验。采用八槽环形的冗余记录：更新时不覆盖当前最新的有效槽位，读取时选择代次最高且完整有效的一份。**确认状态和良好集指针必须在同一份记录中提交**，不能先清标志、再另写版本指针。完整性校验用于检测写损，不能替代产物签名验证。记录格式、槽位布局与写入顺序见[引导状态记录](Baleen/引导状态记录.md)；集标识与清单摘要的来源见[内核集清单与签名](内核集清单与签名.md)。

`Trying` 未能可靠落盘时不得进入候选。确认写入失败时仍保留未确认状态并报告；下次启动按失败处理。**状态区域从未写过（空区域）不是记录损坏**：没有状态就按“没有试启动记录”处理，直接启动布局描述指定的缺省集（可写介质上验证通过后会把可记事实落成 `Confirmed` 记录，见[引导状态记录](Baleen/引导状态记录.md)第三节）；记录有写入痕迹但全部无法验证时不猜测目标集，进入受控恢复或停止。空与损坏的判定见[引导状态记录](Baleen/引导状态记录.md)第三节。实际存储后端必须提供满足上述语义的写入顺序与持久化能力，并通过掉电演练。

## 三、确认点

**确认点必须是成功条件。** Init 校验本次尝试身份，在必需模块及其硬依赖可用、必需驱动和服务就绪、健康探针通过、状态写入可用后提交确认。图形发行可要求会话就绪，无界面的发行可定义其他就绪条件。超时进入失败处理，不能把超时当作确认成功。卡死后需要 watchdog 或外部复位才能重新进入选择器；没有可靠复位能力时不承诺自动重启。

运行期确认写入与引导期选择必须使用同一状态存储后端和记录格式——格式即[引导状态记录](Baleen/引导状态记录.md)。只有该后端能在内核交权前可靠写入并持久化时，才启用试启动；否则直接启动指定的已确认镜像。

## 四、失败范围与处理

| 失败范围 | 处理 |
| --- | --- |
| 候选清单、镜像或必需能力失败 | 回退整个已知良好集；已执行不可逆初始化时必须先重启 |
| 可选模块在可撤销阶段失败 | 撤销其准备状态，标记它及全部直接、间接硬依赖者不可用；只有发行健康条件明确允许的降级才可确认 |
| 已知良好集也不能提供必需能力 | 报告并进入仍可运行的维护路径；进程、调度等条件不足时只能早期诊断或停机，不强行启动 Maintenance.exe |
| 系统卷、状态记录或恢复本身不可用 | 在可用通道报告并停止，或按明确的介质恢复策略处理，不反复切换失败集。其中**状态记录读失败或状态区域参数非法不是“无记录”**：按 `FATAL E-CORE-89` / `E-CORE-90`（UEFI 侧同号 `E-UEFI-89` / `E-UEFI-90`）报告并停止，不当成空记录继续启动 |

## 五、更新方式与边界

| 更新对象 | 机制 | 生效与暂停范围 |
| --- | --- | --- |
| 整个内核集 `.os` + `.osm` | 新旧集并存，Pending / Trying / Confirmed 状态机；`.os` 中的设备框架、驱动和文件系统一并更新 | 重启生效；失败回滚可能需要再次重启 |
| 外部 `.drv` | 满足契约时执行受控热替换，否则随重启切换 | 热替换期间暂停受影响设备请求；关键设备按专门策略处理 |
| `.exe` 与服务声明 | 版本并存、更新选择、重启相关进程或重新编排 | 内核通常无需重启，相关服务可能中断 |
| `.app` | 暂存、校验、发布选择记录，保留恢复文件 | 安装事务本身不决定载荷的生效时机 |

内核集不做热更新，也不做函数级热补丁。模块共享全局状态，替换可能涉及接口引用、调度、内存和对象状态迁移；本项目没有定义这类迁移协议，因此统一通过重启切换。内置驱动的阶段转换不更换代码；外部驱动的设备生命周期允许定义受控替换协议，但不提供任意内核态故障隔离保证。热替换前置条件与步骤见[模块与驱动装载](模块与驱动装载.md)。

## 六、保留与清理

**清理不是引导器的动作。** Baleen 对系统卷只有读操作，引导期只写引导状态区的裸块记录（见 [Baleen 引导器](Baleen/README.md) 第五节）；删旧集由 Update 侧（Updater / Installer）执行，且**只在确认提交成功之后**。

### 6.1 锚点集合

**三个版本必须始终在盘上。** 这是"清理完成后应当剩下什么"的**下限**，不是"任何时刻不得超过几个"的上限：

| 锚点 | 是什么 | 身份从哪来 |
| --- | --- | --- |
| 当前运行的集 | 本次从哪个集起来的 | `BootInfo` 的 `KernelSetBuildId`（试启动另有 `AttemptId`） |
| 上一个稳定版本（可配长度，默认 1） | 本次确认之前的那一个已知良好集 | 安装记录 |
| 出厂缺省集 | 介质组装时布局描述 `KernelPath` 指向的集 | `BootInfo` 的 `KernelPath` 推出的集目录（装载路径取自该集清单登记的 `.os`，布局路径须与它一致） |

**稳定历史是一份可配长度的列表，默认只留 1 个。** 默认行为就是“当前 + 上一个稳定 + 出厂集”；发行侧需要更长的回退余地（例如服务器）时把长度调到 2、3，机制不变——多出来的每一个都按同一条前置校验保护。长度只影响占用，不影响语义。

**出厂集在出厂介质上默认就被钉住。** “最终兜底”不该只是一句约定：Installer / 组装器把出厂集写进安装记录的钉住清单，清理逻辑即使被写坏也会被这一条挡住。出厂集本身是出厂前验过的那一版，默认钉住它不额外占空间。

**出厂集是唯一不会被更新推进改写的锚点**：发布候选只写 `Pending` 记录与集目录，不改布局描述，因此 `KernelPath` 始终指向它。回退链条是"当前运行 → 上一个稳定 → 出厂集"，出厂集也不可用时按第四节处理（报告并进入仍可运行的维护路径），而不是删掉它腾空间。

**重试次数的语义是“至少 N 次”，不是“恰好 N 次”。** 剩余次数记在状态记录里，每次试启动写一份 `Trying` 递减一次；那次写没落盘（掉电、写失败、只读介质）就等于这次尝试没有被记账，下次启动会再给一次机会。主流实现同样是这个口径（systemd-boot 把计数写成文件名的改写，掉电丢一次改名的结果一样是多试一次），追求“恰好 N 次”需要不可回退的计数器（TPM），与本项目“两条固件环境同一套语义”的设计冲突。记录里的 `TriesDone` 是这条口径的对账字段：它只增、不参与判定，现场用它就能看出“这一版实际被试过几次”——数值明显大于计划次数，说明中间发生过掉电或写失败。

**多于三个是常态，不是例外**：刚完成更新、尚未清理时，盘上必然有锚点加新候选加待清理的旧集；更新后最新版没能正常引导、需要修复时，回退后的运行集、**失败候选**与出厂集都在。失败候选要留到有人明确处理（判明原因或人工放弃）——它是唯一的现场，清掉之后只剩"坏了"这个结论。

**钉住**：安装记录里可以列出不许删的 `BuildId`（发行策略或人工维护用），它优先于一切清理规则。隐藏问题导致锚点自身不可信时，钉住的是最后一道保险。

### 6.2 删除的前置校验

任一条不成立就不删：

1. 状态记录的 `Confirmed` 已提交，且本次启动来自该集；
2. 三个锚点在盘上可验证（清单与摘要完整）；
3. 待删的不是：当前运行的集、`Pending` / `Trying` 候选、出厂集、被钉住的 `BuildId`、任何有失败痕迹的候选；
4. 安装记录可读且与盘上一致——**记录不可读或对不上就不清理**：宁留垃圾，不失回退能力。

**空间不够时**：发布候选之前先检查"候选 + 三个锚点"能否同时容纳；不够就**拒绝发布**并报告，不允许通过删锚点腾空间。

**清理要留记录**：每次删除写出删了哪些 `BuildId`、依据哪条状态与哪次确认。否则事后无法区分"这版坏了"和"这版被删了"——这两种情况对排障的意义完全相反。

### 6.3 安装记录

承载**稳定历史（可配长度，默认 1）**、**钉住的 `BuildId` 清单（出厂集默认在内）**与**清理历史**的持久位置，格式与落点随 Installer / Updater 阶段确定（[系统卷布局](Common/系统卷布局.md)第七节）。当前运行集与出厂集不需要它：分别由引导状态与布局描述给出。

安装记录不放进引导状态记录：那份记录是掉电敏感的八槽环形紧格式，`Confirmed` / `Candidate` 是引导选择器真正需要的事实；"上一个稳定"只有清理用得上，属保留策略。

安装包与安装事务的约定见[用户空间与常驻服务](用户空间与常驻服务.md)；后缀与载荷类别的对应关系见[后缀设计](后缀设计.md)。
