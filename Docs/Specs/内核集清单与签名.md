# 内核集清单与签名

**内核集是选版、试启动、确认与回滚的单位。** 一个内核集包含一颗 `LikesProgram.os`、同一发布线的若干 `.osm` 模块、模块加载列表与一份签名清单；`.os` 与模块的主版本必须一致，不接受跨发布线混装。清单是集合当前修订的身份与内容列表，并承载签名：引导选择器在装载之前先验证清单签名，再按清单给出的摘要逐个核对将要装载的产物。

`BuildId` 是 **`.os` 发布线身份**：由 `.os` 的内容摘要与集内路径派生，模块补丁不改变它，同一发布线的全部模块修订共用一个 `KernelSets/<BuildId>/` 目录。模块内容由**每个模块修订重签的清单**绑定：清单摘要（`ManifestDigest`）与 `SecurityVersion` 区分同一发布线内的不同模块修订，版本保留与回滚见[模块修订与更新](模块修订与更新.md)。`.os` 文件起点的 `BuildId` 字段就是这个发布线身份，`.osm` 不自带 `BuildId`。

清单的产物类型包含 `Modules.list`（内核侧书写的完整模块加载列表，与 `Manifest.mft` 同级，见 2.3）；引导闭包成员由 `Packages/Common/Contract/BootClosure.def` 单点声明，Baleen 从列表里挑出闭包成员预装，其余条目由内核挂卷后装载。`Modules.list`、当前模块文件、`.os` 与清单同属一个模块修订；跨主版本（`ModuleMajor` 与 `.osm` 的 `ModuleVersionMajor` 不等）一律拒绝装载，即使 ABI 范围碰巧匹配。

本文定义内核集的卷内落点、清单字节表、签名与信任锚、密钥轮换与撤销、防回滚版本与试启动身份传递。状态机的语义见[内核集更新与回滚](内核集更新与回滚.md)，状态的介质形态与读写协议见[引导状态记录](Baleen/引导状态记录.md)，校验对象（内核镜像文件自身的字节表）见[内核镜像数据](Baleen/内核镜像数据.md)。

## 一、内核集与卷内落点

| 项 | 约定 |
| --- | --- |
| 集构成 | 一个 `.os`（必需，恰好一条）、同一发布线的若干 `.osm`（`0..30` 条）、一份 `Modules.list` 与一份签名清单；`.osm` 的 `ModuleVersionMajor` 必须等于 `.os` 的 `ModuleMajor`。模块可以在发布线内按修订独立更新，但主版本不可混用 |
| 落点 | 系统卷内的 `/LikesProgram/System/KernelSets/<BuildId>/`，目录名是 `BuildId` 32 字节的小写十六进制（64 个字符） |
| 目录内容 | 清单固定叫 `Manifest.mft`，加载列表固定叫 `Modules.list`（两者同级）；模块文件在 `Modules/` 下，文件名带版本（`<名称>.<major>.<minor>.<patch>.osm`）；旧修订的 `Manifest.<rev>.mft` / `Modules.<rev>.list` 成对保留。产物按清单给出的相对路径存放（可以在子目录里），路径相对集目录、不得指向集目录之外；装载路径由集目录与清单登记的这条相对路径拼出，选择器不得按固定文件名另行拼接 |
| 缺省集 | 组装镜像时放入的那一集；[布局描述](Baleen/布局描述.md)的 `KernelPath` 指向缺省集目录里、清单登记的 `.os` 条目，形如 `/LikesProgram/System/KernelSets/<BuildId>/LikesProgram.os`，相对产物路径必须与清单条目逐字节一致（`E-CORE-85`） |
| 并存 | 候选集与已知良好集各占一个集目录，互不覆盖；同一份文件的落点唯一，更新不得原地覆盖回滚仍需要的版本 |
| 内存占用 | 每个集目录是一份完整拷贝，并存数量由发行策略限制（[内核集更新与回滚](内核集更新与回滚.md)要求至少保留候选与良好两集） |

**选版启用后（当前形态），选择器只接受 `KernelSets/<BuildId>/` 形态的落点。** 布局描述 `KernelPath` 必须指向缺省集目录里、清单登记的 `.os` 条目：选择器先按 `<集根>KernelSets/<64 位小写十六进制 BuildId>/<相对产物路径>` 拆出集目录，验证该集清单，再把装载路径拼成“集目录 + 验证通过的清单 `.os` 条目相对路径”，且布局路径里的相对产物路径必须与这条清单条目逐字节一致（否则 `E-CORE-85` / `E-UEFI-85`）。旧形态的单集扁平落点（`/LikesProgram/System/LikesProgram.os`）不再被接受：布局路径推不出集目录形态的启动一律拒绝（`E-CORE-84` / `E-UEFI-84`），**不存在任何未验证的直启路径**；布局描述的校验和只检测写损、不是认证，改布局描述不能跳过清单验签。目录名只是指针之一——状态记录里的集标识（[引导状态记录](Baleen/引导状态记录.md)）与目录名共同确定“启动哪一集”。这次迁移是[系统卷布局](Common/系统卷布局.md) 3.2 预留的“按 `BuildId` 分目录加当前指针”的落实。

## 二、清单字节表

清单是变长结构：固定头部、产物条目数组、尾部签名区。所有整数小端序，不允许编译器填充；偏移相对清单文件起点。保留字段必须写 0，读取方遇到非 0 保留字段按格式不符拒绝，不猜测语义。

| 偏移 | 字节数 | 字段 | 当前语义 | 填出方 |
| --- | --- | --- | --- | --- |
| `0x000` | 4 | `Magic` | 字节 `4C 50 4D 53`，即 `LPMS` | 生成器 |
| `0x004` | 2 | `Version` | 当前值 `1` | 生成器 |
| `0x006` | 2 | `HeaderBytes` | `0x40`，头部固定长度 | 生成器 |
| `0x008` | 4 | `Bytes` | 本结构总长度（头部、条目与签名区），不超过 `0x10000` | 生成器后由签名工具确认 |
| `0x00C` | 4 | `Flags` | `0`，当前不定义可选标志 | 生成器 |
| `0x010` | 32 | `BuildId` | `.os` 发布线身份：由 `.os` 内容摘要与集内路径派生，模块补丁不改变它；派生规则见 2.2，全零禁止 | 清单生成器（`MakeManifest`） |
| `0x030` | 8 | `SecurityVersion` | 单调安全版本：发行在发布时给定，只增不减；模块修订每次发布必须递增，防回滚比较的依据，语义见第六节 | 发行构建 |
| `0x038` | 2 | `ArtifactCount` | 产物条目数，取值 `2..32`；恰好一条 `Type=1`、恰好一条 `Type=3` | 生成器 |
| `0x03A` | 2 | `Reserved` | 全 0 | — |
| `0x03C` | 4 | `Reserved` | 全 0 | — |
| `0x040` | 变长 | `Artifacts` | `ArtifactCount` 条产物条目，逐条拼接，格式见下 | 生成器 |
| `Bytes-68` | 68 | `Signature` 区 | 签名算法、密钥编号与签名值，格式见下 | 签名工具 |

产物条目（每条 `44 + PathBytes` 字节）：

| 条目内偏移 | 字节数 | 字段 | 当前语义 |
| --- | --- | --- | --- |
| `0x00` | 1 | `Type` | `1` = `.os`，`2` = `.osm`，`3` = `Modules.list`；`0` 与 `4..255` 保留 |
| `0x01` | 2 | `PathBytes` | 路径字节数，取值 `1..255` |
| `0x03` | 1 | `Reserved` | 全 0；未定义语义 |
| `0x04` | 8 | `DataBytes` | 产物文件的实际字节数；不得为 `0`，零字节产物一律拒绝 |
| `0x0C` | 32 | `Digest` | 产物内容的 SHA-256 原始 32 字节摘要 |
| `0x2C` | `PathBytes` | `Path` | 相对集目录的路径，按[文件系统抽象与 VFS](Common/文件系统抽象与VFS.md)的统一路径语法（分量非空、不含 `.` 与 `..`、不以 `/` 开头），非 ASCII 字节按原字节使用 |

签名区（清单尾部固定 68 字节，偏移 `Bytes-68`）：

| 区偏移 | 字节数 | 字段 | 当前语义 | 填出方 |
| --- | --- | --- | --- | --- |
| `0x00` | 1 | `SignatureAlgorithm` | `1` = Ed25519（内部摘要 SHA-512）；其他值拒绝，无“不验证”值 | 签名工具 |
| `0x01` | 1 | `KeyId` | 签名密钥编号，取值 `1..255`；`0` 保留，不得使用 | 签名工具 |
| `0x02` | 2 | `Reserved` | 全 0 | — |
| `0x04` | 64 | `Signature` | Ed25519 签名值 | 签名工具 |

### 2.1 签名覆盖与清单身份摘要

设清单的原始字节串为 `M`、实际长度为 `Bytes`。签名值字段位于 `[Bytes-64, Bytes)`，计算签名与摘要时只将这 64 字节视为零：

```text
ManifestDigest = SHA-256(M[0x000 : Bytes-64] || 64 个零字节)
Signature      = Ed25519 签名(M[0x000 : Bytes-64] || 64 个零字节)
```

切片右端均不含。签名区里的算法与密钥编号、头部、全部条目与保留字节都在覆盖范围内，只有签名值本身按规则归零，避免自引用（与[内核镜像数据](Baleen/内核镜像数据.md)第三节对 `Digest` 的处理同一套办法）。**清单身份摘要** `ManifestDigest` 就是[引导状态记录](Baleen/引导状态记录.md)里 `ConfirmedManifestDigest` / `CandidateManifestDigest` 要存的值。

### 2.2 构建身份 `BuildId` 的派生

`BuildId` 是 **`.os` 发布线身份**：只由 `.os` 的内容摘要与 `.os` 的集内路径派生，模块补丁、模块版本与 `Modules.list` 都不参与。同一发布线内的全部模块修订共用同一个 `BuildId` 与集目录；模块内容由每个修订重签的清单摘要绑定，修订身份见[模块修订与更新](模块修订与更新.md)。

设 `.os` 文件字节串为 `F_os`、实际长度为 `ImageBytes`（文件长度必须与数据字段一致），`[0x28,0x48)` 是 `BuildId` 字段、`[0x48,0x68)` 是 `Digest` 字段：

```text
C_os = SHA-256(F_os[0x00:0x28) || 32 个零字节 || 32 个零字节 || F_os[0x68:ImageBytes))
```

切片右端均不含。`C_os` 把 `BuildId` 与 `Digest` 两段都按零代入，因此对最终 `.os` 与原型 `.os`（两段全零）算出的值相同；`.os` 镜像数据里的 `ModuleMajor`（偏移 `0x68`）也在覆盖范围内，所以发布线变化必然改变 `C_os`。设 `osPath` 是 `.os` 条目相对集目录的路径，路径按原始字节比较：

```text
BuildId = SHA-256(
    "LPKSID02"                                    // 8 字节 ASCII 域分离标记，含派生算法版本
    || u16le(osPathBytes) || osPath
    || C_os[32]
)
```

约束与说明：

- **为什么不再包含模块**：模块补丁必须留在同一个 `KernelSets/<BuildId>/` 目录里才能“独立更新、重启生效”；若 `.osm` 摘要参与 `BuildId`，换一个模块就换目录，版本保留也只能退化成按目录堆叠。模块内容改由清单摘要级联绑定，每个模块修订重签清单，用 `ManifestDigest` 与 `SecurityVersion` 区分修订。
- **`BuildId` 与“同集”的关系**：同 `BuildId` 现在表示“同一 `.os` 发布线”，不等于“同一组模块字节”；同一目录内允许存在多个模块修订的保留文件，但一次启动只装载一个修订。修订选择与回滚见[模块修订与更新](模块修订与更新.md)。
- **域分离**：`"LPKSID02"` 把发布线身份与镜像摘要、清单身份摘要、签名等其它 SHA-256 用途隔开；派生算法变化时改这段标记，不再产旧标记的新集。旧 `LPKSID01` 已退役，历史记录见[退役项清单](../Test/退役项清单.md)。
- **规范编码**：所有整数小端、定宽；路径按原始字节比较（不规范化大小写、不做 Unicode 折叠）。
- **不参与派生的字段**：`SecurityVersion`、`ModuleRevision`、模块文件、`Modules.list`、清单签名、构建时间、构建路径与配置文本。`SecurityVersion` 与 `BuildId` 正交：发布线不变、只发模块补丁时 `BuildId` 不变、`SecurityVersion` 必须递增。
- **文本形态**：64 个小写十六进制字符，用作 `KernelSets/<BuildId>/` 目录名、`BootInfo.KernelSetBuildId` 与构建输出；比较一律按字节。
- **填充顺序**：`MakeManifest` 先按上式算出 `BuildId` 并写入 `.os` 的 `BuildId` 字段，再按[内核镜像数据](Baleen/内核镜像数据.md)第三节计算并写入 `Digest`。`C_os` 在填充前后一致，因此 `--verify` 可以随时从最终 `.os` 重算。
- **可复现**：同一 `.os` 产物字节与同一集内路径必须产出同一个 `BuildId`；构建不得把时间戳或本机路径带进参与派生的字节。

### 2.3 模块加载列表与产物类型

清单的产物条目按 `Type` 分三类，`ArtifactCount` 取值 `2..32`：

| `Type` | 含义 | 条目约束 |
| --- | --- | --- |
| `1` | `.os` | 恰好一条；路径为集内相对路径 |
| `2` | `.osm` | `0..30` 条；路径必须在 `Modules/` 下、文件名带版本；同一路径只能出现一次 |
| `3` | `Modules.list` | 恰好一条；路径固定为 `Modules.list`（与 `Manifest.mft` 同级） |

- **`Modules.list` 是内核侧书写的完整模块加载列表**：条目集合与本节 `Type=2` 条目集合逐一相等，顺序由内核侧决定（构建侧先闭包顺序、再其余模块）。Baleen 只消费其中命中引导闭包期望集的成员，其余条目留给内核挂卷后装载；它是配置，不是完整性根——清单以 `Type=3` 条目登记它的字节数与 SHA-256，签名覆盖清单，改列表必须重新生成并重签清单。
- **引导闭包成员由 `BootClosure.def` 声明**：模块补丁更新列表时不必同时维护“清单标志 + 列表”两处（旧 `ArtifactFlags.BootClosure` 已退役，历史记录见[退役项清单](../Test/退役项清单.md)）。列表的固定头与 `module <相对路径>` 条目语法、容量上限、集合口径与排序规则见[模块修订与更新](模块修订与更新.md)第四节；条目路径与本节 `Type=2` 条目的 `Path` 逐字节对应，闭包成员按「路径主名派生 `ModuleId` → 命中期望集」识别。
- **模块主版本硬门**：`Modules.list` 的 `major` 与每个 `.osm` 的 `ModuleVersionMajor` 都必须等于 `.os` 的 `ModuleMajor`；不等即拒绝，不进入 ABI/接口/依赖判定。完整规则见[模块修订与更新](模块修订与更新.md)第三节。
- 条目内偏移 `0x03` 的字节是保留字节，必须为 0；未定义类型或未定义位一律拒绝，不猜测语义。

约束至少包括：`Version` 与 `HeaderBytes` 固定；`Bytes` 与文件实际长度一致且不小于 `0x40 + 68`；`ArtifactCount` 在 `2..32` 内且条目区恰好放得下；`Type=1` 恰好一条、`Type=3` 恰好一条且路径为 `Modules.list`；路径非空、互不重复、不含 NUL 字节、不越出集目录；`DataBytes` 不为 `0`；`SignatureAlgorithm` 与 `KeyId` 合法；头部 `Flags`、条目保留字节与全部保留字段为 0。**路径按字节比较与去重**：集目录加 `/` 加清单相对路径的组合长度不得超过 510 字节（引导器按 512 字节缓冲实现，含结尾空字符；超限按清单格式错误拒绝），NUL 会在 C 字符串接口处截断路径，因此一律拒绝。所有长度加法先检查溢出。

## 三、验证顺序

引导选择器（BaleenCore / UEFI）在装载任何集之前按以下顺序验证，任一不通过即报告原因，并按“候选失败回退良好集 / 良好集失败进维护路径”处理（[内核集更新与回滚](内核集更新与回滚.md)第四节）：

1. **定位清单**：按集标识推导集目录（`/LikesProgram/System/KernelSets/<BuildId>/Manifest.mft`）；缺省集的集标识从布局描述 `KernelPath` 的集目录段拆出，形态不符即拒绝（`E-CORE-84` / `E-UEFI-84`），只读介质同样适用；
2. **结构与保留字段**：读清单，核对 `Magic`、`Version`、`HeaderBytes`、`Bytes`、`Flags`、条目区的类型/路径/保留字节与全部保留字段；
3. **算身份摘要**：按 2.1 计算 `ManifestDigest`；
4. **验签**：先按有效吊销事实判定——`KeyId` 在吊销位图里 → 拒绝并报告（`E-CORE-74`）；再按 `KeyId` 查信任锚表（第四节），用对应的 Ed25519 公钥验证签名；密钥不存在（`E-CORE-63`）或签名不通过（`E-CORE-64`）→ 拒绝。吊销先于查表：被吊销是显式策略结论，比“不在表里”更能说明现场；
5. **集身份一致**：清单 `BuildId` 必须与所选集标识（目录名、状态记录里的候选/良好标识）一致；
6. **防回滚**：清单 `SecurityVersion` 必须不低于[引导状态记录](Baleen/引导状态记录.md)里的 `SeenSecurityVersion`、引导器内嵌的最低允许版本（第六节）与吊销记录给出的最低允许版本（5.2）；
7. **逐产物**：按条目核对路径合法、文件存在、`DataBytes` 与实际长度一致、`Digest` 与重算的 SHA-256 一致；`Type=3` 的 `Modules.list` 还要核对固定路径与文本结构，见[模块修订与更新](模块修订与更新.md)第四节；
8. **集内一致与主版本硬门**：`.os` 文件起点的[内核镜像数据](Baleen/内核镜像数据.md)里的 `BuildId` 必须等于清单 `BuildId`，`BootInfoVersion` 必须是本侧能构造的版本；`Modules.list` 的 `major` 与每个 `.osm` 的 `ModuleVersionMajor` 都必须等于 `.os` 的 `ModuleMajor`，不等即拒绝（`E-CORE-95` / `E-UEFI-95`）。主版本门先于 ABI、接口与依赖判定，**即使范围碰巧匹配也不放行**；
9. **装载路径取自清单**：选择器把集目录与验证通过的清单里 `Type=1` 条目的相对路径拼成装载路径，不得按固定文件名（如 `LikesProgram.os`）另行拼接；缺省集还要求布局描述 `KernelPath` 与这条装载路径逐字节一致，不一致即拒绝（`E-CORE-85` / `E-UEFI-85`）——布局路径只用来定位缺省集，不是装载路径的来源；
10. **装载前的镜像身份**：读取的内核镜像里的 32 字节 `BuildId` 必须等于所选集标识，不符即拒绝（`E-CORE-65`）——路径来自已验证清单、镜像自述身份再核对一次，与第 8、9 步形成纵深，挡住“验 A 装 B”；
11. 全部通过后装载。内核镜像数据里的 `Digest` 自检仍按原顺序执行——它检测非预期字节变化，**签名才是执行前认证**。

**引导闭包预装。** 验证通过后，选择器装载 `.os`，并按 `Modules.list` 把其中命中引导闭包期望集的 `.osm` 一并读入内存（列表里的运行期条目不在引导期装载）：列表本身已由清单 `Type=3` 条目与签名覆盖，每个文件必须存在、实际长度等于清单 `DataBytes`、SHA-256 等于清单 `Digest`；读入位置必须在低 4GiB 的可用内存里、不越过内存图上限、不与内核装载跨度或引导器自身重叠。预装失败按所选集失败处理（候选回退已知良好集、缺省集终止启动），**不交接半套**：清单副本、模块加载列表、预装模块记录与 `BootInfo` 一起交给内核，字段与记录格式见 [Baleen 引导器](Baleen/README.md) 6.2。选择器不解析 `.osm` 容器内部、不做重定位、不执行模块——那属于内核的模块装载器；每个模块只核对最小读取面与主版本门，口径见[内核模块容器](内核模块容器.md) 5.1。

**验证的是清单，覆盖的是全部产物。** 清单自己带签名，产物靠清单里的摘要级联；不逐个文件签名。这样一次验签就把“这一集的完整内容”绑定在一起，防止把不同构建的产物混装——这正是 `BuildId` 检查之外签名要补的部分，也是业界（AVB 的 vbmeta、U-Boot 的 signed configuration、TF-A 的 content certificate）的一致做法。

## 四、信任锚

| 项 | 约定 |
| --- | --- |
| 形态 | 引导器内嵌的公钥表：条目 = `KeyId`（1 字节） + Ed25519 公钥（32 字节）；表最多 4 条：轮换窗口两把并存，另留吊销授权与轮换余量（5.1 的签名者规则要求设备上预先装有一把未被吊销的密钥） |
| 位置 | 公钥表是 BaleenCore 镜像（及 UEFI 侧 `BOOTX64.EFI`）的一部分，随引导器一起构建、只读；两侧共用同一份表的定义 |
| 变更 | 换锚 = 重新构建并更新引导器；清单里不存在任何能改变锚的材料，清单只带 `KeyId` |
| 自证禁止 | 清单里的公钥（若将来的格式加入）不构成信任，只有引导器内嵌的表是信任锚 |
| 与 Secure Boot 的关系 | UEFI Secure Boot 验证的是“固件愿意执行引导器”，本机制验证的是“引导器愿意装载内核集”，两条链独立、不能互相替代（[Baleen 引导器](Baleen/README.md) 3.3） |

**威胁模型，如实写明**：本机制防的是内核集被替换、混装与降级（清单签名 + 摘要级联 + `BuildId` + `SecurityVersion`）。它不防引导器本身被替换——BIOS 路径的引导区在可写介质上可被改写，那是固件信任链（Secure Boot、固件写保护）的职责。信任锚的可信性以“引导器自身完整”为前提。**布局描述本身只有校验和、不是认证**，但选择器不拿它作为跳过验签的依据：布局路径只用来定位缺省集并核对清单登记的产物路径，形态不合规或与清单不符一律拒绝（`E-CORE-84` / `E-CORE-85`），装载路径最终取自验证通过的清单。

## 五、密钥轮换与撤销

**轮换按“先更新引导器、后换签名密钥”的顺序，一次跨两个发布周期：**

1. 发布含新旧两把公钥的引导器更新（锚表容量 2 条就是为这个窗口留的）；旧引导器不认识新 `KeyId`，此时清单仍用旧密钥签；
2. 确认设备侧已更新后，发行侧改用新密钥签清单；
3. 下一次引导器更新移除旧公钥，`KeyId` 回收。

**开发期这条顺序有可复现的落地形态**：旧公钥写在进版本库的保留锚条目里（`Packages/Baleen/Core/Anchors/Retained.txt`），当前密钥来自仓库外的种子；`Tools/Bin/MakeKeys --anchors` 把两者合并生成 `Out/TrustAnchors.cpp`，条目按 `KeyId` 升序，同一编号出现两次直接报错，条目数超容量由生成源里的 `static_assert` 拦下。打开轮换窗口 = 把旧公钥追加进保留锚条目并重建引导器，关闭 = 删掉对应行。两把公钥并存时的查找与按 `KeyId` 选钥验签由 [CheckCrypto](../../Tools/Test/CheckCrypto/README.md) 的用例覆盖，生成器输出的确定性与超容量拒绝也在那里。

**撤销有三种粒度。前两种固化在引导器里、随引导器更新离线分发；第三种由签名吊销记录承载，不必更新引导器：**

| 粒度 | 做法 | 适用 |
| --- | --- | --- |
| 吊销密钥（固化） | 移除公钥条目；该 `KeyId` 签的清单一律拒绝 | 密钥泄露，且设备能更新引导器 |
| 吊销版本（固化） | 抬高引导器内嵌的“最低允许 `SecurityVersion`”，低于下限的清单一律拒绝 | 某一批构建发现缺陷，不需要动密钥 |
| 吊销密钥与版本（记录） | 系统卷内一份签名的吊销记录，选择器读它、验签并按单调并集应用（5.1、5.2） | 不便更新引导器的设备：离线投递一份记录即可生效 |

吊销版本不要求改源码：`BaleenCore` 的内嵌下限由构建参数 `SECURITY_FLOOR` 写出（`make -C Packages/Baleen/Core SECURITY_FLOOR=<n>`，默认 `0` 表示不吊销任何世代），值随引导器镜像一起发布。下限只对重新构建并部署的那一份引导器生效。

### 5.1 签名吊销记录

**落点**：系统卷内固定路径 `/LikesProgram/System/Revocation.rvk`。**只有文件不存在（打开返回 `NotFound`）表示没有吊销记录**，是正常形态、不报错；存储层打不开或读不了不是“没有记录”，与长度、结构、签名者规则或签名不成立一样按不可用处理（5.2 第 4 条）。记录是**离线投递**的：由发行侧签名后随安装包、U 盘或整盘镜像送到设备；设备端不联网、不访问服务器——**验证永远离线，联网只影响投递快慢**，所以断网设备与联网设备在这里没有区别。

**字节表**（总长 `0x84`；所有整数小端序，不允许编译器填充；保留字段必须写 0，遇到非 0 保留字段按格式不符拒绝）：

| 偏移 | 字节数 | 字段 | 当前语义 |
| --- | --- | --- | --- |
| `0x000` | 4 | `Magic` | 字节 `4C 50 52 56`，即 `LPRV` |
| `0x004` | 2 | `Version` | 当前值 `1` |
| `0x006` | 2 | `HeaderBytes` | `0x40` |
| `0x008` | 4 | `Bytes` | `0x84`：本格式没有变长部分，长度不符一律拒绝 |
| `0x00C` | 4 | `Flags` | `0`，当前不定义可选标志 |
| `0x010` | 8 | `Epoch` | 吊销纪元，**非零**；只增不减，判据见 5.2 |
| `0x018` | 8 | `MinSecurityVersion` | 记录给出的最低允许清单 `SecurityVersion` |
| `0x020` | 32 | `RevokedKeyMask` | 已吊销签名密钥位图：`KeyId k` 对应第 `k-1` 位、字节 `(k-1)/8` 内的第 `(k-1)%8` 位；`KeyId 0` 是保留值，不构成吊销 |
| `0x040` | 68 | `Signature` 区 | 与清单 2.1 同构：算法 1 + 密钥编号 1 + 保留 2 + 签名值 64 |

**签名覆盖与 2.1 同一套办法**：签名值 64 字节视作零，`Ed25519` 对整份 `0x84` 字节签名；算法与密钥编号在覆盖范围内，签名之后记录的任何字节变化都必须重新生成并重签。

**签名者规则**：签名者的 `KeyId` 必须命中信任锚表（第四节），且**不得出现在本记录自己的 `RevokedKeyMask` 里**——自吊销的记录不成立，一律拒绝。由此得到一条前提：**“密钥泄露后仍能吊销它”要求设备上已经装有一把当时未被吊销的可信密钥**，也就是锚表至少要在轮换窗口里预先装入第二把——这是容量放到 4 条的理由，也是生成器在锚表少于两条时给出警告（不失败）的理由：警告指向的正是“把第二把公钥放进保留锚条目”这个动作。

**生成工具**：[MakeRevocation](../../Tools/Build/MakeRevocation/README.md) 生成并签名；同一组输入产出同样的字节，结构检查用的是引导侧同一份实现。

### 5.2 应用与单调纪元

1. **有效吊销事实** = 并集（系统卷里的吊销记录，[引导状态记录](Baleen/引导状态记录.md)里持久化的撤销事实）：`Epoch` 取较大者、`MinSecurityVersion` 取较大者、位图按位或；
2. 应用在第三节第 4、6 步：位图里有该清单的 `KeyId` → `E-CORE-74`；`SecurityVersion` 低于记录下限 → `E-CORE-66`；
3. **单调**：选择器把并集写回状态记录，只增不减。记录被删除、损坏或被回滚成旧纪元，都不会解除已经落地的吊销——签发记录的文件在系统卷上，但**吊销事实的落点在系统卷之外**；
4. **只有 `NotFound` 是正常缺失，记录不可用只报 `WARN`**（`E-CORE-75` / `E-UEFI-75`）：文件不存在按“没有记录”继续、不报错；存储层打不开或读不了，以及长度、结构、签名者规则或签名不成立，一律按不可用处理——忽略该记录、报 `WARN` 后按已持久化的吊销事实继续，不 `FATAL`。理由：记录只能增加限制，忽略它不给攻击者任何收益，而停机让“写坏一个文件”就能拒绝服务；
5. **固化在引导器里的那两种粒度没有变**：吊销条目与抬高内嵌下限的生效点仍是一次可信的引导器更新；
6. **边界，如实写明**：持久事实放在可写介质上的状态记录里，没有防篡改存储，能改写介质的攻击者同样能回滚它——与[引导状态记录](Baleen/引导状态记录.md)第六节是同一条“尽力而为”，本节不把它说得更硬；
7. **不存在任何未验证的回退**：布局路径推不出集目录形态（包括旧扁平落点）以 `E-CORE-84` / `E-UEFI-84` 拒绝，布局路径里的相对产物路径与缺省集清单登记的 `.os` 条目不一致以 `E-CORE-85` / `E-UEFI-85` 拒绝，因此改布局描述不能跳过清单验签——布局描述只有校验和、不是认证（[布局描述](Baleen/布局描述.md)第三节）；吊销判定对所有被装载的集一律适用。

**发布侧的落地形态**（工具已就位，流程按此执行）：

1. 在一台**离线机器**上生成发布种子：`Tools/Bin/MakeKeys --out <发布密钥目录>`（种子权限 600，不进仓库、不进镜像）；签发机器不长期保存种子；
2. 公钥进引导器：把 `<KeyId> <公钥 64 位十六进制>` 追加进进版本库的保留锚条目 `Packages/Baleen/Core/Anchors/Retained.txt`（轮换窗口用），或把该密钥目录当作当前密钥：构建时 `make KEYS_DIR=<发布密钥目录>`，锚表随引导器一起构建；同一 `KeyId` 出现两次由生成器拒绝，超容量由生成源的 `static_assert` 拦下；
3. 签清单：用同一把密钥签内核集清单（`MakeManifest` + `SignManifest --key-id <n>`，签名覆盖见 2.1）；
4. 审计：发布记录里留 `BuildId`、`SecurityVersion`、`KeyId`、清单身份摘要（`ManifestDigest`）与签发时间；出问题时可据此定位是哪一把密钥、哪一个世代签的；
5. 撤销：密钥泄露 → 从锚表移除该条目并重建引导器；某一批构建有缺陷 → 抬高 `SECURITY_FLOOR` 并重建引导器（第五节）；**不便更新引导器的设备** → 用一把未被吊销的密钥生成签名吊销记录（`MakeRevocation --key <种子> --key-id <n> --epoch <n> [--min-security-version <n>] [--revoke-key-id <n>] --out Revocation.rvk`），把 `Revocation.rvk` 放进系统卷的 `/LikesProgram/System/`（5.1、5.2）；

**公钥进仓库、私钥永不进仓库**：与 MakeKeys 的开发期约定同一条规则；锚表是发布产物的一部分，保留锚条目是它的版本化输入。

## 六、防回滚

`SecurityVersion` 是发行侧维护的单调版本号（u64），在新集发布时给定，只增不减；它表达“这一集的发行世代”，与 `BuildId`（构建级身份）正交：内容变了 `BuildId` 必变，安全世代不变时 `SecurityVersion` 可以不变。

设备侧的比较规则（“尽力而为”，记录与其限制见[引导状态记录](Baleen/引导状态记录.md)第六节）：

1. 清单 `SecurityVersion` 低于引导器内嵌的最低允许版本 → 拒绝，报告 `FATAL` 并停止；
2. 清单 `SecurityVersion` 低于设备已见最高（`SeenSecurityVersion`）→ 拒绝，报告 `FATAL` 并停止，等待人工接受（入口见[引导状态记录](Baleen/引导状态记录.md)第八节）；
3. 不低于 → 正常装载；若高于已见最高，按[引导状态记录](Baleen/引导状态记录.md)第四节更新记录；
4. 无状态记录、记录损坏或介质只读 → 只做第 1 条检查。

第 2 条阻挡的是“拿旧镜像重放”：旧镜像即使签名有效，也不该在见过更高世代之后重新上机。没有防篡改存储时它只是尽力而为——攻击者能清除记录，这一限制在[引导状态记录](Baleen/引导状态记录.md)第六节有完整声明，此处不重复粉饰。

## 七、试启动身份与 `BootInfo`

**引导选择器在尝试候选时，把写入 `Trying` 记录的 `Generation` 值作为本次尝试身份**（[引导状态记录](Baleen/引导状态记录.md)第二节的 `AttemptId`），并随 `BootInfo` 交给内核，由内核转交给 Init。`BootInfo` 增加两个字段：

| 字段 | 字节数 | 语义 |
| --- | --- | --- |
| `KernelSetBuildId` | 32 | 本次启动的内核集标识；全零表示“未提供”（占位件或第三方引导来源） |
| `AttemptId` | 8 | 本次尝试身份；`0` 表示本次不是试启动（直接启动已知良好集或缺省集） |

**`BootInfo` 的接口版本保持 `1`。** 该接口尚未发布，本次属设计调整：两个字段直接加进现有结构，尺寸随字段增加，[内核镜像数据](Baleen/内核镜像数据.md)的 `BootInfoVersion` 与内核侧核对同步保持 `1`；首次发布之后的字段调整才按[ABI 兼容与外部契约](Common/ABI兼容与外部契约.md)第二节的追加规则使用新接口版本。内核只核对尺寸与版本、把两个字段原样转交，不解读选版语义。

**模块修订身份。** `KernelSetBuildId` 只标识 `.os` 发布线；同一发布线内切换模块修订时，`BuildId` 不变，修订身份由清单身份摘要 `ManifestDigest` 与 `Modules.list` 的 `ModuleRevision` 共同确定。状态记录选中修订、回退旧修订时以这组事实为准，见[模块修订与更新](模块修订与更新.md)与[引导状态记录](Baleen/引导状态记录.md)。

同一套“只追加、不移动、不抬版本”的追加规则随后也用在了启动来源字段上，见 [Baleen 引导器](Baleen/README.md) 6.1。

**内核集交接包。** `BootInfo` 还携带本次启动的清单副本、`Modules.list` 副本与预装模块记录：清单副本与列表都是选择器验证过的那份字节，预装模块记录逐条给出模块文件字节的物理地址、长度与清单产物条目下标。字段偏移、记录布局与“内核必须先核对再执行任何模块”的要求见 [Baleen 引导器](Baleen/README.md) 6.2；内核侧的核对顺序、主版本硬门、失败处理与引导闭包完整性判据见[模块修订与更新](模块修订与更新.md)与[内核模块容器](内核模块容器.md)。字段占用 `BootInfo` 的既有保留区，接口版本保持 `1`；引导器预装（M2）与内核入口核对（M3）均已实现。

Init 到达确认点时按“比较再提交”写确认记录（[引导状态记录](Baleen/引导状态记录.md)第四节）：当前记录仍是 `Trying` 且 `Generation` 等于收到的 `AttemptId`，才写入 `Confirmed`；不成立就拒绝写入并报告，本次确认不成立。这防止一次迟到的确认覆盖掉引导器已经推进的新状态。

Updater 的发布路径与之对称：主版本升级时，候选集全部文件落进 `KernelSets/<BuildId>/`、清单验签与依赖检查通过之后，最后写 `Pending` 记录（`TriesRemaining` 取默认 `3`）；同一发布线内的模块修订按[模块修订与更新](模块修订与更新.md)第六节发布新的 `Manifest.mft`/`Modules.list` 并把修订身份写入状态，不换集目录。

## 八、构建与签名流程

| 环节 | 职责 |
| --- | --- |
| 构建系统 | 产出 `.os` 原型（`BuildId` 与 `Digest` 全零，镜像数据里 `ModuleMajor` 非零）与同一发布线的 `.osm`；把产物清单与集内路径交给 `MakeManifest`；不自行派生 `BuildId` |
| 清单与身份工具（`MakeManifest`） | 按 2.2 派生 `BuildId`、写入最终 `.os` 的 `BuildId` 与 `Digest`；生成 `Modules.list`（主版本取自 `.os`、修订号来自构建参数）并作为 `Type=3` 条目登记，生成清单；`--verify` 从最终产物重算并核对清单与列表主版本。清单字节必须确定性，同一份输入产出同样的清单与 `BuildId` |
| 打包校验工具（`PackImage`） | 对内核镜像只校验、不派生：结构、字段、`ModuleMajor` 非零与已分配身份下的 `Digest`；Baleen 镜像的派生/填充规则不变 |
| 组装器 | 先由 `MakeManifest` 在暂存目录生成最终 `.os`、`Modules.list` 与清单，再从 `BuildId` 文本得到集目录名，把缺省集放进 `KernelSets/<BuildId>/`；布局描述 `KernelPath` 指向缺省集目录里清单登记的 `.os` 条目（相对产物路径与清单逐字节一致）；不生成也不校验签名之外的内容 |
| Updater（运行期） | 模块补丁按[模块修订与更新](模块修订与更新.md)暂存新模块文件、新清单与新列表，检查签名/防回滚/主版本门/依赖，完整落盘后发布 `Pending` 记录；主版本升级按整集更新处理 |
| Init（运行期） | 到达确认点按 `AttemptId` 比较后提交 `Confirmed`；模块修订切换同样在确认点提交 |

工具对照见[用户空间与常驻服务](用户空间与常驻服务.md)第五节：签名与信任工具负责“密钥、信任锚、签名和撤销规则”，内核集与启动状态工具负责“清单校验、镜像槽位、选择记录、尝试身份和良好集管理”。签名私钥的操作规范（离线保管、签发流程）与工具的命令形态随实现阶段确定。
