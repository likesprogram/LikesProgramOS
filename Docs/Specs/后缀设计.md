# 后缀设计

本文定义本系统容器**后缀的语义**：后缀是什么、为什么需要它、每个后缀取自哪个词、对应哪类载荷、在从构建到退役的全程里各起什么作用，以及它不承担什么。

**本文是后缀的正式定义。** 根 [README.md](../../README.md) 只在文档索引里列出本文，不再转述其结论；两者不一致时以本文为准，并回头修正 README。

**容器内部的东西不在本文范围。** 文件头与魔数取值、版本字段、段映射与重定位、导入导出表、摘要与签名算法、包内清单格式、装载与热替换的步骤细节，全部归「详细内容」规格——另立文档，当前先不写。本文提到它们时只说明后缀在其中的位置，不给定义。

## 一、后缀是什么

- **容器类别的可读标签**，与容器元数据里的 `kind` 一一对应：看到后缀就知道这类载荷装的是什么、该由谁装载。
- **给人读的**：文档、目录列表、构建产物、介质内容用同一套后缀表达类别，讨论和排查时不必先解包。
- **构建期赋予的**：由容器打包器按产物类别写入并校验，不是事后改名得来的。

**每个后缀都要能说出「取自」哪个英语技术词**，不造无意义的字母组合。据此后缀分三类：

| 类别 | 成员 | 说明 |
|---|---|---|
| 可装载容器（本项目设计） | `.os`、`.osm`、`.drv`、`.exe`、`.dso`、`.app` | 有 `kind`，由装载器按类别处理 |
| 非装载载荷（本项目设计） | `.arc`、`.svc`、`.res`、`.sym` | 没有 `kind`，只被工具或程序读取，不被装载器处理 |
| 外部约定 | `.bin`、`.efi` | 名字由固件与引导协议决定，**不是本项目设计**，见第六节 |
| 非容器形态 | 源码、SDK 发布的库、契约层、构建期工具与中间产物 | **不是后缀类别**：源码沿用工具链约定，SDK 的库复用 `.dso` / `.arc`，工具与中间产物不进入交付体系，见 5.11 |

## 二、后缀不是什么

| 不是 | 说明 |
|---|---|
| 不是格式判据 | 格式由容器自身的文件头等内部信息判定；只看后缀会误判 |
| 不是安全边界 | 不提供任何隔离或信任保证；来源可信与否由签名与信任锚判定 |
| 不是兼容承诺 | 共用后缀不表示兼容其他系统的同名格式，见第八节 |
| 不是版本或架构标记 | 版本与发行不写进文件名，架构不体现在后缀里，见第九节 |

## 三、后缀的全程

后缀在六个阶段各起一次作用，每个阶段都不允许它代替后续检查：

| 阶段 | 后缀的作用 | 不能代替什么 |
|---|---|---|
| 构建 | 打包器按产物类别赋予后缀与 `kind`，并校验两者一致 | 不能代替对载荷内容的校验 |
| 分发 | 传输、目录存放、安装包里按后缀区分载荷类别 | 不能代替摘要与签名检查 |
| 识别 | 作为初筛，让人和工具先判断该找哪类容器 | 不能代替读容器自身的识别信息 |
| 装载 | 由后缀对应的类别决定交给哪个装载器 | 不能代替 `kind`、依赖与清单校验 |
| 生效与更新 | 由类别决定生效方式：重启切换、受控热替换、重启进程、安装事务 | 不能代替停用协议与恢复条件 |
| 退役 | 多版本并存存放，靠目录与清单区分旧版 | 不能靠改后缀标记版本或回滚 |

非装载载荷只走「构建」和「分发」两段：它们不被装载器读取，不进入识别、装载和生效阶段，其完整性随所属包或所属二进制的清单校验。

## 四、后缀总表

### 4.1 可装载容器

| 后缀 | 取自 | `kind` | 含义 | 谁载入 | 特权级 | 生效方式 |
|---|---|---|---|---|---|---|
| `.os` | Operating System | `core` | 内核本体 | 自家引导器 [Baleen](Baleen/README.md)；第三方需自写中间层 | `ring 0` | 随内核集重启切换 |
| `.osm` | Operating System Module | `module` | 外置内核模块 | `.os` 的模块装载器 | `ring 0` | 随内核集重启切换 |
| `.drv` | driver | `driver` | 外部设备驱动 | `.os` 内的 DriverLoader | `ring 0` | 满足协议时热替换，否则重启升级 |
| `.exe` | executable | `user` | 用户程序与常驻服务 | Init 或 Session | `ring 3` | 切换文件版本并重启进程 |
| `.dso` | Dynamic Shared Object | `library` | 用户态动态库 | 用户态装载器 | `ring 3` | 切换文件版本并重启使用它的进程 |
| `.app` | application package | `pkg` | 安装包 | Installer | — | 安装事务，生效方式由载荷决定 |

### 4.2 非装载载荷

| 后缀 | 取自 | 含义 | 谁读取 | 生效方式 |
|---|---|---|---|---|
| `.arc` | archive | 用户态静态库：目标代码归档 | 链接器（构建期） | 随使用它的程序重新构建 |
| `.svc` | service | 服务声明 | Init 与服务编排方 | 随所属服务的版本切换 |
| `.res` | resource | 资源与数据：图标、字体、主题、界面文本等 | 使用它的程序或服务 | 随使用它的程序 |
| `.sym` | symbol | 调试符号 | 诊断工具与自检 | 随对应二进制的版本并存 |

### 4.3 外部约定

| 后缀 | 取自 | 含义 | 约束来源 |
|---|---|---|---|
| `.bin` | binary | 引导链裸镜像 | 通行叫法；BIOS 与 El Torito 不检查扩展名 |
| `.efi` | Extensible Firmware Interface | 固件应用镜像 | UEFI 固件：只加载 PE/COFF，并按固定路径查找 |

### 4.4 非容器形态（不是后缀类别）

| 形态 | 后缀或形式 | 说明 |
|---|---|---|
| 源码与头文件 | `.cpp` / `.hpp` | 工具链约定的源码类型；没有 `kind`、不验签、不装载 |
| SDK 发布的库 | `.dso` / `.arc` | **复用库后缀，不新增**：SDK 给的动态库就是 `.dso`，静态库就是 `.arc` |
| 契约层 | 源码树内：契约头、Tools工具校验 与汇编常量 | 随整集构建，不单独发布 |
| 构建期工具 | 宿主形态 | 跑在宿主上、用宿主的格式，不是本系统的容器 |
| 构建中间产物 | 目标文件等 | 不进入交付体系，不定义后缀 |

## 五、逐个后缀的语义

### 5.1 `.os` — 内核本体

**取自 Operating System**：这份镜像就是操作系统本体，不是它的附属物。

一份 `.os` 就是一次内核交权要载入的那一个镜像：自举闭包（退出固件启动服务后读系统卷、装载模块、报告错误所需的能力）加发行必备基线。一次交权只需载入一个 `.os`，不要求引导器预装 `.osm`。

它是唯一必须自带**原生引导镜像格式**的容器：`.os` 内提供 [Baleen 引导器](Baleen/README.md) 交接契约要求的镜像头和入口，`kind=core` 的元数据不能代替装载所需的原生格式。内核不为第三方引导协议附加标准入口头；要用其他引导方式启动，转换由中间层或二开的打包工具完成。具体入口形式属于「详细内容」。

### 5.2 `.osm` — 外置内核模块

**取自 Operating System Module**，`Module` 指模块，不使用表示模型的 `Model`。

`.osm` 是 `LINK_MODE=module` 的产物，与 `.os` 共享地址空间和特权级，成功激活后与内核同寿命、不卸载。

后缀由构建参数决定，不由运行期决定：`LINK_MODE` 只决定这份模块编进 `.os` 还是单独产出 `.osm`，不表示运行期按需加载。一次构建里同一个模块只产出一个形态，内置形态不产出 `.osm`，所以**不存在同一模块的内置形态与 `.osm` 并存**的情况。

### 5.3 `.drv` — 外部设备驱动

**取自 driver。**

`.drv` 是可以在内核集之外单独分发、单独更新的驱动，由 DriverLoader 按设备事实匹配装载。**启动必需的驱动以完整实现编入 `.os`，没有独立的必需 `.drv` 文件**，它们的升级随内核集重启完成。

是否支持热替换由设备、驱动能力和系统策略共同决定；默认系统卷链路使用内置驱动，随内核集重启升级。内部结构与装载协议属于「详细内容」。

### 5.4 `.exe` — 用户程序与常驻服务

**取自 executable。**

`.exe` 是用户态可执行程序的统一后缀：用户程序和常驻服务都用它，**服务不另设后缀**，靠服务声明区分角色。这样应用与服务共用同一套进程、文件、事件、日志和能力机制。

**与 Windows 的 `.exe` 同名，但不保证任何互通的兼容性**：

- LikesProgramOS 的 `.exe` 拿到 Windows 上**不保证能运行**——本项目不采用 PE 格式、不兼容 Windows API，Windows 也不认识本系统的容器格式。
- Windows 的 `.exe` 在本系统上**同样不保证能运行**——本系统没有实现 PE 装载路径，也不会为同名后缀额外放行。
- 同名只说明两边都用了「可执行文件」这个词，**不说明格式相通**；两边各自按自己的容器格式识别，认不出来就拒绝。

用户态载荷具有独立进程和地址空间。该容器的内部格式、服务声明格式属于「详细内容」。

### 5.5 `.dso` — 用户态动态库

**取自 Dynamic Shared Object**，POSIX 体系里的通用叫法，不属于任何一家系统专有。

`.dso` 是被用户程序在运行期装载的代码库：装载后与请求它的程序同处一个地址空间，因此**不是独立进程**，也没有自己的 `Init`；它由用户态装载器读入、重定位并向程序提供符号。

它和 `.exe` 分开的理由是类别不同：`.exe` 建立进程，`.dso` 被进程使用。装载器的归属、符号解析与版本选择规则属于「详细内容」。

### 5.6 `.arc` — 用户态静态库

**取自 archive**：它本质上是**目标代码的归档**，在构建期被链接器整段读入，不进入运行期。

取名说明：不用 `library` 系的词头，是因为 `.lib` 与 MSVC 的静态库、导入库撞得太直接；`.slib` 超过三个字符；后缀 `.a` 又与 Unix 的归档格式撞名。`archive` 说的是它的形态而不是链接方式，且不与任何主流工具链的后缀重合。

`.arc` **没有运行期生命周期**：不被装载器读取，不参与识别与生效阶段，只随使用它的程序一起重新构建、随安装包一起分发。它和 `.dso` 不共用后缀，正是因为它属于另一类载荷。

### 5.7 `.svc` — 服务声明

**取自 service。**

`.svc` 是常驻服务的声明文件：写明程序、运行身份、启动时机、依赖与顺序、失败策略、能力、日志目标、控制接口和健康确认。**服务本身是 `.exe`，声明是 `.svc`**——后缀不区分进程，声明才区分角色。

它由 Init 与服务编排方读取，不装载、不执行；声明格式由 HostSDK 定义，属于「详细内容」。声明与所属服务的版本并存：换声明就是换这份声明所处的版本记录，不靠改文件名标记。

### 5.8 `.res` — 资源与数据

**取自 resource。**

`.res` 是随程序分发的静态数据：图标、字体、主题、界面文本等。它不被装载器处理，由使用它的程序或服务读取，随该程序的版本一起切换。

哪些资源打进 `.res`、哪些内嵌进 `.exe`、哪些由服务动态生成，属于「详细内容」。

### 5.9 `.sym` — 调试符号

**取自 symbol。**

`.sym` 是与某份二进制对应的调试符号，供诊断工具与自检读取：它不参与装载，也不影响运行，缺失时程序照常运行。它与对应的二进制**版本并存**，按[内核架构与自举闭包](内核架构与自举闭包.md)的体积口径单独统计，不计入发布文件大小。

### 5.10 `.app` — 安装包

**取自 application package。**

`.app` 是 Installer 处理的分发单元，**不是可执行程序**：它自己不运行，只承载多类载荷（`.os`、`.osm`、`.drv`、`.exe`、`.dso`、`.arc`、`.svc`、`.res`、`.sym` 以及配置与签名清单）并把它们交给 Installer。

它是唯一**可以包含其他所有后缀**的后缀，因此后缀与 `kind` 的一致性检查要穿透到包内每一项载荷，而不只检查包本身。包内的组织方式、清单与签名格式属于「详细内容」。

### 5.11 SDK、源码与构建期形态

**这些不是「不带后缀」，而是后缀体系之外的存在形态。** 本系统的后缀只给容器与载荷分类；源码、SDK 的库、契约层、构建期工具和中间产物按各自的形态交付：

- **源码与头文件用工具链约定的后缀**：C++ 源码 `.cpp`，头文件 `.hpp`。它们没有 `kind`、不验签、不装载，谁编谁读由构建系统决定，不属于本文的后缀体系。
- **SDK 发布的库复用库后缀，不新增**：发布给驱动作者与应用作者的动态库就是 `.dso`，静态库就是 `.arc`——同一个东西在源码树里和 SDK 里是同一个后缀。
- **契约层随整集构建**：契约头、Tools工具校验 与汇编常量都在源码树内，不单独发布，因此没有独立后缀。
- **构建期工具是宿主形态**：契约生成器、构建系统、打包器、验证脚本跑在宿主上、用宿主的格式（脚本或宿主可执行文件），**不是本系统的容器**，也不进入目标系统的交付体系。
- **构建中间产物不进入交付体系**：目标文件等只在构建过程中存在，不定义后缀、不参与签名与分发。

所以 SDK 的一次发布大致是：契约头（`.hpp`）＋库（`.dso` / `.arc`）＋格式定义与工具（宿主形态）。

## 六、`.bin` 与 `.efi`：不是本项目设计，而是兼容

这两个后缀**不是本项目为自家容器选的标签**，而是为了能被固件与引导协议接受而必须遵守的外部约定。名字和内容形态都由外部决定，本项目在这两个后缀上没有设计自由。

- `.bin` **取自 binary**，裸二进制；这个叫法是通行的，不是本项目挑的词。
- `.efi` **取自 Extensible Firmware Interface**，即固件接口及其应用；这个名字由固件生态给定。

| 后缀 | 约束来源 | 本项目能决定的 | 不能决定的 |
|---|---|---|---|
| `.efi` | UEFI 固件：只加载 PE/COFF 镜像；可移动介质按固定路径查找引导程序 | 镜像里的实现 | 扩展名、镜像格式、引导路径 |
| `.bin` | 无固件要求：BIOS 与 El Torito 引导目录记录的是加载位置，不读文件名 | 文件名本身 | —（沿用裸二进制的通行叫法） |

**`.efi` 为什么不能改**：

- UEFI 固件只加载 PE/COFF 镜像；EFI stub 正是以 PE/COFF 镜像的形式才被固件装载（依据：Linux EFI stub 文档）。
- 可移动介质启动时，固件在 EFI 系统分区里按**固定路径** `\EFI\BOOT\BOOTX64.EFI` 查找引导程序（IA32 固件对应 `BOOTIA32.EFI`）；这就是 UEFI 可移动介质能够启动的方式（依据：Arch Wiki「Arch boot process」）。

所以 `BOOTX64.efi` 这个名字是固件要的，不是我们起的；它不能按本项目的命名规则改写，也没有 `kind`。

**`.bin` 为什么只是沿用叫法**：BIOS 与 El Torito 都不检查扩展名，引导目录记录的是加载位置而不是文件名。因此 `.bin` 是裸二进制产物的通行叫法，本项目沿用，**没有把它设计成带元数据的容器**。若某个引导路径将来要求特定文件名，以该协议为准。

## 七、后缀与 `kind` 的绑定

- **一一对应**：后缀 ↔ `kind` 必须一致；打包器拒绝产出不一致的容器，装载器按 `kind` 再校验一次。
- **载荷类别错配即拒绝**：`kind` 与载荷真实类别不符时拒绝装载，不因为后缀正确就放行。
- **不共享后缀**：不同类别的载荷不共用后缀；同类载荷内部再分角色（服务与用户程序、动态库与静态库）用声明或后缀区分，不合并。
- **没有 `kind` 的后缀分两种**：非装载载荷（`.arc`、`.svc`、`.res`、`.sym`）从来没有装载路径；外部约定（`.bin`、`.efi`）的类别体系由外部定义。
- **后缀体系之外的形态不参与这套绑定**：源码（`.cpp` / `.hpp`）、宿主上的构建期工具和构建中间产物既不是容器也不是载荷，见 5.11。
- **校验不等于本文的职责**：打包器和装载器依据的是容器的内部识别信息，其判定顺序、字段与失败码属于「详细内容」。本文只固定一件事：**后缀不参与判定，只作初筛。**

## 八、与其他生态重名的口径

| 后缀 | 重名情况 | 本系统的口径 |
|---|---|---|
| `.osm` | OpenStreetMap 数据文件 | 本系统使用自身格式标识识别内核模块；同名不构成任何关系 |
| `.exe` | Windows PE | **同名不保证互通**：本系统的 `.exe` 在 Windows 上不保证能运行，Windows 的 `.exe` 在本系统上也不保证能运行；不采用 PE、不兼容 Windows API、未获微软授权 |
| `.dso` | 部分系统的动态对象扩展 | 该词是 POSIX 通用术语，不由某一系统专有；同名不构成关系 |
| `.arc` | 若干压缩与归档格式 | 仅为本系统静态库的命名约定；同名不构成兼容声明 |
| `.svc` | 其他系统的服务描述文件 | 仅为本系统服务声明的命名约定；同名不构成关系 |
| `.res` | 其他系统的资源文件 | 仅为本系统资源载荷的命名约定；同名不构成关系 |
| `.sym` | 其他系统的符号文件 | 仅为本系统调试符号的命名约定；同名不构成关系 |
| `.app` | 其他系统的应用包 | 本系统的 `.app` 是安装包，不是可执行程序；同名不构成兼容声明 |

**后缀不代替格式识别。** 代码许可、产品商标和兼容性宣传分别处理，不因为共用后缀而合并讨论。

## 九、后缀不承担的事

- **不表达版本与发行**：多版本并存靠目录、构建清单和选择记录区分；正在使用或回滚所需的版本不原地覆盖，也不靠改文件名标记。
- **不表达架构**：目标架构是 x86_64；将来若需多架构并存，用目录与清单区分，不扩展后缀。
- **不表达发行策略**：发行决定选择哪些能力、哪些必需；不能借改后缀绕过依赖检查。
- **不表达互通**：与外部生态同名的后缀不构成任何一方对另一方的承诺，尤其不承诺双向可运行。
- **不提供隔离**：内核模块、内置驱动与外部 `.drv` 都运行在同一特权级；用户态后缀（`.exe`、`.dso`）表示进程内的执行环境，也不表示后缀本身提供任何保护。
- **不改写外部约定的名字**：`.bin`、`.efi` 按规定路径与文件名交付，不套用本项目的命名规则。

## 十、命名规则

1. **扩展名小写、尽量三个字符以内**，主名使用模块清单里的输出名称，不自行改写。
2. **版本与发行不写进文件名。**
3. **一个模块在一次构建里只产出一个交付形态**：`builtin` 不产 `.osm`，内置启动驱动不产必需的 `.drv`。
4. **同类不同角色分后缀**：程序与库、动态库与静态库、二进制与符号都是不同后缀，不用一个后缀带不同 `kind`。
5. 有哪些产物、各自叫什么，属于模块清单的内容，见[内核模块与驱动清单](内核模块与驱动清单.md)与 [Baleen 引导器](Baleen/README.md)；本文只规定后缀怎么用。

## 十一、待定项

1. **非装载载荷是否需要容器元数据**：`.arc`、`.svc`、`.res`、`.sym` 随包分发时是否要自带可校验的头部与摘要，还是只依赖包清单，尚未决定。
2. **`.dso` 装载器的归属**：由 AppSDK 内的装载器负责，还是独立组件，尚未定义。
3. **`.res` 与内嵌资源的分界**：哪些资源独立成 `.res`、哪些内嵌进二进制，尚未定义。
4. **`.bin` / `.efi` 是否纳入 `kind` 体系**：现表中没有 `kind`；若要纳入，需要与 [Baleen 引导器](Baleen/README.md) 一并定义。
5. **后缀与实际内容不符时的处理**：直接拒绝，还是按内容继续并告警，尚未决定。
6. **引导介质上的文件名约束**：ISO9660 依赖 Rock Ridge、FAT32 依赖长文件名支持才能表达 `EquipmentManager.exe`、`LikesProgram.os` 这类名字；是否需要在同一卷内避免仅大小写不同的重名（FAT32 大小写不敏感）尚未规定。
