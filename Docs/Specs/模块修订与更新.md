# 模块修订与更新

**`.os` 发布线是硬边界；模块在同一发布线内按修订独立更新，升级重启生效。** 本文定义模块的多版本模型、目录布局、模块加载列表、修订保留与更新/回滚流程。它回答两个容易混在一起的问题：*哪些版本可以并存*（多版本）与 *一个新版本怎样生效*（更新）。后缀语义见[后缀设计](后缀设计.md)，容器字节表见[内核模块容器](内核模块容器.md)，清单与签名见[内核集清单与签名](内核集清单与签名.md)。

## 一、版本模型

### 1.1 发布线（主版本）

- **发布线标识**：`.os` 镜像数据里的 `ModuleMajor`（偏移 `0x68`，非零），由内核构建的汇编常量给出；它是这一颗内核所属的发布线。
- **模块主版本**：每个 `.osm` 文件头里的 `ModuleVersionMajor`。装载器对它做**硬相等**判定：必须等于 `.os` 的 `ModuleMajor`，否则拒绝装载。
- **不承诺跨主版本兼容**：两个主版本的 `.os` 与 `.osm` 即使 ABI、接口版本与依赖范围碰巧全部匹配，也**一律不允许跨主版本装载**。代码里没有“忽略主版本继续尝试”的开关，也不靠范围判定反推兼容性。这条限制先于 ABI 与接口协商执行，见第三节检查顺序。

### 1.2 小版本

- 模块版本是 `major.minor.patch` 三个 `u16`，`major` 跟随发布线；补丁更新只允许抬 `minor` / `patch`，不得改变 `major`。
- 同一发布线内各模块的小版本**彼此独立**：某个模块修 BUG 或协议升级只更新它自己，其它模块的版本可以落后，版本差可以越拉越大。这是正常形态，不是异常。
- 模块版本号写在 `.osm` 文件头里；文件名也带版本（见第二节），但**版本判定以文件头与清单/加载列表登记的版本为准**，文件名只用于保留与人工识别。

### 1.3 `.os` 升级

`major` 变化意味着新的 `.os` 发布：生成新的 `BuildId` 与新的 `KernelSets/<BuildId>/` 目录，按[内核集更新与回滚](内核集更新与回滚.md)的整集更新与回滚处理。**不存在只换 `.os`、不换集目录的路径。**

## 二、目录布局

```text
KernelSets/<BuildId>/           # BuildId = .os 发布线身份，模块补丁不改变它
  LikesProgram.os               # .os，含 ModuleMajor
  Manifest.mft                  # 当前模块修订的签名清单
  Modules.list                  # 内核侧书写的完整模块加载列表，与 Manifest.mft 同级
  Modules/                      # 模块文件，平铺，文件名带版本
    DevModel.1.3.0.osm
    Ext4.1.5.0.osm
    Process.1.3.2.osm
    ...
  Manifest.<rev>.mft            # 旧修订的清单快照（默认保留 1 个）
  Modules.<rev>.list            # 旧修订的加载列表快照（同语义）
```

- **不用版本目录**：`Modules/` 下不建 `版本号/` 子目录；版本体现在文件名、文件头、清单与加载列表里。原因是各模块版本不同步，按版本建目录会让树形结构随维护历史无限分叉。
- **`Modules/Optional/` 是唯一的例外子目录**：M6 起用它承载可选运行期模块（见第五节），属于必需/可选的夹具约定，不是版本目录；引导闭包模块与必需运行期模块仍平铺在 `Modules/` 下。
- **BuildId 不随模块补丁变化**：同一发布线内所有模块修订共用同一个 `KernelSets/<BuildId>/`；`BuildId` 只由 `.os` 内容与集内 `.os` 路径派生（[内核集清单与签名](内核集清单与签名.md) 2.2）。
- 旧修订的 `Manifest.<rev>.mft` / `Modules.<rev>.list` 与它们引用的模块文件必须成组保留：回滚时选择器要按旧修订号取回旧清单与旧列表，而不是猜文件名。

## 三、硬主版本门与检查顺序

装载器对每个 `.osm` 按以下顺序判定，**主版本门在最前**：

```text
1. Manifest 验签 / SecurityVersion 防回滚 / BuildId 一致
2. Modules.list 结构合法；Modules.list 的 major == .os 的 ModuleMajor
3. .osm 的 ModuleVersionMajor == .os 的 ModuleMajor        ← 硬门
4. KernelAbiMin/Max 包含当前 KernelAbiVersion             ← 同主版本内的次级闸门
5. 导入接口的版本范围可满足
6. 模块依赖的版本范围可满足
```

- 第 2、3 步任一不满足即失败：不进入第 4–6 步，不尝试“也许兼容”。
- `KernelAbiMin/Max`、接口版本范围与依赖范围**只在同一主版本内**有意义，不能反过来放宽主版本门。
- Baleen 预装时读 `.osm` 头部到 `ModuleVersionMajor`（`0x66`）就能在搬运前拒绝明显跨主版本的模块，减少无谓搬运；内核装载器仍会再判一次，不把 Baleen 的检查当成唯一防线。
- 第三方引导器不遵守该门时，内核装载阶段同样拒绝；本项目不为第三方引导方式提供绕过路径。
- 运行期模块（M6 起，见第五节）在装载时同样逐项走第 3–6 步：主版本门与次级闸门都要再判一次，不因“不是预装模块”而跳过；第 1–2 步是集级检查，启动时已由 Baleen 完成。

## 四、模块加载列表 `Modules.list`

- **位置**：`KernelSets/<BuildId>/Modules.list`，与 `Manifest.mft` 同级。列表是**内核侧书写的完整模块加载列表**：内核集构建（`MakeManifest`）按当前修订登记全部 `.osm` 条目；Baleen 只从里面挑出引导闭包成员预装，内核用同一份列表装载闭包与运行期模块。
- **权威性**：列表是**配置**，不是完整性根。它被清单以 `Type=3` 产物条目登记（路径固定为 `Modules.list`），摘要与签名由清单覆盖；改列表必须重新生成并重签清单，不能只改文件。
- **内容**（ASCII、LF、确定性；当前版本 1）：固定头三行，随后是 0..30 条模块条目，每条一行：

  ```text
  LPML 1
  major 1
  revision 1
  module Modules/DevModel.1.0.0.osm
  module Modules/DriverLoader.1.0.0.osm
  module Modules/AtaPio.1.0.0.osm
  module Modules/Ahci.1.0.0.osm
  module Modules/Nvme.1.0.0.osm
  module Modules/UsbCore.1.0.0.osm
  module Modules/Xhci.1.0.0.osm
  module Modules/UsbHub.1.0.0.osm
  module Modules/UsbStorage.1.0.0.osm
  module Modules/Vfs.1.0.0.osm
  module Modules/Ext4.1.0.0.osm
  module Modules/ISO9660.1.0.0.osm
  module Modules/FAT32File.1.0.0.osm
  ```

  上面是正式发布集（只有引导闭包成员）的一个合法示例：`MakeManifest` 生成、Baleen 解析与内核核对必须同时接受它。变体集还会追加运行期模块条目，例如 `module Modules/Fault.1.0.0.osm` 与 `module Modules/Optional/Optional.1.0.0.osm`。

  - 固定头三行顺序固定、不得缺失；条目区紧随其后。只有固定头的空列表只对「清单没有 `.osm` 条目」的集合合法；集里有 `.osm` 时列表必须全部登记。
  - `module` 与相对路径之间一个空格；路径与清单 `Type=2` 条目的 `Path` **逐字节相同**，按字节比较，不做大小写或分隔符归一化。Baleen 与内核都不按固定文件名拼接模块路径。
  - 条目集合与清单 `Type=2` 条目集合**逐一相等**（数量相等 + 每条路径命中一条 `.osm`，清单 `.osm` 也都被登记）。顺序由内核侧决定：构建侧先按 `Packages/Common/Contract/BootClosure.def` 的顺序排闭包成员，再按确定性顺序排其余模块；读取方不依赖顺序，内核把列表顺序作为装载偏好（同层拓扑的稳定序）。
  - 条目上限 30 条（清单 `Type=2` 条目上限），路径长度上限 255 字节（与清单 `Artifact.PathBytes` 一致）；同一路径不得出现两次，不得指向非 `Type=2` 条目。
  - 不得含 CR、NUL、空行、注释、行尾空白或额外字段；文件必须以 LF 结尾。**容量上限 16 KiB**（含固定头）：按 30 条最长路径（255 字节）计算的解析缓冲与上限常量都取这个值，不得按“实际路径通常很短”设 4 KiB。
- **一致性**：`major` 必须等于 `.os` 的 `ModuleMajor`；`revision` 是本次模块修订号，与清单同一次发布。列表格式非法、主版本不符、条目集合与清单 `Type=2` 不相等或摘要不符都按所选集失败处理。
- **引导闭包成员的识别（唯一定义）**：路径主名 = 逻辑名（`Modules/<逻辑名>.<major>.<minor>.<patch>.osm`），由 `SHA-256("LPMOD01" ‖ 逻辑名)[0:16)` 派生 `ModuleId`，命中 `BootClosure.def` 期望集的是**引导闭包成员**；取不出逻辑名的条目（例如 `Modules/Optional/` 下的可选运行期模块）不是闭包成员。闭包成员必须在列表里**齐全且各出现一次**，否则列表非法（`E-CORE-96` / `E-UEFI-96`，detail 区分缺 / 重）；其余条目是运行期模块，Baleen 不预装、不报错。
- **三个核对点**：构建期 `MakeManifest` 保证列表条目与清单 `Type=2` 条目集合相等；Baleen 解析后按内嵌期望集挑出闭包成员并核对“应有成员齐全、无重复”，不一致按列表非法处理（`E-CORE-96` / `E-UEFI-96`）；内核入口核对列表 ↔ 清单集合（`E-KRN-54`）与预装记录只覆盖闭包成员（`E-KRN-55`）。三处同源，不允许各自维护成员表。
- **清单副本的签名区为零**：Baleen 验签时按[内核集清单与签名](内核集清单与签名.md) 2.1 的规则把签名值 64 字节原地归零再算 `ManifestDigest`；交给内核的清单副本就是这份已归零的字节（清单摘要原像）。内核**不重验签名、不重算清单摘要**，只按头部与条目区做结构核对；断言“清单副本签名值全零”不是交接要求，内核不因签名值非零单独失败。
- **运行期模块的识别**：列表条目里不属于引导闭包期望集的就是**运行期模块**（第五节）；不再使用「清单 `Type=2` 条目集合减列表条目集合」的差集口径。

## 五、运行期模块（M6 落地口径）

- **两个装载时机**：引导闭包模块由 Baleen 预装（`Modules.list` 里命中引导闭包期望集的成员，装载器在“预装闭包”阶段装载）；列表里其余条目是**运行期模块**，在内核挂载系统卷、读过清单之后由内核用**同一套装载编排**装载（`closureModule=false`，来源核对不做，摘要仍复算）。
- **识别规则**（唯一定义）：
  - 条目在 `Modules.list` 里（列表与清单 `Type=2` 集合相等，因此也在清单里），且**不属于** `BootClosure.def` 定义的引导闭包期望集；
  - 集内路径必须以 `Modules/` 开头、`Modules/` 之后至少还有一个字节；否则按条目非法处理，不猜路径；
  - 运行期模块不占引导闭包期望集的成员名；正式发布集没有运行期条目，三个运行期计数都是 0。
- **必需与可选（M6 夹具约定，正式清单语义留后续阶段）**：清单条目与 `.osm` 容器头都**没有**“必需/可选”标志位。M6 用集内路径前缀承载：在 `Modules/` 下但不是以 `Modules/Optional/` 开头的是**必需**，以 `Modules/Optional/` 开头的是**可选**。可选模块发行时放进 `Modules/Optional/` 子目录，清单条目按实际路径生成。清单条目将来若增加正式字段，以清单字段为准、路径前缀约定退场；在此之前，路径前缀是运行期处理器的唯一判据。
- **上限**：单次启动最多处理 **16** 个运行期条目（`kRuntimeModuleMaxCount`）；每个模块文件不超过 **256 KiB**（`kRuntimeModuleMaxBytes`），且 Stat 到的文件长度必须等于清单条目的 `dataBytes`。超限不截断、不静默跳过：必需条目报 `E-KRN-82`，可选条目降级 `WARN E-KRN-83`。
- **装载流程**（逐条按 `Modules.list` 里的运行期条目顺序，顺序不表达依赖；M6 夹具的运行期模块互不依赖，只依赖引导闭包已提供的接口，运行期模块之间的依赖声明归后续）：
  1. 用 VFS `Stat` 核对路径存在、非目录、长度在缓冲上限内且与清单登记一致；
  2. `Open` / `Read` 把整份字节读进内核静态缓冲（不映射卷上的页，读完即 `Close`）；
  3. 交装载器同一套编排：最小读取面 → 容器结构 → 摘要复算并与清单条目比对 → 主版本门与 ABI 区间 → 映射与重定位 → 导入解析与依赖检查 → `Init`；
  4. 成功打印 `runtime module init ok: <逻辑名>`（逻辑名取容器自描述的 `ModuleName`），失败按必需/可选分派。
- **摘要与来源**：运行期模块不做“来源核对”（它不在预装记录里，`closureModule=false`），但装载器仍复算摘要并与清单条目的摘要逐字节比较；摘要不符、容器非法、依赖或接口不满足都归装载机制失败，不因“不是预装模块”放松核对。
- **失败语义**（编号见[内核诊断编号](内核诊断编号.md)）：
  - 必需模块：读数失败（`Stat` / `Open` / `Read`）与装载编排失败（摘要、容器、映像、重定位）报 `FATAL E-KRN-80`；`Init` 返回失败报 `FATAL E-KRN-81`；条目非法（路径不在 `Modules/` 下、拼出的卷内路径越界、条目数超限、读到的长度与清单不符）报 `FATAL E-KRN-82`。三者都按本次启动失败处理：屏幕可见 `FATAL` + 等待 + 重启，不写确认记录，下一次启动按未确认回退（回退粒度是整修订，见第六节）。
  - 可选模块：任一失败只打印 `WARN E-KRN-83`（detail 带集内路径与机制层原因），计入汇总 `failed`，继续处理后续条目；不重启、不回退、不写状态。
- **汇总行**：全部运行期条目处理完后打印 `[ OK ] runtime modules: loaded=<n> failed=<n> optional=<n>`。`loaded` 是成功装载数，`failed` 是可选降级失败数（必需失败已 FATAL，走不到汇总），`optional` 是清单里的可选条目数。正式发布集没有运行期条目时三个数都是 0，这一行仍然打印，便于矩阵按列判定。
- **一次启动一个状态**：运行期模块不卸载、不热替换、不运行期重载；失败的恢复手段只有重启后的修订选择与回退（第六节）。
- **M6 夹具**（只验证机制，不验证具体服务模块）：`Modules/Fault.1.0.0.osm` 为必需运行期模块、`Init` 返回 `kCorrupt`，用于 `E-KRN-81` 与“FATAL 后重启”的稳定性；`Modules/Optional/Optional.1.0.0.osm` 为可选运行期模块，默认 `Init` 失败用于 `WARN E-KRN-83` 降级，`Makefile.ok` 变体（`-DOPTIONAL_INIT_OK`）成功用于 `loaded=1` 且出现 `runtime module init ok: Optional`。夹具条目同时进清单与 `Modules.list`（列表是完整模块清单），由内核按“非闭包条目”识别并装载。
- **同集两修订的选择与回退（M6 验证口径）**：集目录内同时存在当前修订的 `Manifest.mft` / `Modules.list` 与上一修订快照 `Manifest.<rev>.mft` / `Modules.<rev>.list`，选择器按状态记录里的 `ModuleRevision` 选修订，选定后打印 `Rev=0x%016x`；所选修订不可用时回退上一修订，一次启动只装载所选的**一个**修订。M6 夹具三个场景：新修订直启 → `Rev=0x0000000000000002`；旧修订直启 → `Rev=0x0000000000000001`；状态区记录旧修订且新修订候选不可验证 → 回退成功、`Rev=0x0000000000000001`。修订切换失败**不单独分配编号**，按失败位置并入 `E-KRN-50`–`59` 段（清单副本类并入 `51`、格式类 `52`、主版本/BuildId 类 `56` 等），detail 带所涉修订号。

## 六、模块修订与版本保留

- **一次模块补丁 = 一个模块修订**：修订号 `ModuleRevision`（`u64`，非零）随补丁单调递增；清单的 `SecurityVersion` 同步单调递增，作为防回滚依据。修订号写在 `Modules.list`，清单通过摘要与签名绑定它。
- **清单每个修订重签**：新修订生成新的 `Manifest.mft` 与 `Modules.list`；`BuildId` 不变，签名用发行密钥，`SecurityVersion` 不低于设备已见最高。
- **保留默认 1 个旧修订**（与内核集“当前 + 上一个稳定”同口径）：
  - 模块旧版本文件保留在同一个 `Modules/`，文件名带版本；
  - 旧修订的 `Manifest.<rev>.mft` / `Modules.<rev>.list` 成对保留；
  - 保留深度由发行策略配置，但**不得靠版本目录**实现。
- **清理只在确认之后**：当前修订被 Init 确认、且旧修订仍能完整验证时，才允许删除更早的修订文件；出厂基线、被钉住的修订与有失败痕迹的修订不删。清理规则与内核集锚点一致，见[内核集更新与回滚](内核集更新与回滚.md) 第六节。
- **保留是回滚材料，不是可运行态**：一次启动只装载一个修订；旧文件不会同时映射，也不存在“新旧模块同时运行”。

## 七、更新流程

```text
模块补丁包：新 .osm 文件 + 新 Manifest.mft + 新 Modules.list（清单签名覆盖三者）
  → Updater/Installer 校验签名、SecurityVersion 单调、模块主版本门、依赖与保留空间
  → 候选文件落进同一 KernelSets/<BuildId>/（新模块文件名，旧文件保留）
  → 写 Pending（记录 ModuleRevision / ManifestDigest）
  → 重启：选择器按状态记录选修订 → 验清单签名与防回滚 → 核对 Modules.list 主版本
      → 内核入口核对交接包与模块硬门 → 装载该修订
  → Init 确认点提交 Confirmed；任一阶段失败则下一次启动回退上一修订
```

- **生效必须重启**：模块不做运行期替换、不卸载、不热补丁。更新包落盘不等于生效，确认记录写成功也不等于新修订已稳定——下一次启动的选择结果才是。
- **不承诺“只换一个文件”的原子性边界**：补丁包是一个事务；允许只包含一个模块的新版本，但清单、列表、模块文件与签名必须一起落盘，缺一项按不完整修订处理。
- **回滚粒度是修订**：多个模块可以一起进入一个修订；回滚按整修订原子回退，不按单个模块拼接，避免依赖组合爆炸。`major` 升级仍按整集更新/回滚处理。

## 八、失败与诊断

- 主版本门不通过：内核侧 `E-KRN-5x`（编号在 `50`–`59` 段内预留，P5 的 M3/M4 已分配）；Baleen 侧 `E-CORE-95` / `E-UEFI-95`（模块主版本与内核不一致），`E-CORE-96` / `E-UEFI-96`（`Modules.list` 结构非法、条目与清单 `Type=2` 不对应，或引导闭包成员缺 / 重；列表里的非闭包条目不算错）。
- `Modules.list` 摘要不符按产物摘要失败处理（`E-CORE-68` / `E-UEFI-68`）；缺失按引导闭包/所选集失败处理；模块文件读取失败沿用 `E-CORE-67` / `E-UEFI-67`，摘要不符沿用 `E-CORE-68` / `E-UEFI-68`。
- 预装阶段的编号分配：最小读取面不通过（魔数 / 版本 / `HeaderBytes` / `Flags` / `TotalBytes` 与清单不符）用 `E-CORE-94` / `E-UEFI-94`；预装落点分配失败（低 4GiB 内无满足条件区间）用 `E-CORE-97` / `E-UEFI-97`；候选集预装失败后回退已知良好集时输出 `WARN E-CORE-98` / `E-UEFI-98`（不终止启动）；`99` 保留，不分配。
- 引导闭包或必需模块失败：屏幕可见 `FATAL` + 等待（默认 10 秒，可配）+ 重启，不写确认记录；下一次选择器按未确认的 `Trying` 递减并回退整集或上一修订。可选模块失败按发行策略降级 `WARN`。
- 运行期模块（M6 起）的编号：必需模块装载机制失败 `E-KRN-80`、必需模块 `Init` 失败 `E-KRN-81`、条目非法 `E-KRN-82`、可选模块降级 `E-KRN-83`；都由内核在挂卷并读过清单后打印，detail 带集内路径与机制层原因，编号由内核核心在调用点选一次。
- 修订选择与回退本身不新增编号：失败按失败位置并入 `E-KRN-50`–`59` 段（清单副本类 `51`、格式类 `52`、主版本/BuildId 类 `56` 等），detail 带所涉修订号；回退成功不是失败，按所选修订正常启动。
- 运行期不写引导状态区；状态写入仍只属于 Init。
