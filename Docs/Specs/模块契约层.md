# 模块契约层

**契约层是内核核心与 `.osm` 模块之间唯一的调用面。** 它把接口标识、槽位布局、版本协商、入口调用、失败表示与驱动接入面固定成一份生成式定义：`Packages/Common/Contract/` 下的两份私有输入由 `MakeContract` 生成头文件，内核核心、引导闭包模块、运行期模块、`.osm` 打包器与宿主检查都从同一份生成物取常量，**不手写第二份**。

[内核模块容器](内核模块容器.md)定义 `.osm` 如何承载导出表、导入表与依赖表，以及装载器按什么顺序解析（第四、七、八、九、十二节）；本文定义这些表里**装什么**、由谁提供、版本怎样冻结。装载流程、初始化契约与失败语义见[模块与驱动装载](模块与驱动装载.md)，失败编号见[内核诊断编号](内核诊断编号.md)。

**四条硬规则先写在这里：**

1. **单点定义。** 接口的唯一事实源是 `Packages/Common/Contract/Interfaces.def`，闭包成员的唯一事实源是 `Packages/Common/Contract/BootClosure.def`；生成头是它们的函数，源码不得手写 `InterfaceId`、槽位顺序或第二份接口清单。
2. **提供者唯一。** 同一 `(InterfaceId, Version)` 在内核核心与全部已装载模块合并计算后只能有一个提供者：构建期重复即构建失败，装载期复核并拒绝。
3. **槽位冻结。** 一个接口版本发布后，槽位数、槽位顺序、每槽签名与语义冻结；只能新增版本，且新版本只允许在尾部追加槽位。改既有槽位必须新建接口稳定名。
4. **错误码单点。** 模块返回码不产生诊断编号；`E-KRN` 由装载器按失败点选，模块原因作 detail 附后。这与[内核诊断编号](内核诊断编号.md)第五节"共享机制只回报文本、不产生编号"是同一条原则。

**状态：规格先行。** 本文是 M0 收口任务 T0.6 的定稿；`Interfaces.def`、契约生成器与构建期检查由 T1.1 落地，接口 v1 由 T5.1 生成并冻结。G6c 的 `Usb.Host` v1 与 `Dev.Model` v2 是冻结后的增量（4.2 只加版本、5.1 不抬内核 ABI），由 M6 G6c 落地。首次发布前接口按设计调整（[ABI 兼容与外部契约](Common/ABI兼容与外部契约.md)第二节第 7 条），发布后按本文第十一节演进。

## 一、定位与分工

### 1.1 术语与角色

| 术语 | 含义 |
| --- | --- |
| 接口（interface） | 一个稳定名字标识的调用面，由 `(InterfaceId, Version)` 与一组槽位组成；如 `Core.Page`、`Dev.Model` |
| 槽位（slot） | 接口表里的一个函数指针条目，有槽位号、槽名、C 签名与语义；槽位号从 `0` 起 |
| 提供者（provider） | 导出某接口某版本的一方：内核核心或某个已装载模块；同一 `(InterfaceId, Version)` 只允许一个 |
| 消费者（consumer） | 通过导入表使用接口的一方；声明 `MinVersion/MaxVersion` 与使用的槽数 |
| 闭包单例 | 由某个引导闭包成员唯一导出的接口（`Dev.Model`（v1/v2）、`Drv.Loader`、`Block.Registry`、`Fs.Vfs`、`Boot.Volume`、`Usb.Host`），提供者固定 |
| 内核 ABI 版本 | `KernelAbiVersion`（`u16`），入口调用约定、`KernelAbiContext`、模块返回码语义与核心服务集合的版本 |
| 驱动契约版本 | `DriveSDKVersion`（`u16`），`BlockDeviceOps` / `FileSystemOps` / `DriverDesc` 布局的版本，与内核 ABI 版本独立 |

### 1.3 与容器规格的分工

容器规格管字节与流程，本文管内容与策略。两边口径不一致时，容器格式字节以容器规格为准，接口内容以本文为准，并修另一处。

| 事实 | [内核模块容器](内核模块容器.md) 定义 | 本文定义 |
| --- | --- | --- |
| `InterfaceId` 宽度与字段位置 | 16 字节字段（导出/导入条目 `0x00`） | 派生算法、稳定名语法、文本形式 |
| 导出/导入/依赖条目布局 | 字段偏移、长度、对齐 | 哪些接口、槽位数、槽序、每槽签名与语义 |

| 失败路径 | 装载步骤与整集失败边界 | 模块返回码单点、与 `E-KRN` 的选号关系 |

### 1.4 生成式契约与消费方

契约的"定义"是输入，"头文件"是产物。手写头（`Packages/Common/Include/` 下的 `BootInfo.hpp`、`Print.hpp`、`Manifest.hpp`、`KernelImage.hpp`、`BootState.hpp` 与 `Storage/*`）承载已有共享契约；生成头只承载由 `Interfaces.def` 与 `BootClosure.def` 推导出来的东西，落在 `Packages/Common/Out/Contract/`，由各包 include 路径引入。

| 消费方 | 消费的生成物 |
| --- | --- |

| 内核装载器（T4.1–T4.6） | `Entry.hpp`、`Slots.hpp`、`Imports.hpp`、`BootClosure.hpp`、`Types.hpp` |
| 引导闭包模块与运行期模块 | 全部生成头 + 本模块的导出/导入表 |

| `MakeManifest` / `CheckPreload`（T0.5、T2.10） | `BootClosure.hpp` 期望集表 |
| 宿主检查（T4.4 起） | 全部生成头，按编号与常量断言 |

## 二、私有输入格式

### 2.1 `Packages/Common/Contract/Interfaces.def`

**一行一个槽位**，格式固定为：

```text
interface <稳定名> <版本> <槽名> <C 签名>
```

| 字段 | 语法 | 说明 |
| --- | --- | --- |
| `interface` | 固定关键字 | 小写，必须逐字节相等 |
| `<稳定名>` | 见 3.3 | 接口的稳定名字，如 `Core.Page`、`Dev.Model` |
| `<版本>` | 十进制 `u16`，无前导零，取值 `1..65534` | `65535`（`0xFFFF`）是导入上限的"不设上限"哨兵，不允许作为接口版本 |
| `<槽名>` | `[A-Z][A-Za-z0-9]*`，同一版本内唯一，≤32 字节 | 生成结构体的成员名 |
| `<C 签名>` | `<返回类型> (<参数类型列表>)`，行内剩余全部字节 | 函数**类型**，不含参数名与 `(*)`；生成结构体成员时插入槽名 |

签名允许的类型只有：定宽整数（`uint8_t`…`uint64_t`、`int32_t`、`int64_t`）、`void`、`void*` / `const void*`、`char*` / `const char*`（路径字符串，非拥有、以 NUL 结尾）、上述类型的指针、`KernelError`、`Storage::Error`、`ModuleId*`、`Boot::Info*` / `const Boot::Info*`、`Storage::FileInfo*`、`Storage::FileSystemCaps*`、契约层句柄 typedef（`DeviceHandle`、`FileSystemId`、`ObjectHandle`、`ControllerHandle`、`UsbDeviceHandle`、`ClassHandle` 等，见 10.0）、以及本文定义的结构指针（`DeviceFacts*`、`DriverDesc*`、`UsbSetupPacket*` / `const UsbSetupPacket*`、`UsbDeviceFacts*`、`UsbControllerOps*` / `const UsbControllerOps*`、`UsbClassOps*` / `const UsbClassOps*`、ops 表指针等）。**不允许**：C++ 引用、模板、按值传结构体、可变参数、省略 `(void)` 的空参数列表、`bool` / `char` 等宽度不固定类型。

文件规则：

- 纯 ASCII，LF 行尾，末行可带 LF；不允许空行、注释、CR、NUL、BOM、行首尾空白；字段之间单个空格。
- 全文件按 `<稳定名>` 的 ASCII 字节序升序排列；同一稳定名的多个版本块按 `<版本>` 升序排列，同一版本块的槽行必须连续；版本块内**文件顺序即槽位顺序**。
- `BootClosure.def` 之外没有第二份接口清单：模块的导出/导入声明只引用本文接口（见 2.4），不另起接口名字。

示例（节选，槽位语义见第十节）：

```text
interface Core.Abi 1 Version uint16_t (void)
interface Core.Abi 1 BuildId64 uint64_t (void)
interface Core.Abi 1 DriveSdkVersion uint16_t (void)
interface Core.Boot 1 Info const Boot::Info* (void)
interface Core.Page 1 PageBytes uint32_t (void)
interface Core.Page 1 Allocate uint64_t (uint32_t)
```

### 2.2 `Packages/Common/Contract/BootClosure.def`

**一行一个闭包成员**，格式固定为：

```text
closure <顺序> <逻辑名>
```

- `<顺序>`：十进制，`1..13` 连续升序，**即预装顺序、期望集顺序与拓扑排序的同层次序**；由 [模块修订与更新](模块修订与更新.md)第四节登记成员，`BootClosure.def` 是其实体。
- `<逻辑名>`：`[A-Z][A-Za-z0-9]*`，是 `ModuleId` 的派生输入（3.2）；如 `DevModel`、`Vfs`。逻辑名唯一。
- 允许以 `#` 开头的说明行与空行（成员表是给人读的，注释解释成员顺序的依赖理由）；工具跳过它们，成员行本身仍受上面的语法约束。`Interfaces.def` 则不允许注释与空行（生成器要按行号定位错误，见 2.1）。
- 行数必须为 13（闭包成员固定，发行不能裁剪，见[内核架构与自举闭包](内核架构与自举闭包.md) 2.2）；缺行、多行、顺序不连续、`ModuleId` 重复都按格式错误拒绝。
- 排序必须满足依赖拓扑：提供者先于消费者；**同层成员由文件行序决定，行序即预装顺序与注册顺序**。容器第九节与 T4.5 的稳定拓扑排序以 `Modules.list` 的预装顺序为同层首选，`ModuleId` 字节序只是同层次序缺失时的兜底——不在本文件里按哈希值重排行。

**成员增删改名不是契约层的例行变更。** 闭包成员固定；改这份文件等于改期望集与预装集合，必须同时改[内核架构与自举闭包](内核架构与自举闭包.md) 2.2、[模块修订与更新](模块修订与更新.md)第四节与列表生成，并重新走 M0 冻结。`BootClosure.def` 是期望集的唯一事实源，Baleen 的预装筛选、内核装载器（E-KRN-55 判定）与 `CheckPreload` 都从生成的 `BootClosure.hpp` 取，不各写名字列表。

### 2.3 冻结表 `Packages/Common/Contract/Frozen.tsv`

槽位冻结需要一个可比较的基线，否则"发布后不得改"只能靠评审记忆。冻结表是工具私有的定稿记录，不是生成头，放在输入目录、随仓库提交：

```text
<稳定名>	<版本>	<槽数>	<槽位定义摘要>
```

- 槽位定义摘要 = 该版本槽位定义规范化后（每槽一行 `<槽号>\t<槽名>\t<签名>`，LF 连接、末尾不带多余换行）的 SHA-256 前 16 字节，小写十六进制。
- 由 `MakeContract --freeze` 追加，一行一个**已发布**版本；构建默认只读比对当前 `Interfaces.def` 与冻结表，任一已发布版本块不一致即构建失败。
- 首次发布前（T5.1 之前）文件可以为空或缺席，表示没有已发布版本，不做冻结检查；首次写入发生在 T5.1 的 v1 冻结，此后只增行、不改行。

### 2.4 模块契约声明

接口定义是全局的，谁提供、谁使用是模块事实。每个模块包在构建配置里声明三项（T1.7 模块骨架固定写法）：

| 变量 | 内容 | 示例 |
| --- | --- | --- |
| `MODULE_NAME` | 逻辑名，决定 `ModuleId`（3.2） | `Ext4` |
| `CONTRACT_EXPORTS` | 导出项列表，`<稳定名>:<版本>` | `Dev.Model:1` |
| `CONTRACT_IMPORTS` | 导入项列表，`<稳定名>:<MinVersion>:<MaxVersion>:<使用槽数>` | `Core.Log:1:1:4` |

规则：内核核心不写这三项，它的导出表由 `Core.*` 固定生成；闭包单例的提供者固定（4.3），模块声明必须与提供者表一致，不一致即构建失败；运行期模块可以声明新的导出，但接口本身仍必须先在 `Interfaces.def` 里定义。

### 2.5 私有输入的边界

- `.def` 只被 `MakeContract` 读取，**不参与其它构建**：不被 C++ `#include`、不被 NASM `%INCLUDE`、不进入任何目标文件或产物、不随内核集分发。
- 仓库现有常量文件是 `.inc`（如 `Packages/LikesProgramOS/Core/Include/Const.inc`、`Packages/Baleen/Common/Include/Contract.inc`），由预处理器或汇编器包含；**仓库没有 `.def` 先例**。两者用途不同：`.inc` 是编译期常量包含文件，`.def` 是构建工具的私有输入格式。`.def` 的逐字段解析细则（容错、报错文本）由 `Tools/Build/MakeContract/README.md` 说明（T1.1 产出），语义以本文为准，两者不一致时修 README。
- `.def` 不是新的容器或载荷类别，不进[后缀设计](后缀设计.md)的后缀表：它属于源码与构建期形态。

## 三、标识派生

### 3.1 `InterfaceId`

```text
InterfaceId = SHA-256("LPIF01" ‖ 稳定名 ASCII 字节) 的前 16 字节
```

- 与容器规格第七节一致；域标记 `LPIF01` 与 `ModuleId` 的 `LPMOD01` 分离，两个命名空间不会互相碰撞。
- 稳定名按文件里的 ASCII 字节原样参与计算：大小写敏感、不做归一化、不加终止零。
- 全零 `InterfaceId` 非法（容器第七节拒绝全零）。派生是构建期一次性的：生成头里是常量字节，**运行期任何代码都不从名字重新计算 ID**。

### 3.2 `ModuleId`

```text
ModuleId = SHA-256("LPMOD01" ‖ 逻辑名 ASCII 字节) 的前 16 字节
```

- 与容器规格 4.1 一致；逻辑名是模块在构建配置里的稳定名字（`MODULE_NAME`），如 `DevModel`、`Ext4`。
- 内核核心没有 `ModuleId` 条目；需要表示"内核核心提供"的地方使用全零 `ModuleId`（`kModuleKernelCore`）。全零在模块侧非法（容器第九节拒绝依赖全零），因此不会与模块冲突。
- 同一内核集里 `ModuleId` 不得重复；`BootClosure.def` 成员与运行期模块的逻辑名共用一个命名空间。
- 人类可读模块名（容器 `ModuleName`）只用于诊断，不参与标识。

### 3.3 稳定名与逻辑名语法

| 项 | 规则 |
| --- | --- |
| 字符集 | 纯 ASCII：`A–Z`、`a–z`、`0–9`，接口稳定名额外允许 `.` 作分量分隔符 |
| 接口稳定名 | `[A-Z][A-Za-z0-9]*(\.[A-Z][A-Za-z0-9]*)+`：至少两个分量，每个分量首字符大写，`.` 分隔 |
| 逻辑名（模块） | `[A-Z][A-Za-z0-9]*`：单分量，不允许 `.` |
| 长度 | 稳定名与逻辑名都不超过 64 字节 |
| 禁止 | 空分量、连续 `.`、首尾 `.`、下划线、连字符、空格、数字开头、非 ASCII 字节 |
| 大小写 | 大小写敏感；改名等于换 ID，不提供别名或旧名映射 |
| 唯一性 | `InterfaceId` 全仓唯一；同一稳定名可有多版本，但版本号唯一；逻辑名在集内唯一 |

### 3.4 派生单点与文本形式

- 派生只有一处实现：`MakeContract` 内部的 SHA-256（与 `Tools/Common` 的同一实现同源）。`PackModule`、内核注册表、Baleen 与宿主检查都消费生成常量或生成表，**不各自实现第二份派生**。
- `InterfaceId` / `ModuleId` 的文本形式为 32 位小写十六进制（无 `0x` 前缀、无分隔），用于日志、诊断、宿主检查输出；容器与生成头里是 16 字节原始值。
- 生成头提供的常量命名：稳定名或逻辑名去掉 `.`、各分量首字母大写拼接，前缀 `kIf` / `kMod`：`Core.Page` → `kIfCorePage`，`DevModel` → `kModDevModel`，内核核心 → `kModuleKernelCore`。

## 四、槽位、版本与提供者

### 4.1 槽位与生成结构

- 槽位号从 `0` 起，等于版本块内的行序；槽数 `1..64`（与容器第七、八节的 `SlotCount` 范围一致）。
- 每个 `(接口, 版本)` 生成一个槽位结构 `<接口>SlotsV<版本>`：成员按槽位顺序排列，类型为对应 C 签名的函数指针，成员名即槽名。如 `interface Core.Page 1 Allocate uint64_t (uint32_t)` 生成 `struct CorePageSlotsV1 { uint32_t (*PageBytes)(void); uint64_t (*Allocate)(uint32_t); ... };`。
- 生成头为每个接口给出当前版本别名 `<接口>Slots`（等于最高版本的结构）与常量 `k<接口>SlotCountV<版本>`、`k<接口>CurrentVersion`。
- 槽位结构是**函数指针数组的强类型视图**：生成头用 `static_assert` 把 `sizeof(<接口>SlotsV<n>) == 槽数 × sizeof(void*)` 钉死；导出表、导入回填区、容器槽位表都以它为唯一布局来源。
- 签名与容器表的关系：导出条目的槽位表是 `SlotCount` 个 `u32`（相对模块基址的代码偏移，容器第七节）；导入条目的回填表是 `SlotCount` 个 `u32`（相对本模块基址的 8 字节指针槽内存偏移，容器第八节）。生成头只定结构形状，偏移计算由 `PackModule` 与装载器完成。
- 提供者与消费者的表符号固定（`extern "C"`，由生成头声明）：提供者导出表 `_Contract_Export_<接口>_v<版本>`，消费者回填区 `_Contract_Import_<接口>_v<版本>`，`PackModule` 按 ELF 符号表取，不解析 C++ 修饰名。

### 4.2 版本冻结与追加规则

- **槽位冻结**：同一 `(InterfaceId, Version)` 发布后，槽位数、槽位顺序、每槽签名与语义都不得改变；改动等于换接口。`Frozen.tsv` 是构建期比对基线（2.3）。
- **只加新版本**：需要新能力时发布 `Version + 1`；新版本必须**保留旧版本的全部槽位在相同位置**（逐槽同名、同签名、同语义），新槽只能追加在尾部。构建期检查名字与签名，语义兼容由发布评审负责。
- **破坏性变更不通过版本表达**：改变既有槽的签名、返回值语义或所有权，必须新建接口稳定名（新 `InterfaceId`），旧接口保留到退役窗口结束。接口版本的递增只表达"尾部追加"，不表达"改旧槽"。
- 版本号单调递增，已发布版本号不复用；同时存在多个版本时，提供者在导出表里同时导出（容器第七节允许同一接口多版本条目），消费者按 4.5 选择。
- 兼容窗口与退役见 11.3；在窗口内，旧版本消费者与旧版本提供者都能工作（容器 14.3 第 1、5 条）。

### 4.3 提供者唯一

**同一 `(InterfaceId, Version)` 在一次启动内只能有一个提供者，内核核心与全部已装载模块合并计算。** 这条规则是两个前提的产物：容器第八节的版本选择要求"候选集合里每个版本只有一个来源"，否则选择结果依赖装载顺序；接口槽位是同一布局，多来源会破坏"消费者只按版本选择"的确定性。

当前已定义接口版本的提供者表固定如下（构建期硬检查，`Frozen.tsv` 之外的第二道门）：

| 接口 | 唯一提供者 | 说明 |
| --- | --- | --- |
| `Core.Page`、`Core.PhysMap`、`Core.Mem`、`Core.Log`、`Core.Time`、`Core.Boot`、`Core.Dma`、`Core.Mmio`、`Core.Object`、`Core.Abi` | 内核核心（`kModuleKernelCore`） | 内核核心只提供 `Core.*`，不内置设备与文件系统接口 |
| `Dev.Model` v1 / v2 | `DevModel` 模块 | 设备模型唯一实例；v2 在 v1 六槽尾部追加槽 6 `Register` |
| `Drv.Loader` | `DriverLoader` 模块 | 驱动加载器唯一实例 |
| `Block.Registry`、`Fs.Vfs`、`Boot.Volume` | `Vfs` 模块 | 块设备注册、VFS 与系统卷挂载由同一模块提供 |
| `Usb.Host` v1 | `UsbCore` 模块 | USB 主机接口唯一实例：控制器注册、类登记、传输与轮询 |
| 未来运行期模块新增的接口 | 声明它的那个模块 | 必须先在 `Interfaces.def` 定义并进冻结表 |

**闭包单例接口共 6 个；提供者表按"每接口每已定义版本一条"计，当前 7 条**：`Dev.Model` 的 v1 与 v2 各一条，`Drv.Loader`、`Block.Registry`、`Fs.Vfs`、`Boot.Volume`、`Usb.Host` 各 `v1` 一条（生成头 `kClosureProviderCount = 7`，不要把它当成单例个数）。提供者唯一按 `(InterfaceId, Version)` 逐条计算，同一模块同时导出 `Dev.Model` v1/v2 不构成重复。

- **构建期**：`MakeContract` 把内核核心与所有模块声明的导出合并，任一同 `(InterfaceId, Version)` 出现两次即失败；闭包单例的提供者与上表不符即失败。
- **装载期**：内核接口注册表在登记导出时按 `(InterfaceId, Version)` 查重。重复时：必需模块路径整集失败（`E-KRN` 选号按失败点），可选模块拒绝该模块并 `WARN`，不静默覆盖先装载的提供者（容器第七节同口径）。
- 版本选择不受装载顺序影响：由于同版本唯一来源，区间内"最高版本"唯一；不同版本可以由不同提供者提供（例如新模块提供某接口的 v2、旧模块仍提供 v1），选择按版本而非按提供者。

### 4.4 多实例能力走单例注册 ops

**不导出同名多实例接口。** 驱动、文件系统、设备这类天然多实例的能力不在接口层复制成 `Core.X2`、`Dev.Model.Slot1` 之类的条目；它们的做法固定为：

1. 能力提供者模块导出**一个单例接口**（每 `(InterfaceId, Version)` 一个提供者）；
2. 该接口提供一个"注册"槽，接收一个 **ops 结构体指针 + 不透明 `context` 指针**；
3. 调用方把 `context` 与 ops 表一起登记，每次回调把 `context` 传回实现，实现据此区分实例；
4. 实例标识按能力面区分：块设备实例不另发句柄，直接用 `Dev.Model` 的设备句柄标识（不在提供者唯一之外再引入第二套编号）；文件系统实现由注册槽带回 `FileSystemId`；驱动实例由 `DriverDesc.context` 区分，绑定关系由 `BindHandle` 标识。

例：`Block.Registry.Publish(deviceHandle, ops, context, flags)` 把块设备实现注册到设备句柄，`Fs.Vfs.RegisterFileSystem(ops, context, &registration)` 登记文件系统实现，`Drv.Loader.RegisterDriver(desc)` 登记驱动描述（`desc->context` 区分实例）。ops 表的布局与版本见第八节。

### 4.5 消费者的导入规则

- 每个消费者对同一接口只有一条导入（容器第八节）；声明 `MinVersion`、`MaxVersion`（`0xFFFF` 表示不设上限）与**实际使用的槽数**。
- 装载器在全部已装载提供者的导出里，取 `MinVersion <= Version <= MaxVersion` 的最高版本；使用槽数不得超过所选提供者的 `SlotCount`，否则拒绝——消费者只能使用提供者承诺过的槽位（容器第八节）。
- 构建期检查：`MinVersion <= MaxVersion`；本次构建的提供者集合中至少存在一个满足区间的版本；使用槽数不超该版本槽数。检查不通过即构建失败，不等到装载期才发现。
- 运行时接口指针只能经导入表回填获得，模块不得用固定地址或内核核心符号直接调用（第九节硬约束）。

## 五、内核 ABI 版本

### 5.1 值、覆盖范围与抬版条件

`KernelAbiVersion` 是 `u16`，当前值 `1`（与容器 4.3 一致）。它覆盖"模块怎样被内核调用与装载"这一层，不覆盖单个接口的槽位细节。

| 覆盖 | 不覆盖 |
| --- | --- |
| 入口符号名与三入口签名（`_Module_Init` / `_Module_Activate` / `_Module_Abort`） | 单个接口的槽位数量与签名（由接口版本表达） |
| `KernelAbiContext` 的字段、语义与追加规则 | 新增接口、新增单例（不抬版，消费者按导入声明自行选择） |
| `KernelError` 既有取值的语义 | 模块自身 `ModuleVersion` 与容器格式版本 |
| `Init` / `Abort` 的调用契约与阶段约束、`Activate` 的调用条件 | `DriveSDKVersion` 及其 ops 表布局（独立版本，见 5.5） |
| 内核核心提供的基础服务集合（`Core.*` 接口的移除） | 新增 `Core.*` 接口（追加服务不破坏旧模块） |

**抬版条件（满足任一即抬 `KernelAbiVersion`）：**

1. 入口符号名、入口参数类型或返回值语义变化；
2. `KernelAbiContext` 既有字段偏移、类型或语义变化（只追加不算）；
3. `KernelError` 既有取值语义变化或删除取值；
4. 移除一个已发布的 `Core.*` 接口；
5. `Init` / `Abort` 的调用时机、可撤销边界或失败语义变化。

抬版必须同时更新模块的 `KernelAbiMin` / `KernelAbiMax`（容器 4.3、14.3）：旧内核拒绝声明更高下限的模块，新内核按范围拒绝过旧模块，不"尽力运行"。

**M6 G6c 的契约增量不抬版**：`Usb.Host` v1 是新增接口（新增单例），`Dev.Model` v2 是在 v1 六槽尾部追加槽 6；两者都属于"新增接口 / 新增单例 / 尾部追加槽位"，`KernelAbiVersion` 仍为 `1`。`DriveSDKVersion` 也不变：`UsbControllerOps` / `UsbClassOps` 是契约层结构，USB 不走 DriveSDK 的 `DriverDesc` / `BlockDeviceOps` / `FileSystemOps` 面（第八节）。只声明 `KernelAbiMin/Max = 1/0xFFFF` 的旧模块继续按原版本工作。

### 5.2 导出位置

`KernelAbiVersion` 的发布位置固定为两处，且必须同源：

1. **生成头常量**：`Packages/Common/Out/Contract/Abi.hpp` 的 `constexpr uint16_t kKernelAbiVersion = 1;`（同文件还有 `constexpr uint16_t kDriveSdkVersion = 1;`）。
2. **`Core.Abi` 导出条目**：内核核心以容器第七节同一形式导出 `Core.Abi` v1，槽位如下：

| 槽 | 槽名 | 签名 | 语义 |
| --- | --- | --- | --- |
| 0 | `Version` | `uint16_t (void)` | 返回 `kKernelAbiVersion` |
| 1 | `BuildId64` | `uint64_t (void)` | 返回 `.os` `BuildId` 前 8 字节按小端装入的值；仅用于诊断与归属，不是身份判定 |
| 2 | `DriveSdkVersion` | `uint16_t (void)` | 返回 `kDriveSdkVersion`（驱动契约版本） |

`Core.Abi` 槽 0/1 与计划 6.2 草案一致；槽 2 是 v1 在尾部追加的槽位，不改变槽 0/1 的顺序与语义。装载器判定模块 `KernelAbiMin/Max` 时使用生成头常量（它与 `Core.Abi` 槽 0 是同一个值，见 5.3）。

### 5.3 构建期一致性

- 生成头把常量与 `Core.Abi` 版本块绑定：`Core.Abi` v1 的槽 0 实现由生成器固定（内联函数返回 `kKernelAbiVersion`，符号名由生成器给出），内核核心导出表必须登记该实现，**不得另写数字**；`Abi.hpp` 用 `static_assert` 钉住 `Core.Abi` 版本块存在、槽数 ≥ 3、槽 0/2 签名分别为 `uint16_t (void)`。
- 生成器在生成时检查：`Interfaces.def` 中 `Core.Abi` 的槽 0/2 签名与本文一致，否则构建失败（防止有人在 .def 里改签名绕开绑定）。
- `CheckRegistry`（T4.4）在宿主侧核对内核核心导出表：`Core.Abi` 槽 0 的实际返回值等于 `kKernelAbiVersion`、槽 2 等于 `kDriveSdkVersion`；不一致即检查失败。
- 运行时登记：内核接口注册表初始化时把 `kKernelAbiVersion` 作为装载器的 ABI 判定值；该值只从生成头取。

### 5.4 不改 `.os` 镜像数据保留区

`KernelImage::ImageDataLayout` 的保留区（`0x6A` 起 22 字节，见 `Packages/Common/Include/KernelImage.hpp`）保持全零，**不写入内核 ABI 版本**。理由：内核 ABI 是"内核核心对模块的调用面"，属于内核核心自己的导出条目；镜像数据是 Baleen 与内核之间的交接事实，Baleen 不需要、也不应该知道模块 ABI 版本。`Core.Abi` 的基准地址是内核核心装载地址，由注册表登记（容器第七节末段）。

### 5.5 `DriveSDKVersion` 的独立演进

版本事实互相独立，装载器按固定顺序判定，不能互相替代：

| 事实 | 值域 | 谁声明 | 作用 | 抬版条件 |
| --- | --- | --- | --- | --- |
| 容器格式 `Version` | `u16`，当前 `1` | `PackModule` | 容器字节布局 | 容器字段变化（[内核模块容器](内核模块容器.md)第三节、14.3） |
| `KernelAbiVersion` | `u16`，当前 `1` | 内核核心 | 入口、上下文、错误码语义、核心服务集合 | 5.1 五条 |
| 接口 `Version` | 每接口 `u16` | 提供者 | 槽位集合 | 尾部追加槽位；改旧槽建新接口（4.2） |
| `DriveSDKVersion` | `u16`，当前 `1` | 内核核心发布，驱动声明 | `BlockDeviceOps` / `FileSystemOps` / `DriverDesc` 布局 | ops 表或 `DriverDesc` 布局变化（第八节） |
| 模块版本 `major.minor.patch` | 三个 `u16` | 模块 | 发布线硬门 + 修订选择 | 模块修订流程（[模块修订与更新](模块修订与更新.md)） |

判定顺序沿用容器第十二节第 4 步：主版本硬门 → `KernelAbiMin/Max` → 接口版本 → 依赖；`DriveSDKVersion` 在驱动注册时判（8.6），不是模块装载的前置门——文件系统模块可以不涉及驱动契约，不因驱动契约版本不匹配被拒。

## 六、入口 ABI

### 6.1 入口符号与签名

容器文件头的 `EntryInit` / `EntryActivate` / `EntryAbort` 是相对模块基址的代码偏移（容器第六节）；入口函数本身由本文定义：

```cpp
extern "C" KernelError _Module_Init(const KernelAbiContext* context);
extern "C" KernelError _Module_Activate(const KernelAbiContext* context);
extern "C" KernelError _Module_Abort(const KernelAbiContext* context);
```

- 符号名固定为 `_Module_Init` / `_Module_Activate` / `_Module_Abort`（T1.2 链接配方），必须是默认可见性、不被 strip；`PackModule` 从 ELF 符号表取偏移，不解析 C++ 修饰名。
- `_Module_Init` 必须存在且偏移非零；`_Module_Activate` 与 `_Module_Abort` 允许缺失（容器 `EntryActivate` / `EntryAbort` 为 `0`）。
- 调用约定见 6.4；三个入口都返回 `KernelError`（7.1）。

### 6.2 `KernelAbiContext`

上下文是内核→模块的唯一入口参数，**只追加**：首字段是结构长度，既有字段偏移不变，新字段只能追加在尾部。v1 的字节表（32 字节）：

| 偏移 | 字节 | 字段 | 语义 |
| --- | --- | --- | --- |
| `0x00` | 4 | `bytes` | 本结构长度；模块据此判断能读到哪些字段 |
| `0x04` | 2 | `version` | 上下文结构版本，当前 `1` |
| `0x06` | 2 | `kernelAbiVersion` | 当前 `KernelAbiVersion`，与 `Core.Abi` 槽 0 同值 |
| `0x08` | 8 | `moduleBase` | 模块装载映像在当前地址空间的基址；M4 恒等映射下等于物理基址，M6 起是映射后虚拟基址 |
| `0x10` | 16 | `moduleId` | 本模块的 `ModuleId` |

规则：

- 结构只含定宽整数与字节数组，不含函数指针表；模块需要的服务一律经导入接口获得，不塞进上下文。
- 上下文在模块整个生命周期内有效且**只读**；模块可以保存指针，但不得改写，也不得假定 `bytes` 等于本版长度——按 `bytes` 有界读取，读不到的字段按缺失处理。
- 追加字段不改 `version` 的逻辑与既有字段偏移；模块用 `bytes` 与 `version` 双重判断。追加字段不破坏旧模块（旧模块按 `bytes` 忽略新字段），因此不抬 `KernelAbiVersion`；改变既有字段才抬（5.1 第 2 条）。
- 模块不得通过 `moduleBase` 之外的假设定位自身：代码寻址用位置无关（`-fPIC`），指针表放可写段（容器第十节）。

### 6.3 三入口语义与阶段边界

| 入口 | 何时调用 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| `_Module_Init` | 装载步骤 10（容器第十二节）：映射、重定位、导入解析、依赖检查全部通过之后 | 可撤销准备：读设备事实、申请页/DMA、登记对象与绑定、校验硬件 | 不启用 IRQ、不建线程、不启动异步 I/O、不改不可撤销状态、不假定 `Activate` 已调用 |
| `_Module_Activate` | 阶段 3 起，激活条件满足后（线程/IRQ 可用、依赖已激活） | 启用中断、工作队列、异步与后续运行期行为 | 不重新映射、不重新解析导入（容器第十二节第 11 步） |
| `_Module_Abort` | `Init` 返回非 `kOk` 且有入口时 | 撤销 `Init` 已登记的资源、注册与绑定，验证没有残留引用 | 不承担不可逆状态的回滚（按[模块与驱动装载](模块与驱动装载.md) 2.2 第 7 步重启处理） |

- **P5（阶段 0–2）不调用 `_Module_Activate`**：闭包模块只要求 `Init` 与挂卷读路径；`Activate` 的签名与偏移在 v1 就冻结，避免阶段 3 再改 ABI。
- `Init` 成功后装载器才发布该模块的导出接口并登记模块（容器第十二节第 10 步）；`Init` 失败时已登记的归属记录必须可回收，不留下可调用的导出。
- 任何模块代码在交接校验与归属上下文建立之前不执行；入口只由装载器调用，模块不互相调用入口。

### 6.4 调用约定与编译约束

- **调用约定**：x86-64 System V ABI（整数/指针寄存器传参，`u32` 返回值在 `EAX`，栈 16 字节对齐）。模块与内核用同一编译器族与同一批选项编译，不引入第二套约定。
- **禁止跨越边界**：C++ 异常、RTTI、栈展开、红区、TLS、静态构造；浮点与 SIMD 也不得使用（内核不保存 FPU/SSE 状态），由 T1.2 的编译选项落实。
- 模块链接选项、`nm -u` 为空、`.init_array` 为空等硬约束见[模块与驱动装载](模块与驱动装载.md)与计划 6.6；这些不是契约参数，但违反任何一条都会让本文的入口 ABI 失效。

## 七、模块返回码与诊断编号

### 7.1 `KernelError`

模块入口与 `Core.*` / `Dev.Model` / `Drv.Loader` / `Usb.Host` 槽位的返回码，`u32` 底层、`0` 表示成功；存储面（`Block.Registry`、`Fs.Vfs`、`Boot.Volume` 与两类存储 ops 表）统一返回 `Storage::Error`（7.3），两套不混用。取值由生成头 `Types.hpp` 给出（v1）：

| 值 | 名字 | 语义 |
| --- | --- | --- |
| `0` | `kOk` | 成功 |
| `1` | `kNotSupported` | 当前版本/当前实现不支持该操作，调用方不得重试同一调用 |
| `2` | `kInvalidArgument` | 参数非法：空指针、零长度、未对齐、越界、取值不在允许集合 |
| `3` | `kOutOfResources` | 资源不足：页帧、DMA、对象表、句柄表 |
| `4` | `kBusy` | 对象已被占用或操作进行中；调用方可稍后重试 |
| `5` | `kIo` | 底层 I/O 失败 |
| `6` | `kCorrupt` | 结构非法：魔数、校验、范围或环路错误 |
| `7` | `kNotFound` | 对象、设备、路径或版本不存在 |
| `8` | `kPermission` | 设备或卷状态不允许该操作（只读卷写入等） |
| `9` | `kNoSpace` | 空间不足 |
| `10` | `kTimeout` | 有界等待超时 |
| `11` | `kAlreadyExists` | 登记/绑定已存在 |
| `12` | `kVersionMismatch` | 版本不匹配（ABI、接口、驱动契约或格式） |
| `13` | `kState` | 对象状态不允许该操作（未初始化、未挂载、已停止） |

- 生成头同时给出 `KernelErrorName(KernelError)`（返回稳定短名，如 `"kNotSupported"`），供装载器写 `E-KRN` 行的 detail 与模块日志；**名字文本不是编号**。
- 错误码稳定规则：发布后只增不改；追加新值不抬 `KernelAbiVersion`（消费者把未知值按普通失败处理）；改变既有值语义或删除必须抬 `KernelAbiVersion`（5.1 第 3 条）。

### 7.2 与 `E-KRN` 的关系

**模块返回码不产生编号。** 与[内核诊断编号](内核诊断编号.md)第五节对 `Kernel::CheckImageData` 的处理同一原则：机制层只回报原因，编号由调用方按失败点选。

| 场景 | 编号来源 | 输出 |
| --- | --- | --- |
| 必需模块 `Init` 返回非 `kOk` | 装载器选 `E-KRN-59`（必需模块初始化失败；导入/依赖/ABI 失败并入此号，detail 区分子原因） | `FATAL` + 屏幕 + 等待 + 复位；detail 带 `KernelErrorName` 与模块标识 |
| 可选模块 `Init` 返回非 `kOk` | 不占 `E-KRN` 编号 | `WARN` 行，带模块标识、版本与返回码 |
| 槽位调用失败（`KernelError` 或 `Storage::Error` 非成功值） | 由调用方模块按自身策略处理；内核核心的调用点按自身号段（`E-KRN-60–89` 等）在需要失败可见处选号 | 不因一次槽位调用失败自动产生编号 |
| 容器/摘要/ABI 前置失败 | 装载器按容器第十二节的步骤选号（`E-KRN-57/58/59` 等） | 编号在模块 `Init` 之前产生，此时还没有返回码 |

- 模块**不得**写 `[ FATAL ] E-KRN-…` 行、不得自行等待或复位；失败可见性由装载器决定（引导闭包/必需模块 FATAL，可选 WARN）。
- 模块需要输出自身诊断时用 `Core.Log.Code`（第十节），其中的 `code` 是模块命名空间内的审计码，不进入 `E-KRN` 体系，也不参与失败判定。
- 编号的分配、号段规划与源码登记仍以[内核诊断编号](内核诊断编号.md)与 `Diagnostics.hpp` 为单点；本文只固定"谁选号"。

### 7.3 与 `Storage::Error` 的关系

- 存储层的错误模型由[文件系统抽象与VFS](Common/文件系统抽象与VFS.md) 3.1 定义（`Storage::Error`，`int32_t` 底层、数值是稳定编号），块设备、文件系统与 VFS 的跨模块调用沿用该枚举；本文不复制、不另造一套文件系统错误码。
- 边界划分固定为：`KernelError`（`u32`）用于模块入口（`_Module_Init` / `_Module_Activate` / `_Module_Abort`）、`Core.*`、`Dev.Model`、`Drv.Loader` 与 `Usb.Host`；`Storage::Error` 用于 `Block.Registry`、`Fs.Vfs`、`Boot.Volume` 的槽位与 `BlockDeviceOps` / `FileSystemOps` 的全部回调。两套都是稳定编号，各自面上使用、不混用。
- 需要把存储面失败归一为 `KernelError` 的地方（装载器 detail、模块入口把底层失败收敛）只有一张固定映射表（生成头提供 `KernelErrorFromStorage`）：

| `Storage::Error` | `KernelError` |
| --- | --- |
| `Ok` | `kOk` |
| `NotFound` | `kNotFound` |
| `NotDirectory` / `IsDirectory` / `InvalidArgument` / `NameTooLong` | `kInvalidArgument` |
| `NotSupported` | `kNotSupported` |
| `Corrupt` | `kCorrupt` |
| `Io` | `kIo` |
| `ReadOnly` | `kPermission` |
| `NoSpace` | `kNoSpace` |

- 两套枚举都是稳定编号：改语义走各自规格的版本规则，不就地改写（VFS 规格 3.1 末段）。模块内部不得定义第三套跨边界错误码。

### 7.4 稳定规则

- 首次发布前（T5.1 之前）取值可调整；发布后只增不改（与[内核诊断编号](内核诊断编号.md)第二节同原则）。
- 生成物里的 `KernelError` 值不得由模块源码重定义；模块只能引用生成头常量。
- 回归按值断言，不按错误文本子串断言。

## 八、驱动契约（DriveSDK 内核面）

### 8.1 定位

[ABI 兼容与外部契约](Common/ABI兼容与外部契约.md)第一节把 DriveSDK 列为外部稳定调用表：驱动不包含内核私有头，也不直接绑定具体 `.osm` 的符号。本文只定义 DriveSDK 的**内核面**——驱动与文件系统模块在内核里怎样被登记、怎样提供 ops；驱动对硬件的行为语义由[文件系统抽象与VFS](Common/文件系统抽象与VFS.md)与设备模型规格定义。

分工：

| 内容 | 单点 |
| --- | --- |
| `BlockDeviceOps` / `FileSystemOps` / `DriverDesc` 的槽位布局、字节表、版本 | 本文 |
| 块设备行为（块大小、对齐、读写、错误码） | [文件系统抽象与VFS](Common/文件系统抽象与VFS.md) 3.2 |
| 偏移视图与路径语义 | 同规格 3.3、3.5；挂载点裁剪由 VFS 负责，裁掉挂载点后交给 FS ops 的是卷内绝对路径 |
| 文件系统行为（挂载探测、能力位、路径查找、读取、卷标识） | 同规格 3.4；卷标识查询归文件系统模块（`FileSystemOps.VolumeIdentity`，8.4），块设备层只透传候选 |
| 设备枚举、资源分配、绑定与匹配 | [模块与驱动装载](模块与驱动装载.md)与引导闭包实现（T5.2/T5.3） |

ops 表**不是**容器接口：它们不分配 `InterfaceId`、不进容器的导出/导入表，版本由 `DriveSDKVersion` 表达，实例经单例接口的注册槽传入（4.4）。

### 8.2 `DriveSDKVersion`

- `u16`，当前值 `1`，生成头常量 `kDriveSdkVersion`，由 `Core.Abi` 槽 2 发布（5.2）。
- 与 `KernelAbiVersion` 独立：ops 表或 `DriverDesc` 的**既有布局**（字段偏移、类型、语义）变化抬 `DriveSDKVersion`，不抬 `KernelAbiVersion`；尾部追加字段按 `bytes` 有界读取、不抬版。入口/上下文/错误码变化抬 `KernelAbiVersion`，不抬 `DriveSDKVersion`。两者同时改变时才同时抬。
- 驱动声明自己实现的 `DriveSDKVersion`（`DriverDesc.driveSdkVersion`）；`DriverLoader.RegisterDriver` 比对当前值，不相等即拒绝登记并返回 `kVersionMismatch`，不"尽力绑定"。
- 文件系统模块不经过 `DriverDesc`：它直接调 `Fs.Vfs.RegisterFileSystem`，但 `FileSystemOps` 的布局同样受 `DriveSDKVersion` 约束；`Fs.Vfs` 在登记时按当前 `kDriveSdkVersion` 核对（v1 下两者同版，见 8.4 末条）。

### 8.3 `BlockDeviceOps` v1

块设备实现的调用表，字段与 `Storage::BlockDevice` 的公开方法对应：`HasFlushPrimitive()` 以能力位 `capabilities.bit0` 表达（不是函数槽），其余方法一一对应；语义（块大小必须为 2 的幂、偏移对齐、长度是块整数倍、不缓存不重试）见[文件系统抽象与VFS](Common/文件系统抽象与VFS.md) 3.2。所有回调第一个参数是登记时给的 `context`。首字段是能力位而不是函数指针：

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `capabilities` | `uint32_t` | 能力位：`bit0` = `kBlockCapabilityFlushPrimitive`（设备有真实刷新原语，对应 `Storage::BlockDevice::HasFlushPrimitive()`）；未置位时 `Flush` 可为空，`Block.Registry` 按"无缓存"处理、不调用 |
| `BlockBytes` | `uint32_t (*)(void* context)` | 逻辑块大小，字节；必须为 2 的幂，未绑定返回 `0` |
| `CapacityBytes` | `uint64_t (*)(void* context)` | 设备容量，字节 |
| `Writable` | `uint32_t (*)(void* context)` | 是否可写；`0` 只读，非 `0` 可写（C 调用面用 `u32` 表示布尔） |
| `Read` | `Storage::Error (*)(void* context, uint64_t, void*, uint32_t)` | 读 `[offset, offset+bytes)` 到调用方缓冲 |
| `Write` | `Storage::Error (*)(void* context, uint64_t, const void*, uint32_t)` | 写；只读设备返回 `ReadOnly` |
| `Flush` | `Storage::Error (*)(void* context)` | 刷新写缓存；无缓存返回 `Ok`；能力位未置位时允许为空 |

### 8.4 `FileSystemOps` v1

文件系统实现的登记表，槽位与 `Storage::FileSystem` 的公开方法对应，另加卷标识查询（归文件系统模块，不在 `Fs.Vfs` 面另立槽位）；语义（`Mount` 兼格式探测、能力位、统一路径语法、逐段遍历）见[文件系统抽象与VFS](Common/文件系统抽象与VFS.md) 3.4、3.5。

| 槽 | 名称 | 签名 | 语义 |
| --- | --- | --- | --- |
| 0 | `Format` | `const char* (void*)` | 格式名，诊断用，如 `"ext4"`；未实现返回 `"unknown"` |
| 1 | `Mount` | `Storage::Error (void*, const BlockDeviceOps*, void*, uint32_t)` | 识别并挂载设备；第二参数是设备 ops、第三参数是设备实例 `context`、第四参数取值同 `Storage::MountMode`；挂载成功后 `VolumeIdentity` 才有效 |
| 2 | `Unmount` | `void (void*)` | 卸载并释放对设备的引用 |
| 3 | `Caps` | `void (void*, Storage::FileSystemCaps*)` | 回报实现能力位 |
| 4 | `VolumeIdentity` | `Storage::Error (void*, uint8_t*)` | 写 16 字节卷标识（Ext4 `s_uuid` 原字节），挂载成功后有效；块设备层只透传候选、不解析 superblock |
| 5 | `Stat` | `Storage::Error (void*, const char*, Storage::FileInfo*)` | 按路径查询事实 |
| 6 | `Open` | `Storage::Error (void*, const char*, uint64_t*)` | 按路径解析对象标识；目录不算错误 |
| 7 | `Read` | `Storage::Error (void*, uint64_t, uint64_t, void*, uint32_t, uint32_t*)` | 从偏移读至多 bytes，带回实际长度；读到文件尾返回 `Ok` 且长度为 `0` |
| 8 | `ReadDirectory` | `Storage::Error (void*, uint64_t, uint64_t*, char*, uint32_t, uint32_t*, Storage::FileInfo*)` | 游标式目录遍历；结束返回 `NotFound` |

`Format` / `Unmount` / `Caps` / `VolumeIdentity` 等函数指针不能为空：注册时 `Fs.Vfs` 检查非空，缺项即拒绝登记（`Storage::Error::InvalidArgument`）；默认行为的实现由模块负责，契约层不提供缺省回调。

**挂载点裁剪由 VFS 负责。** VFS 把挂载点从绝对路径裁掉后，交给 FS ops 的是**卷内绝对路径**：与共用 `Storage/Path.hpp` 的 `PathRules` 同一套语法（`/` 分隔、分量非空、不含 `.`/`..`、非 ASCII 原字节、不做大小写折叠），FS 实现不得再假设挂载点前缀。路径语法与遍历语义的单点是 VFS 规格 3.5，本表只定签名。

`FileSystemOps` 的布局版本与 `BlockDeviceOps` 同步（同一个 `DriveSDKVersion`）；本表不携带版本字段，版本由登记时当前的 `kDriveSdkVersion` 隐含；两者需要分开演进时另立接口版本，不改本表。

### 8.5 `DriverDesc` v1

驱动描述由驱动模块在 `Init` 里构造并登记，字节表固定（64 字节）：

| 偏移 | 字节 | 字段 | 语义 |
| --- | --- | --- | --- |
| `0x00` | 4 | `bytes` | 结构长度，当前 `0x40`；追加字段时增长 |
| `0x04` | 2 | `driveSdkVersion` | 驱动实现的 DriveSDK 版本 |
| `0x06` | 2 | `opsKind` | 提供的能力类别：`1` = `BlockDeviceOps`；其他值拒绝 |
| `0x08` | 4 | `busKind` | 匹配的总线类别（取值同 `DeviceFacts.busKind`）；`0` 通配 |
| `0x0C` | 4 | `classCode` | 匹配的设备类码；`0xFFFFFFFF` 通配 |
| `0x10` | 4 | `vendorId` | 匹配的厂商 ID；`0xFFFF` 通配 |
| `0x14` | 4 | `deviceId` | 匹配的设备 ID；`0xFFFFFFFF` 通配 |
| `0x18` | 8 | `flags` | 保留，当前 `0`；非零拒绝 |
| `0x20` | 8 | `start` | 启用回调 `Storage::Error (*)(void* context)`；由 `Drv.Loader.Start` 调用，只启用同步服务，不启用中断/异步（阶段 3） |
| `0x28` | 8 | `stop` | 停用回调 `void (*)(void* context)`；由 `Drv.Loader.Stop` 调用，排空后执行 |
| `0x30` | 8 | `ops` | ops 表指针（v1 指向 `BlockDeviceOps`） |
| `0x38` | 8 | `context` | 驱动实例上下文，回调原样传回；多实例靠它区分 |
| `0x40` | — | — | 追加区（后续版本）；`bytes` 之外不得假设长度 |

版本字段即 `driveSdkVersion`，其变化由 8.2 判定。`DriverDesc` 首字段是 `bytes`，尾部追加字段按长度有界读取（旧实现忽略新字段），不抬 `DriveSDKVersion`；既有字段的偏移、类型或语义变化才抬版。

### 8.6 注册与绑定路径

```text
初始化序（引导闭包）：DevModel → DriverLoader → 启动驱动 → Vfs → Ext4 / ISO9660 / FAT32File → 挂载系统卷（Boot.Volume）

驱动模块 Init：
  构造 DriverDesc（driveSdkVersion + 匹配事实 + start/stop + ops + context）
  → Dev.Model.BootCandidates / Enumerate 取设备事实
  → Drv.Loader.RegisterDriver(desc) → Drv.Loader.Bind(deviceHandle, desc, &binding)
DriverLoader：
  绑定成功 → 把绑定事实写进 Dev.Model（设备句柄 + ops + context + 状态）
装载编排（内核核心，模块 Init 之间）：
  对每个已绑定驱动调 Drv.Loader.Start(binding) → 驱动 start 回调 → 设备进入可服务状态
Vfs 模块 Init：
  从 Dev.Model 取绑定事实 → 内部块设备层用 Block.Registry.Publish 登记设备句柄 → ops/context
Filesystem 模块 Init（Ext4 / ISO9660 / FAT32File）：
  Fs.Vfs.RegisterFileSystem(ops, context, &registration)
Boot.Volume（内核装载编排调用、Vfs 模块实现，挂载阶段）：
  按 BootInfo 线索取候选设备 → Fs.Vfs.Mount(registration, deviceHandle, "/", ReadOnly)
  → 文件系统模块 VolumeIdentity 核对 BootInfo.volumeUuid
```

- **驱动不依赖 Vfs**（[内核架构与自举闭包](内核架构与自举闭包.md) 6.3 与[模块与驱动装载](模块与驱动装载.md) 2.2）：驱动只导入 `Core.*`、`Dev.Model`、`Drv.Loader`，把 `BlockDeviceOps` 经 `Drv.Loader.Bind` 登记进 DevModel；**`Block.Registry.Publish` 的唯一调用者是 Vfs 模块内部的块设备层**，在 Vfs 的 `Init` 里按 DevModel 绑定事实登记设备。驱动、文件系统模块与内核核心都不调用 `Publish`；保留该槽是为了把"设备句柄 → ops/context"的登记语义固定在接口面上，测试与后续热替换路径复用同一槽。
- 该顺序同时满足容器第十二节第 10 步（`Init` 成功后才发布导出接口）与 P5 计划 6.3：`Vfs` 必须先完成 `Init` 才能被文件系统模块导入，而挂载必须等驱动 `Start` 与文件系统登记都结束，所以 `Boot.Volume` 落在最后。
- 同一设备同一时刻只能有一个有效控制者（[模块与驱动装载](模块与驱动装载.md)第三节）：`Bind` 前 `Dev.Model.Claim` 认领，重复认领返回 `kBusy`。
- 驱动模块与文件系统模块**不导出** `Dev.Model` / `Drv.Loader` / `Block.Registry` / `Fs.Vfs` / `Boot.Volume`；生成器在构建期拒绝（4.3 提供者表）。
- 外部 `.drv` 与引导闭包驱动共用同一 `DriverDesc` 与 ops 表，属于阶段 3 以后的能力（第十一节 11.4）；本阶段 `.drv` 登记路径返回 `kNotSupported` 并 `WARN`（T5.3）。

### 8.7 不导出单例

**驱动与文件系统模块只导入单例、注册 ops，不导出同名接口。** 这条规则是 4.3 提供者唯一的直接推论：多实例能力如果各导出同名接口，提供者唯一立即被破坏；如果给每个实例发新接口名，接口数量随设备数增长，版本管理失控。正确形态固定为：单例接口（唯一提供者）+ 注册槽 + ops 结构体 + `context`。

| `Abi.hpp` | `kKernelAbiVersion`、`kDriveSdkVersion`、`Core.Abi` 槽绑定与 `static_assert` | 装载器、模块、注册表 |
| `<模块>Tables.cpp` | 该模块的 `_Contract_ModuleTables` 常量定义（导出/导入条目表 + 槽位指针），由模块构建编译进模块 | `PackModule`（按固定符号取表） |

`ModuleTables` 与容器表项同构，但**在内存里**：`PackModule` 负责把内存表翻译成容器字节（槽位表偏移、回填表偏移、版本区间），装载器只按容器表工作。表项结构（v1）：

```cpp
struct ModuleExportEntry { InterfaceId id; uint16_t version; uint16_t slotCount; const void* slots; };
struct ModuleImportEntry { InterfaceId id; uint16_t minVersion; uint16_t maxVersion; uint16_t slotCount; void* slots; };
struct ModuleTables {
    uint32_t bytes;                      // 结构长度
    uint16_t exportCount;                // 导出条目数
    uint16_t importCount;                // 导入条目数
    const ModuleExportEntry* exports;    // 导出条目数组
    const ModuleImportEntry* imports;    // 导入条目数组
};
```

### 9.2 引入方式与构建顺序

- 需要契约的包在编译选项里加入生成目录：内核核心 `-I$(COMMON_DIR)/Out/Contract`；模块包按 T1.7 骨架同法；`PackModule` 等宿主工具按自己的 `COMMON_DIR` 同理。
- 生成头不提交（`Out/` 被 `.gitignore` 忽略）；输入 `.def` 与冻结表提交。
- 构建顺序固定：先跑 `MakeContract` 生成 `Out/Contract/`，再编译内核核心、模块与 `PackModule`；`make clean` 一并删除生成目录。
- `reproducible-check`（T1.5）把生成头与模块表字节纳入交付物比对：同一 `.def` 必须生成逐字节相同的结果。

### 9.3 确定性

生成器不得写入时间戳、构建路径、用户名、环境信息或随机顺序：输出顺序由 `.def` 的文件顺序与本文排序规则决定，保留字段固定，同一输入产出同样字节。生成的 `static_assert` 文本、错误文本也不含路径。

### 9.4 构建期检查

`MakeContract` 生成时执行下列检查，任一失败即非零退出（构建立即失败，不产出半套生成物）；运行时一致性由 T4.4 `CheckRegistry` 与 `PackModule --verify`（T1.3）覆盖。

| 检查 | 判定 | 失败后果 |
| --- | --- | --- |
| 名称语法 | 稳定名/逻辑名符合 3.3，长度与字符集合法 | 生成失败 |
| 排序与分组 | 稳定名字节序、版本升序、版本块内槽行连续 | 生成失败 |
| 值域 | 版本 `1..65534`、槽数 `1..64`、槽名唯一、签名合法、无空行注释 | 生成失败 |
| 追加兼容 | 同接口 `v(N+1)` 的前 `SlotCount(vN)` 个槽与 `vN` 逐槽同名同签名、槽数不得减少（已实现并验证：`Dev.Model` v2 正例通过、负例报错带行号） | 生成失败 |
| 冻结比对 | `Frozen.tsv` 中已发布版本块与当前定义摘要一致 | 生成失败 |
| 提供者唯一 | 内核核心导出 + 所有模块 `CONTRACT_EXPORTS` 合并后无重复 `(InterfaceId, Version)` | 生成失败 |
| 单例提供者固定 | 6 个闭包单例接口（`Dev.Model`（v1/v2）、`Drv.Loader`、`Block.Registry`、`Fs.Vfs`、`Boot.Volume`、`Usb.Host`）的提供者与 4.3 表一致；驱动/文件系统/USB 模块未导出单例 | 生成失败 |
| 导入区间可满足 | `MinVersion <= MaxVersion`；本次构建的提供者集合中存在满足区间的版本；使用槽数不超该版本槽数 | 生成失败 |
| 闭包表 | 13 行、序号连续、逻辑名唯一、`ModuleId` 不重复 | 生成失败 |
| ABI 绑定 | `Core.Abi` 版本块存在且槽 0/2 签名正确；`kKernelAbiVersion`/`kDriveSdkVersion` 与导出表登记值一致 | 生成失败或 `CheckRegistry` 失败 |
| 入口符号 | 模块存在 `_Module_Init` 且偏移非零、落在 `TEXT`；`_Module_Activate`/`_Module_Abort` 可缺省 | `PackModule --verify` / `CheckOsm` 失败 |
| 符号表干净 | 模块 `nm -u` 为空、无 TLS、`.init_array` 为空、除入口与契约表符号外无 `extern "C"` 全局符号 | T1.2 / `CheckOsm` 失败 |

### 9.5 模块侧硬约束（与契约相关）

- 跨模块调用只能经导入表回填的函数指针；不得直接引用内核核心符号、其他模块符号或固定地址。
- 唯一允许的导出符号：三个入口、`_Contract_ModuleTables`、提供者槽位表符号（`_Contract_Export_<接口>_v<版本>`）；不得导出其他全局符号绕过接口表。
- 与内核共享契约头：只 include 生成头与 `Packages/Common/Include/` 下的手写契约头，不 include 内核私有头。
- `ModuleTables` 与生成头不一致（缺条目、多条目、版本区间与声明不符）由 `PackModule --verify` 拒绝。

## 十、接口清单与槽位语义

### 10.0 基础类型与阶段标注

**类型规则**：槽位参数与返回值只用 6.1 签名允许的类型；结构按值不传，一律传指针。句柄统一为 `uint32_t` 的强类型别名，`0` 表示无效：`DeviceHandle`（块设备与子设备也用它，不另编号）、`ClaimHandle`、`BindHandle`、`FileSystemId`（登记 id）、`ObjectHandle`、`ControllerHandle`（USB 控制器，10.2）、`UsbDeviceHandle`（USB 设备）、`ClassHandle`（USB 类登记）；文件引用是 VFS 自有的不透明 `uint64_t`（`Open` 返回，`Read`/`Close` 使用），不是句柄表项。

**可扩展结构**：首字段为 `uint32_t bytes` 的契约结构（`DeviceFacts`、`DeviceResources`、`BindingFacts`、`SystemVolumeFacts`、`UsbDeviceFacts`、`KernelAbiContext`、`DriverDesc`、`ModuleTables`）按长度有界读取，尾部可追加字段；追加不改变既有字段偏移，也不抬接口版本，但追加字段的语义要登记在生成头的 `static_assert` 与本节。其余结构（ops 表、`<接口>Slots`、`UsbSetupPacket`、`UsbControllerOps`、`UsbClassOps`）是固定结构，布局随版本冻结。

**阶段标注**（读法）：

| 标注 | 含义 |
| --- | --- |
| `M4` | M4 装载器与注册表就绪后可用；此时模块基址用恒等映射 |
| `M4→M6` | 签名与语义不变；M4 在直映射上实现，M6 起走 4 KiB 映射。这是唯一需要 4 KiB 映射（M6）才完整的一组槽位 |
| `M5` | 挂载系统卷阶段可用（引导闭包初始化序）；运行期模块在挂载后才可能使用 |
| `M6` | G6c USB 闭包链可用：控制器注册、类登记、同步轮询与设备事实；不依赖 4 KiB 映射 |

**契约不承诺"物理地址即指针"**：M4 的恒等映射让 `Core.Page.Allocate` 返回的物理地址恰好可直接解引用，M6 起必须经 `Core.PhysMap.ToVirt`。模块不得把物理地址转成指针，除非同时限定了 M4 阶段（且不得把该假设写进跨阶段数据结构）。模块段权限、W^X 与 NX 属装载器实现（M6），不是契约槽位。

### 10.2 引导闭包单例导出（6 个接口：5 个 `M5` + `Usb.Host` `M6`）

提供者固定（4.3），消费者按依赖序在 `Init` 里导入；驱动、文件系统与 USB 类模块只导入这些接口并注册 ops，不导出它们。返回码按 7.3 分面：`Dev.Model` / `Drv.Loader` / `Usb.Host` 返回 `KernelError`，`Block.Registry` / `Fs.Vfs` / `Boot.Volume` 返回 `Storage::Error`（存储面，数值是共用稳定编号）。

#### `Dev.Model` v1（6 槽）与 v2（7 槽，提供者 `DevModel`）

`DevModel` 是设备模型的唯一提供者，同时导出 v1 与 v2（同一 `InterfaceId`、不同 `Version`；提供者唯一按版本逐条计算）。v1 六个槽保持原序原签名，v2 只在尾部追加槽 6：

| 槽 | 槽名 | 签名 | 语义 |
| --- | --- | --- | --- |
| 0 | `Enumerate` | `KernelError (uint32_t*, DeviceFacts*)` | 枚举设备；`cursor` 从 `0` 起，`facts` 带回句柄与事实，结束返回 `kNotFound` |
| 1 | `Resources` | `KernelError (uint32_t, DeviceResources*)` | 取设备资源事实（BAR、IRQ、DMA 约束） |
| 2 | `Claim` | `KernelError (uint32_t, uint32_t, uint32_t*)` | 认领设备唯一控制权，返回 `ClaimHandle`；已有控制者返回 `kBusy` |
| 3 | `Release` | `KernelError (uint32_t)` | 归还控制权 |
| 4 | `BootCandidates` | `KernelError (uint32_t*, uint32_t*)` | 按 `BootInfo` 启动线索枚举候选设备；线索不可解析时退回全量枚举并报告，不猜设备 |
| 5 | `Binding` | `KernelError (uint32_t, BindingFacts*)` | 取设备当前绑定事实；未绑定返回 `kNotFound` |
| 6 | `Register`（v2 追加） | `KernelError (const DeviceFacts*, uint32_t*)` | 把 USB 等枚举发现的设备登记进设备树，第二参数带回设备句柄；未经枚举到达的设备不得登记 |

- **v1 消费者不变**：`Vfs` 继续导入 `Dev.Model:1:1:6`，按区间选择时取到 v1，不会误用槽 6；新消费者声明 `Dev.Model:2:2:7` 才使用 `Register`（使用槽数不得超过所选版本槽数，4.5）。

- v2 的追加只发生在尾部、槽 0–5 与 v1 逐槽同名同签名，属 4.2 允许的兼容追加，不抬 `KernelAbiVersion`（5.1）。

`DeviceFacts` v1（可扩展，`bytes` 首字段）：`deviceHandle`、`busKind`、`classCode`、`vendorId`、`deviceId` 与总线地址事实；总线地址的编码由设备模型规格（T5.2）定义，本结构只承载不解释。`DeviceResources` v1（可扩展）：BAR 表（索引、标志、基址、长度）、IRQ 表与 DMA 地址位宽约束。`BindingFacts` v1（可扩展）：绑定句柄、设备句柄、驱动模块 `ModuleId`、状态位、`BlockDeviceOps*` 与实例 `context`（`Start` 成功后有效），Vfs 的块设备层据此登记设备，不再反查驱动模块。

| 2 | `ControlTransfer` | `KernelError (uint32_t, const UsbSetupPacket*, void*, uint32_t, uint32_t*)` | 对设备句柄发起控制传输，最后一个参数带回实际字节数 |
| 3 | `BulkTransfer` | `KernelError (uint32_t, uint32_t, void*, uint32_t, uint32_t*)` | 对设备句柄的端点发起批量传输，带回实际字节数 |
| 4 | `Poll` | `KernelError (uint32_t)` | 推进枚举与完成事件；参数为本阶段最多完成的数目，由内核编排在模块 `Init` 之间调用 |
| 5 | `DeviceFacts` | `KernelError (uint32_t, UsbDeviceFacts*)` | 取设备事实（40 字节可扩展结构） |

**USB 链注册序**（对应引导闭包初始化序 `UsbCore → Xhci → UsbHub / UsbStorage`）：

```text
UsbCore Init：建立控制器表、类表与设备表（可撤销准备）
Xhci Init：构造 UsbControllerOps + 实例 context
  → Usb.Host.AddController(&controllerHandle, ops, context)
内核编排（各模块 Init 之间）：Usb.Host.Poll(budget) 推进枚举
  → UsbCore 分配设备地址 → 控制器 EnableDevice
UsbHub / UsbStorage Init：Usb.Host.RegisterClass(class, classOps, context, &classHandle)
UsbCore 枚举到设备后：按 classCode 分发给已登记类 → 类 Probe / Bind
  → 新设备经 Dev.Model v2 槽 6 Register(facts, &deviceHandle) 登记进设备树
```

- `Usb.Host` 的唯一提供者是 `UsbCore`（4.3）；`Xhci`、`UsbHub`、`UsbStorage` 只导入 `Usb.Host` 并按槽注册，不导出 `Usb.Host`，也不导出块设备/文件系统单例。
- 枚举与传输的完成推进靠 `Poll` 显式轮询（阶段 3 之前不启用中断/异步）；`Poll` 只由内核编排在模块 `Init` 之间调用，模块之间不互调。
- USB 设备进入设备树后，需要块设备 I/O 的消费者按既有单例接口路径接入（`Dev.Model` 绑定 + `Block.Registry`）；`Usb.Host` 本身不提供块设备 I/O，也不涉及 `DriveSDKVersion`。
- 结构字段（`UsbSetupPacket` 8 字节、`UsbDeviceFacts` 40 字节、`UsbControllerOps` 8 个函数指针、`UsbClassOps` 3 个函数指针）与句柄别名见 9.1 与生成头 `Types.hpp`；这些结构属 `Usb.Host` v1 接口版本的一部分，布局变更必须发新接口版本，不抬 `KernelAbiVersion`，也与 `DriveSDKVersion` 无关。

#### `Block.Registry` v1（4 槽，提供者 `Vfs`）

设备是注册表条目而不是接口实例：块设备与子设备都不另发句柄，直接用 `Dev.Model` 的设备句柄（`DeviceHandle`）标识；本阶段句柄不注销、不热替换。

| 槽 | 槽名 | 签名 | 语义 |
| --- | --- | --- | --- |
| 0 | `Publish` | `Storage::Error (DeviceHandle, const BlockDeviceOps*, void*, uint32_t)` | 把设备句柄与 ops/context 登记进块设备注册表；**调用者固定为 Vfs 模块内部的块设备层**（Vfs `Init` 时按 DevModel 绑定事实登记），驱动、文件系统模块与内核核心都不调用；`flags` 当前 `0`，非零拒绝 |
| 1 | `SubDevice` | `Storage::Error (DeviceHandle, uint64_t, uint64_t, uint32_t, DeviceHandle*)` | 建立偏移视图子设备：`begin` 按底层块对齐、区间非空不越界，`flags` 当前必须为 `0`（非零拒绝，后续版本再定义视图标志），返回同类型子设备句柄；对应 VFS 规格 3.3 |
| 2 | `Acquire` | `Storage::Error (DeviceHandle, const BlockDeviceOps**, void**)` | 取得设备使用权，带回 ops 表与实例 `context`；调用方据此直接发 I/O |
| 3 | `Release` | `Storage::Error (DeviceHandle)` | 归还使用权 |

#### `Fs.Vfs` v1（8 槽，提供者 `Vfs`）

v1 在计划 6.2 草案的 7 个槽之外补入 `ReadDirectory`（T5.6 验证要求「列出根目录」，草案漏列）；其余槽位与草案同名同序。挂载点与卸载按路径字符串，文件引用是 VFS 自有的不透明 `uint64_t`。

| 槽 | 槽名 | 签名 | 语义 |
| --- | --- | --- | --- |
| 0 | `RegisterFileSystem` | `Storage::Error (const FileSystemOps*, void*, FileSystemId*)` | 登记文件系统实现（实例由 `context` 承载），带回注册 id |
| 1 | `Mount` | `Storage::Error (FileSystemId, DeviceHandle, const char*, uint32_t)` | 把实现挂载到块设备：第三参数是挂载点绝对路径（本阶段只接受 `/`），第四参数取值同 `Storage::MountMode`（本阶段只接受只读） |
| 2 | `Unmount` | `Storage::Error (const char*)` | 按挂载点路径卸载 |
| 3 | `Stat` | `Storage::Error (const char*, Storage::FileInfo*)` | 按绝对路径取对象事实（路径语法见 VFS 规格 3.5） |
| 4 | `Open` | `Storage::Error (const char*, uint64_t*)` | 按绝对路径打开，返回不透明文件引用 |
| 5 | `Read` | `Storage::Error (uint64_t, uint64_t, void*, uint32_t, uint32_t*)` | 从偏移读至多 bytes，带回实际长度 |
| 6 | `Close` | `Storage::Error (uint64_t)` | 关闭文件引用 |
| 7 | `ReadDirectory` | `Storage::Error (uint64_t, uint64_t*, char*, uint32_t, uint32_t*, Storage::FileInfo*)` | 游标式目录遍历，返回下一项的名字与事实；结束返回 `NotFound` |

#### `Boot.Volume` v1（1 槽，提供者 `Vfs`）

| 槽 | 槽名 | 签名 | 语义 |
| --- | --- | --- | --- |
| 0 | `MountSystemVolume` | `Storage::Error (const Boot::Info*, SystemVolumeFacts*)` | 按 `BootInfo` 的卷偏移、卷标识与内核集标识校验并挂载系统卷到 `/`；卷标识查询走文件系统模块的 `VolumeIdentity`（8.4），本槽不另设查询面；失败不挂载、不猜卷、不回退 |

`SystemVolumeFacts` v1（可扩展）：`volumeUuid[16]` 与 `buildId[32]`，供挂载后诊断与归属记录使用；卸载按挂载点路径（`Fs.Vfs.Unmount`），不设挂载句柄。

### 10.3 驱动契约（不属于接口清单）

`BlockDeviceOps`、`FileSystemOps`、`DriverDesc` 按第八节定义，不分配 `InterfaceId`、不进容器导出/导入表、不占本节槽位；它们的布局版本是 `DriveSDKVersion`，实例经 `Publish` / `RegisterFileSystem` / `RegisterDriver` 登记。

## 十一、发布、兼容与退役

### 11.1 发布判据

一个接口版本"已发布"指：它进入一个发布线 `BuildId` 的内核集并随基线提交，同时其行被写入 `Frozen.tsv`。首次发布是 T5.1 的 v1 冻结；在此之前（M1–M4 开发期）同一版本号内可增删改槽位，按[ABI 兼容与外部契约](Common/ABI兼容与外部契约.md)第二节第 7 条不构成兼容性变更。

### 11.2 变更矩阵

| 变更 | 动作 | 是否抬版本 |
| --- | --- | --- |
| 接口尾部追加槽位 | 发新接口版本，保留旧版本导出 | 接口版本 `+1`；不抬 `KernelAbiVersion` / `DriveSDKVersion` |
| 修改既有槽的签名或语义 | 新建接口稳定名，旧接口保留到退役窗口 | 新 `InterfaceId`；不抬 `KernelAbiVersion` |
| 新增内核核心服务接口 | 新稳定名新版本，消费者按导入声明使用 | 不抬 `KernelAbiVersion` |
| 移除 `Core.*` 接口 | 退役窗口结束；同步抬内核 ABI | 抬 `KernelAbiVersion` |
| 入口签名、`KernelAbiContext` 既有字段、`KernelError` 语义变化 | 同步改三处并登记 | 抬 `KernelAbiVersion` |
| ops 表或 `DriverDesc` 既有布局变化 | 新 `DriveSDKVersion`，驱动声明新版本；尾部追加字段不抬版 | 抬 `DriveSDKVersion` |
| 容器字节布局变化 | 按容器规格抬格式 `Version` | 容器 `Version`（与本文独立） |
| 闭包成员变化 | 改规格与期望集，重新走 M0 冻结 | 不是版本问题，是发布内容变更 |

### 11.3 兼容窗口与退役

- 保险窗口至少保留上一发行世代的接口版本（容器 14.3 第 5 条）：旧版本导出由同一提供者继续提供，旧消费者按自己的 `Min/Max` 仍能选中。
- 移除旧版本必须伴随 `KernelAbiVersion` 抬升，并同步调整消费模块的 `KernelAbiMin`；不提供"删除但仍能选中"的隐式回退。
- 接口退役日程属发行策略（容器第十六节最后一行）；本文只固定"退役必须抬 ABI + 保留窗口"这条规则。

### 11.4 P5 之外的登记（不是本文的未定项）

下列能力属于后续阶段，本文已把它们的**接口形状与版本槽位**预留好，因此不构成契约层的未定项：

| 能力 | 归属 | 契约层现状 |
| --- | --- | --- |
| 调度/IRQ/异步启用、驱动中断模式 | 阶段 3 | `_Module_Activate` 签名与 `EntryActivate` 偏移已冻结；本阶段不调用 |
| 外部 `.drv` 装载与热替换 | 阶段 3 以后 | `DriverDesc` 与 ops 表已定义；`.drv` 登记本阶段返回 `kNotSupported` + `WARN` |
| Objects 完整能力、用户句柄、命名空间 | 阶段 4 以后 | `Core.Object` 只定最小面（登记/代际/归属/释放） |
| Ext4 写入、日志回放、FAT32 写入 | 阶段 3 以后 | `FileSystemOps` 已含 `Mount` 模式与 `Caps` 可写位；能力随实现启用 |
| 接口废弃日程 | 发行策略 | 11.3 已固定规则 |
| DriveSDK 对外发布形态（`.dso`/`.arc` 打包） | 随 SDK 阶段 | 本文只定内核面布局；交付形态见[后缀设计](后缀设计.md) 5.13 |

本文在 P5 范围内**没有待定项**：容器规格第十六节中"打包器与工具链""内核 ABI 版本的导出位置"两项由本文第二、三、五、九节消除；其余未定项属于其它规格（重定位类型、虚拟基址分配、段权限、`.drv` 容器、Updater 事务、接口废弃日程、可选模块策略），与本契约层无交叉。

## 十三、外部依据

以下资料用于对照接口版本化与槽位约定的工程实践。**本项目契约与它们不共用格式、不承诺兼容**，只借鉴三点：槽位表按版本冻结、消费者按版本区间选择、ABI 闸门与接口版本分离。

- ELF gABI：<https://refspecs.linuxfoundation.org/elf/gabi4+/contents.html>（符号表与重定位的基本约定，对照"不用 C++ 符号名、用二进制 ID 解析跨模块调用"）。

- System V Application Binary Interface, AMD64 Architecture Processor Supplement: <https://refspecs.linuxfoundation.org/elf/x86_64-abi-0.99.pdf>（入口调用约定、寄存器与栈对齐的依据）。
- Microsoft COM `IUnknown`：<https://learn.microsoft.com/en-us/windows/win32/api/unknwn/nn-unknwn-iunknown>（vtable 槽位与接口版本约定的对照）。
- Linux 内核模块构建与签名文档：<https://www.kernel.org/doc/html/latest/kbuild/modules.html>、<https://www.kernel.org/doc/html/latest/kbuild/module-signing.html>（模块与内核版本绑定、完整性与信任链分离的对照）。
