# Baleen Stub — 约定与结构草案

`Stub` 是 BIOS 路径中承接 IPL 的实模式服务层。**本目录目前没有功能实现、构建规则或真实的 `BaleenStub.bin`**；本文只定义职责和未来结构草案，不增加可执行占位件，也不将草案强加给当前测试载荷。`Include` 暂不增加代码定义，待格式定稿与实现同步时再建立唯一的机器可读定义。

IPL 的当前行为以 [Baleen 一级引导契约](../../../Docs/Specs/Baleen/一级引导契约.md) 为准；整个引导器的职责见 [Baleen 引导器](../../../Docs/Specs/Baleen/README.md)。本文的 `BaleenStubHeader` 开发草案与介质上的 `BootDescriptor` 是两个独立结构，均未发布；本次只提出前者，不修改后者的现有字段。

## 一、职责与进入条件

IPL 校验 `BootDescriptor` 并读入 Stub 文件，然后固定跳转到 `0000:7E00`。它不解释任何 Stub 头，也不按头中的入口字段跳转。进入时 `DS=07C0`、`ES=0`、`SS:SP=0000:7C00`，`DL` 为实际读取驱动器号，`DH=2` 表示 HDD / USB-HDD、`DH=4` 表示 CD，`IF=1`、`DF=0`；其他寄存器、其他标志及 A20 状态不承诺。

描述符位于介质绝对偏移 `0x300`。其读盘缓冲在装入 Stub 时被覆盖，不能假设收到持久有效的描述符指针。Stub 必须保存仍需使用的驱动器与介质身份，并自行建立数据段、内存占用和运行环境。

未来 Stub 的职责是：

- 检查自身结构与内存占用，完成 BSS 初始化，并按本文的后续实现约定进行完整性自检。
- 建立并核验 A20 状态、取得内存图、维护 BIOS 磁盘会话及必要的调用状态。
- 按尚待定稿的 Core 定位、装载及交权契约加载 `BaleenCore.bin`，检查本阶段应负责的 Core 结构与装载边界。
- 无法完成必要初始化或装载时报告本阶段错误并停止；错误码、输出通道及恢复规则尚待设计。

`BaleenLayout.bin` 的系统卷语义、Ext4、内核集选版、签名策略和引导状态持久化属于 Core / UEFI。Stub 不承担这些策略。它对自身或未来 Core 的结构、内存与摘要检查，也不等于实现了内核集签名链。

## 二、BaleenStubHeader 开发草案

### 2.1 状态与采用规则

这是未发布的二进制结构草案，不表示解析器、生成器或校验器已经存在。若未来采用当前草案，整数均以小端序逐字节编码，不允许编译器插入填充；`Version=1` 暂作开发格式标记，`HeaderBytes=0x80` 标识当前头长。解析时须核对对应实现支持的格式标记、头长、摘要算法与保留字段，不能对不认识的结构猜测读取。

首发前可以直接修改这份草案并同步生成器、解析器与文档，不承担旧草案的迁移或兼容保证；首发后再建立正式版本管理规则。Stub 的构建身份与完整性信息放在自身头中，依据是阶段职责和 IPL 的代码、内存约束，不是为了兼容某个已经发布的描述符。

### 2.2 固定入口与文件布局

所有范围以 Stub 文件起点为 0，右端不含。

| 文件范围 | 内容 | 约束 |
| --- | --- | --- |
| `[0x00, 0x03)` | 16 位 `JMP rel16` 入口前缀 | 从 IPL 固定进入的文件偏移 0 跳到 `EntryOffset`；位移相对于该指令末端编码，由打包器核对其与头字段一致 |
| `[0x03, 0x10)` | 前缀保留字节 | 全 0 |
| `[0x10, 0x90)` | `BaleenStubHeader` | 固定为 128 字节 |
| `[0x90, ImageBytes)` | 早期初始化代码、其余代码与落盘数据 | 包含 `EntryOffset` 指向的入口；当前草案为直接装入的平坦镜像，不使用压缩或重定位 |
| `[ImageBytes, MemoryBytes)` | 未落盘的静态内存尾部 | 包含 BSS 与所需静态对齐空间，由 Stub 验证范围并清零 |

前缀也是 Stub 的可执行内容，列出它只为解决“固定 `0x7E00` 入口与数据头如何共存”的布局问题，本文不提供它的实现。IPL 不识别前缀、不检查其位移、不查找头。`EntryOffset` 是 Stub 自己的早期入口元数据，不是新的 IPL 交权地址，也不是 Core 的入口。

### 2.3 头字段字节表

下表偏移相对于头起点（文件偏移 `0x10`）。

| 头内偏移 | 字节数 | 字段 | 当前草案语义 |
| --- | --- | --- | --- |
| `0x00` | 8 | Magic | 字节 `42 4C 4E 53 54 55 42 00`，即 `BLNSTUB` 加终止零 |
| `0x08` | 2 | Version | 暂定 `1`，仅为未发布的开发格式标记 |
| `0x0A` | 2 | HeaderBytes | `0x80` |
| `0x0C` | 4 | Flags | `0`，当前不定义可选标志 |
| `0x10` | 4 | ImageBytes | Stub 整个文件的实际字节数，含入口前缀、完整头、代码与落盘数据；不含扇区填充和 BSS |
| `0x14` | 4 | MemoryBytes | 从物理 `0x7E00` 起的静态内存跨度，包含文件和未落盘尾部；不包含外部栈、内存图缓冲、磁盘缓冲或 Core 的单独分配 |
| `0x18` | 4 | EntryOffset | 从文件起点算起的早期初始化入口偏移；须在 `[0x90, ImageBytes)`，且与入口前缀一致 |
| `0x1C` | 2 | DigestAlgorithm | `1` = SHA-256；其他值拒绝，无“禁用摘要”值 |
| `0x1E` | 2 | BuildIdBytes | `32` |
| `0x20` | 32 | BuildId | Baleen 自身这一次构建的标识，不透明字节串；全零保留为“未分配”，正式产物不得使用 |
| `0x40` | 32 | Digest | 按第三节计算的 SHA-256 原始 32 字节摘要，不是十六进制文本 |
| `0x60` | 32 | Reserved | 全 0 |

约束至少包括 `0x90 < ImageBytes <= MemoryBytes`、`MemoryBytes <= 0x8200`，以及入口落在文件已初始化区域。`ImageBytes` 的介质限制仍为 HDD `<=0x8200`、CD `<=0x8000`；用于两种入口的同一文件按 CD 上限检查。所有加法和上取整均先检查溢出。

实际占用必须按 `max(MemoryBytes, ceil(ImageBytes / SectorBytes) * SectorBytes)` 预留，并保持 `0x7E00 + 实际占用 <= 0x10000`。完整扇区读取可能已写入 BSS 开头，Stub 仍须按定义清零，不能依赖介质填充碰巧为零。不得覆盖 `[0x7C00, 0x7E00)` 的 IPL；额外栈与其他缓冲必须另行依据内存图和所有权规则检查。

## 三、摘要覆盖与自引用处理

设文件的原始字节串为 `F`、实际长度为 `ImageBytes`。摘要字段位于文件 `[0x50, 0x70)`，计算时只将这 32 字节视为零：

```text
Digest = SHA-256(F[0x00:0x50] || 32 个零字节 || F[0x70:ImageBytes])
```

这里的切片右端均不含，`||` 表示字节串拼接。`Magic`、版本、长度、入口、BuildId、所有保留字节、入口前缀、代码和落盘数据均被覆盖；只有摘要本身按规则归零，避免自引用。SHA-256 的标准依据为 NIST [Hash Functions](https://csrc.nist.gov/projects/hash-functions) 与其列出的 [FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)。

覆盖范围不包含介质上的 `BootDescriptor`、最后一个本地扇区的文件外填充、BSS、其他运行时缓冲、Core、`BaleenLayout.bin` 或内核集。这些对象不能因 Stub 摘要通过而被声称已验证。

未来生成顺序必须是：先确定 Baleen BuildId、长度、入口和所有实际文件内容，将 `Digest` 置零；再计算并填入摘要；最后验证实际文件长度及头字段，并生成匹配的 `BootDescriptor`。摘要写入后再修改任何被覆盖字节都必须重算。校验器可以流式代入零字节，不应为计算摘要而改写自己的代码或头。

自校验针对**刚装入、尚未改写的文件字节**进行。自修改、重定位或把临时状态写进被覆盖数据区都会改变输入，当前草案不允许靠忽略这类字节来维持校验。早期代码使用哪些寄存器、栈和安全临时空间，必须由实际实现设计并证明。

## 四、Baleen BuildId 的归属

这里的 BuildId 标识 **Baleen 引导器构建**。它用于追踪 Stub 及未来与之配套的 Baleen 组件、检查打包时的构建配对，不能与 `.os`、`.osm` 和内核集构建清单的 BuildId 混用；后者的定义见 [内核集更新与回滚](../../../Docs/Specs/内核集更新与回滚.md)。

BuildId 由 Baleen 构建阶段分配，32 字节按原样比较；应绑定确定的源码、配置与构建输入，并支持相同输入下的可复现构建。具体输入清单、规范化编码与 ID 生成算法仍待后续设计。BuildId 必须先于文件摘要确定，不能从包含自身字段的最终文件摘要反推；不为它引入第二个自引用问题。

Stub 的摘要覆盖 BuildId，但 BuildId 相同不证明接口兼容、内容完整或来源可信。未来 Core 的头、构建标识携带方式与配对规则也必须独立定稿，不能假设目前已有可核验的 Core 身份。内核集的选择与签名仍由 Core / UEFI 处理。

## 五、检查责任与信任边界

| 执行方 | 检查责任 | 限制 |
| --- | --- | --- |
| IPL（当前） | `BootDescriptor` 结构、文件偏移与长度、全部必要扇区的读盘结果 | 不读取本草案头、不检查 BSS、BuildId 或摘要，不改变交权 ABI |
| 打包器（未来接入） | 实际文件长度等于 `ImageBytes`；描述符长度与之相同；头、入口前缀、内存尺寸、扇区上取整、摘要与 Baleen 构建配对一致 | 当前工具与占位载荷尚未接入本草案，不能宣称这些门禁已实现 |
| Stub（未来实现） | 先有界检查头与介质长度、内存跨度，再对原始文件字节自校验并完成初始化 | 已开始执行；描述符缓冲已被覆盖，不能假设能从传入指针独立复核 IPL 实际读取的文件字节数 |

打包器必须保证 `BootDescriptor.StubImageBytes == BaleenStubHeader.ImageBytes`。未来 Stub 的本地检查可使用 `DH` 选择文件上限，但它没有来自 IPL 的持久描述符副本；这不构成对原描述符和镜像匹配关系的独立证明。若未来需要重新读取并核对描述符，其过程、缓冲和失败语义另行设计，不能暗增 IPL 参数。

**Stub 自校验发生在 IPL 已经跳入并执行 Stub 之后，不能构成执行前认证，也不是信任根。** 攻击者若能同时改写内容、入口代码和摘要，也能绕过自校验；无密钥摘要最多用于检测非预期字节变化。真实的执行前认证需要可信的更早阶段或外部认证链，该方案尚未定义，不以扩大 IPL 职责冒充已经解决。

IPL 没有验头不等于缺陷，这是现有边界。未来 Stub 因自身头、BSS、A20、内存图或 Core 装载失败，应报告为 Stub 阶段错误；不能把错误归到 IPL，也不能失败后继续使用未检查的 Core。

| 验证与认证 | 头解析、摘要自检、打包校验尚未实现；执行前认证及其信任锚未定义 |

不得仅为满足头格式而在 `Stub/Out/Bin/` 生成同名空壳或停机件，让顶层“真实产物优先”逻辑误把它当成正式实现。当前正式 C++ 工具 `Tools/Build/MakePayloads` 生成的占位 Stub 只输出标记并停机，不采用本文头，不加载 Core，也不代表 Baleen 已能引导内核。

正常构建只能依赖正式源码与工具，不依赖不上传的 `Test` 目录或本地测试脚本。将来可用 NASM 汇编期断言及正式 C++ 工具执行格式和打包检查；额外的本地测试不构成本目录交付所必需的文件。完整测试记录与硬件验证应单独提供，本文不宣称通过。
